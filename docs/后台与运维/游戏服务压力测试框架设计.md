# MyServer 游戏服务压力测试框架设计

## 1. 文档定位

本文定义 MyServer 压力测试框架的目标、边界、总体架构、服务覆盖、场景模型、指标、线上安全门禁和分布式扩展方向，作为后续拆分开发 checklist 的上游设计依据。

本文描述目标态，不表示相关工具已经实现。具体协议字段、接口和服务行为以当前代码与对应专题文档为准；开发阶段若发现本文与代码冲突，应以代码为准并同步修正文档。

### 1.1 当前实现态（2026-08）

`tools/load-test` 已交付离线安全的运行骨架、账号 manifest/租约、预算与
保护门禁、报告脱敏、确定性 HTTP/KCP/WSS/gRPC 测试替身，以及可序列化的
controller/worker 契约。当前实现还包括：

- 通过正式 `game-proxy` KCP 入口的受门禁玩家流程，以及显式
  `two_player_default_match` 的双账号 `RoomJoin -> Ready -> Start -> Input ->
  FrameBundle -> Leave` 本地冒烟路径；房间 ID、策略和账号必须由外部预置，工具不会发现或创建房间。该路径不替代
  `game-proxy -> game-server -> match-service -> room` 的正式匹配容量验收。
- chat WSS、match gRPC/`MatchInternal`、mail HTTP 和 announce HTTP 的有界
  live 诊断 runner。它们只能在 `local`/`test` 且显式设置 `live_*` 开关时
  建立 transport；match 直连诊断不是正式玩家容量路径，mail/announce 生产写入
  和 mail 通知推送默认拒绝。
- 组合服务的步骤权重、`think_time_ms`、单玩家/全局操作上限，以及统一的
  新连接、业务消息、单连接消息和数据写入预算。该组合计划目前主要用于
  deterministic fake 和受控本地诊断，尚未在稳定环境中完成真实用户画像验收。
- 离线 `calibrate` 与 reconnect-burst planner/fake、Windows 发生器资源采样、
  按统一 batch boundary 合并 HDR 分布直方图、计数器和原始时间序列（禁止
  聚合节点预计算百分位数）、MetricBatch ledger、乱序/重复/缺口、pending
  溢出和 controller 失联 fail-closed 测试。

以下目标态能力尚未实现或尚未取得真实环境证据，不能从 dry-run、fake 或单服务
诊断报告推导：Redis service registry 心跳/发现收敛，服务实例及
PostgreSQL/Redis/Core NATS/宿主机观测，真实浸泡和重连风暴，以及重复运行基线验收。
离线 soak 窗口评估/滚动落盘和 baseline 身份/阈值比较模块已经存在，但缺少真实
长连接窗口和稳定环境重复运行数据时必须标记为不可比较。mTLS controller/worker
网络协议、短期 worker 凭证注册，以及多进程多 worker 验收仍未实现。
缺少或过期的服务端观测必须标记为观测空洞并阻止容量外推。

## 2. 目标与非目标

### 2.1 目标

- 在 Windows 开发机上以单机方式手动执行本地或受控线上压力测试。
- 分别测量 `auth-http` 登录、`game-proxy` 接入、`game-server` 玩家操作以及完整玩家链路。
- 覆盖聊天、匹配、邮件、公告、管理控制面、服务发现和指标链路等仓库内服务能力。
- 支持真实账号和批量生成的测试账号，但将账号准备与正式压测严格分离。
- 复用 `packages/proto`、正式 KCP 接入约定和已有联调客户端资产，避免形成第三套协议实现。
- 输出可比较、可追溯的吞吐、延迟、错误、连接和资源报告，并区分压测机瓶颈与服务端瓶颈。
- 在单机实现中预留 controller/worker 协议，使未来可以扩展为多机分布式压测。

### 2.2 非目标

- 首版不实现多机调度、云端压测平台或常驻 Web 管理页面。
- 不以压测工具替代功能测试、协议兼容测试、故障演练或生产监控。
- 不通过压测入口执行生产 GM 写操作、发布、摘流、停服、迁移、归档或数据修复。
- 不把直连 `game-server` 玩家端口、`game-proxy` TCP fallback 或内部固定端口的结果视为正式玩家链路容量结论。
- 不在一次测试中同时寻找所有服务的极限；完整覆盖由多个可独立执行、可组合的场景构成。

## 3. 核心设计原则

1. **正式入口原则**：无论目标是本地还是线上，玩家游戏流量都必须经过 `game-proxy`，压测工具不得直连 `game-server`。本地 TCP fallback 仅可用于协议诊断，不属于本框架的容量测试模式。
2. **协议复用原则**：Protobuf 以 `packages/proto` 为来源；KCP 配置、14 字节包头、消息类型、票据和版本策略应抽取或复用生产代码，不在压测场景中手写另一套实现。
3. **准备与执行分离**：账号注册、角色创建、测试数据初始化在独立 prepare 阶段完成，正式 run 阶段只消费已就绪账号。
4. **可组合场景原则**：单服务场景用于定位瓶颈，完整链路场景用于衡量玩家体验；两类结果分别报告。
5. **单机先校准原则**：任何服务容量结论都必须同时记录负载发生器资源和事件循环/调度延迟，压测机先饱和时不得宣称服务达到极限。
6. **线上默认拒绝原则**：远程目标必须显式授权、匹配白名单并配置硬上限；保护策略由程序强制执行，不能只依赖操作文档。
7. **低基数可观测原则**：报告和服务指标不得使用账号、玩家、角色、房间或 ticket 作为 metrics 标签，身份明细仅进入受限错误样本且必须脱敏。

## 4. 技术选型

压测框架的技术栈确认为 **Rust**，不再保留其他语言的运行时选项。正式负载发生器、账号准备器、场景执行器、指标聚合、报告生成以及未来的 controller/worker 均使用 Rust 实现。

场景采用声明式配置，扩展服务或玩家行为时通过 Rust trait 和模块实现，不引入动态脚本运行时。这样可以统一 KCP、Protobuf、长连接、帧同步、资源采样和分布式 worker 的并发模型，并保持单一构建与发布链路。

建议将以下能力收敛为可复用 Rust crate，而不是从应用目录复制代码：

- `packages/proto` 生成的游戏、聊天和匹配协议类型。
- `game-proxy` 使用的 `tokio_kcp` 配置和正式 KCP 连接约定。
- 玩家协议包头、封包、解包、消息大小限制和序列号关联。
- ticket、协议版本和服务 descriptor 的客户端校验规则。
- `tools/lockstep-client` 中可复用的帧同步输入与场景读取能力。

现有 `tools/mock-client` 已覆盖登录、选角、房间、移动、战斗、背包、聊天、邮件和公告等行为，仅作为场景语义和兼容行为基线；不能把其中的手工 Protobuf 编解码复制为新框架的长期协议层，也不作为压测运行时依赖。

## 5. 总体架构

建议新增独立工具 `tools/load-test`，并将账号准备器与正式运行器分开：

```text
tools/load-test/
├── Cargo.toml
├── src/
│   ├── bin/
│   │   ├── loadtest.rs          # 校验、运行、停止与报告入口
│   │   └── account-prepare.rs   # 批量账号与角色准备入口
│   ├── config/                  # 配置解析、环境与密钥引用
│   ├── safety/                  # 远程白名单、预算、确认与自动中止
│   ├── engine/                  # 调度器、虚拟玩家、阶段与节奏
│   ├── transports/              # HTTP、KCP、WSS、gRPC
│   ├── protocols/               # 共享协议适配与响应关联
│   ├── scenarios/               # 各服务和组合场景
│   ├── accounts/                # 账号池读取、租约与结果回写
│   ├── metrics/                 # 直方图、计数器、资源采样
│   └── report/                  # 控制台、JSON、CSV
├── scenarios/                   # 受版本控制的非敏感场景配置
└── README.md
```

运行时数据流：

```text
场景配置 + 环境配置 + 账号清单
                |
           Preflight/Safety
                |
         单机 Controller/Scheduler
                |
       Worker Runtime（首版进程内）
          |        |        |
        HTTP      KCP    WSS/gRPC
          |        |        |
       虚拟玩家状态机与服务场景
                |
      事件聚合 + 资源采样 + 中止判定
                |
        Console + JSON + CSV
```

即使首版 controller 与 worker 在同一进程，也应通过明确的数据结构交互：`RunPlan`、`WorkerAssignment`、`MetricBatch`、`WorkerHeartbeat`、`AbortSignal` 和 `RunSummary`。这些结构应支持序列化并携带 schema version，为未来分布式实现保留兼容边界。

## 6. 命令与生命周期

建议的概念命令如下，最终参数名可在实现阶段调整：

```text
account-prepare plan       计算账号和角色准备计划，不写入数据
account-prepare apply      按确认后的计划批量准备账号
account-prepare verify     验证账号可登录、角色已就绪
account-prepare export     输出不含明文密钥的账号池清单

loadtest validate          静态校验场景、目标和安全预算
loadtest calibrate         校准本机可承载的虚拟玩家与发送速率
loadtest run               执行压测
loadtest report            读取已有原始结果并生成摘要
```

单次运行生命周期固定为：

```text
Created -> Validated -> WarmingUp -> Ramping -> Steady -> CoolingDown -> Completed
                                   \-> Aborting -> Aborted
                                   \-> Failed
```

正常结束和自动中止都必须停止创建新会话，给已有会话有限的优雅退出时间，随后强制释放连接并落盘最后一批指标。

## 7. 配置模型

配置分为三层：

- **环境配置**：目标环境名称、入口地址、远程白名单、安全预算和服务公开 descriptor。
- **场景配置**：用户模型、步骤、权重、负载阶段、断言和阈值。
- **本机私密配置**：账号清单、密码引用、管理或内部测试 token；必须被 Git 忽略。

场景文件不得包含密码、access token、ticket、数据库连接串或线上管理凭证。敏感值通过环境变量或本机 secret 文件引用，报告只保存引用名和脱敏摘要。

示例结构：

```toml
schema_version = 1
name = "full-player-flow"

[environment]
profile = "local"
auth_base_url = "http://127.0.0.1:3000"
game_proxy = "127.0.0.1:4000"

[load]
model = "stages"
max_virtual_users = 1000
duration = "20m"

[[load.stages]]
duration = "2m"
target_virtual_users = 100

[[load.stages]]
duration = "5m"
target_virtual_users = 500

[thresholds]
max_error_rate = 0.01
p99 = "500ms"

[safety]
max_login_rate = 100
max_new_connections_per_second = 100
```

配置解析必须拒绝未知字段、重复阶段、零时长、无界并发、负数速率、互相冲突的负载模型和无法解析的目标地址。

## 8. 账号准备与数据隔离

### 8.1 独立准备器

批量账号准备器不属于正式负载发生器。它负责：

- 从已有真实账号清单导入账号引用。
- 通过受支持的注册接口或现有 `apps/auth-http/scripts/seed-test-accounts.js` 能力批量生成测试账号。
- 按场景需要创建角色、选择角色并验证 ticket 签发前置条件。
- 使用统一命名空间和批次号，例如 `loadtest_<environment>_<batch>_<index>`。
- 输出账号池 manifest，记录逻辑账号 ID、来源、批次、角色就绪状态和最后验证时间。
- 提供幂等重跑、部分失败续跑和只读 verify；清理属于独立高风险动作，不与 prepare 或 run 隐式绑定。

### 8.2 账号租约

运行器对账号采用租约模型，避免同一账号被多个虚拟玩家意外复用。manifest 不保存明文密码，账号凭据通过 secret provider 按逻辑 ID 读取。

允许显式定义同账号并发登录场景，但它必须使用独立场景类型并标记预期的 session kick 或覆盖行为，不能由账号池不足隐式触发。

### 8.3 指标隔离

账号准备的注册 QPS、角色创建成功率和耗时单独报告，不计入登录或完整链路压测结果。测试产生的玩家、角色、邮件、公告和聊天内容必须带批次标识，便于审计和后续受控清理。

## 9. 负载模型与虚拟玩家

首版应支持：

| 模型 | 语义 | 适用场景 |
|------|------|----------|
| 固定并发 | 保持指定数量的活跃虚拟玩家 | 最大在线数、长连接稳定性 |
| 固定到达率 | 每秒启动指定数量的迭代 | 登录、HTTP、建连吞吐 |
| 阶梯升压 | 分阶段提升并发或到达率 | 查找稳定容量和性能拐点 |
| 突发 | 在短窗口集中创建负载 | 开服、断线重连、公告刷新 |
| 浸泡 | 长时间保持稳定负载；离线实现按窗口滚动落盘并比较资源/尾延迟漂移 | 泄漏、积压、连接老化；真实长连接执行和服务端观测仍需受控验收 |

调度器使用单调时钟，区分排队时间、客户端处理时间、网络时间和端到端业务时间。发生器无法按计划发出操作时记录 `scheduler_lag`，不得通过无限积压补发制造非预期突发。

虚拟玩家状态机至少包含：

```text
AccountLeased
  -> LoggedIn
  -> CharacterSelected
  -> TicketIssued
  -> ProxyConnected
  -> GameAuthenticated
  -> Active
  -> Leaving
  -> Closed
```

`Active` 阶段按场景组合房间、移动、战斗、背包、匹配、聊天、邮件和公告行为。每个步骤都应声明超时、重试策略、幂等性、think time 和预期响应；写操作默认不自动重试。

## 10. 全量服务覆盖矩阵

### 10.1 玩家数据面

| 服务 | 入口与协议 | 核心场景 | 主要指标 |
|------|------------|----------|----------|
| `auth-http` | 稳定 HTTP 入口 | 登录、`me`、选角、签发/刷新 ticket、登出、重复登录、失败与限流 | QPS、P50/P95/P99、状态码/业务码、ticket 成功率、限流率 |
| `game-proxy` | 正式 KCP 入口 | 建连、AuthReq、心跳、消息转发、保持连接、重连、无效/过期 ticket | 新连接率、活跃连接、鉴权延迟、收发吞吐、断线与重连率 |
| `game-server` | 仅经 `game-proxy` 间接施压 | 房间创建/加入/离开/重连、移动、帧同步、战斗、背包和游戏业务操作 | 操作延迟、帧输入/下行速率、拒绝/超时、房间与玩家状态、tick 延迟 |
| `chat-server` | 正式环境使用 auth 下发的 WSS descriptor | 鉴权、连接保持、私聊、群聊、历史、在线 push、重连和慢消费者 | WSS 握手、活跃连接、消息吞吐、持久化延迟、push 成功率、队列积压 |
| `mail-service` | 玩家 HTTPS descriptor | 列表、详情、已读、领取、通知到达；发信只作为受控内部组合场景 | HTTP 延迟、领取结果分类、幂等命中、outbox/NATS 通知延迟 |
| `announce-service` | 玩家可达的稳定 HTTP/HTTPS descriptor | 公告列表、详情、缓存命中、周期刷新；CRUD 仅限隔离环境 | 读 QPS、延迟、缓存/数据库压力、错误率 |
| `match-service` | 玩家流程经正式游戏入口触发，内部为 gRPC | 开始、取消、状态、事件流、成组匹配、超时、进入房间和结束 | 排队时间、匹配成功率、流连接数、gRPC 延迟、房间创建闭环时间 |

`match-service` 的直接 gRPC 压测用于服务隔离容量诊断，只允许从开发或隔离网络执行；正式玩家容量结论必须来自经 `game-proxy -> game-server -> match-service` 的完整流程。

### 10.2 控制面与辅助服务

| 服务/能力 | 覆盖方式 | 边界 |
|-----------|----------|------|
| `admin-api` | 只读登录、玩家查询、审计查询、监控总览与详情的受控负载 | 写操作、breakglass、封禁、发奖、踢人、迁移、摘流、停服和归档不做生产压测 |
| `admin-web` | 浏览器侧页面性能和静态资源检查，必要时独立使用浏览器工具 | 不由核心 Rust 引擎模拟 DOM；API 容量归入 `admin-api` |
| `metrics-collector` | 在业务压测期间观察 NATS 消费、Redis 快照新鲜度和积压 | 不单独制造无业务语义的生产 metrics 洪泛 |
| Redis service registry | 观察注册心跳、发现延迟、stale 清理和多实例路由收敛 | 正常容量测试只读发现结果；故障注入归入独立演练 |
| PostgreSQL、Redis、Core NATS | 作为依赖层关联观测 | 不默认绕过服务直接压数据库、Redis 或 NATS；专项基准另立场景和授权 |
| `myforge-agent` 及开发代理能力 | 健康和只读查询可纳入控制面基线 | 任务创建、取消、暂停、恢复不属于常规压测 |

### 10.3 完整链路场景

至少定义以下组合场景：

1. **登录入服**：账号租约 -> 登录 -> 角色列表/选择 -> ticket -> KCP 连接 `game-proxy` -> AuthReq -> 心跳。
2. **普通在线玩家**：登录入服 -> 房间 -> 按真实 think time 执行移动、轻量业务读取和偶发背包操作。
3. **帧同步房间**：多玩家经 proxy 进入同房间 -> 按帧提交输入 -> 接收帧广播/快照 -> 离开或重连。
4. **匹配闭环**：登录入服 -> 发起匹配 -> 事件结果 -> 房间加入 -> 对局结束。
5. **社交闭环**：登录 -> WSS 聊天鉴权 -> 私聊/群聊 -> 持久化与在线推送。
6. **邮件闭环**：受控内部发信 -> outbox/NATS -> 在线通知 -> 玩家列表/详情/已读/领取；写入和领取必须使用专用测试数据。
7. **公告读取**：登录响应获得服务信息 -> 周期拉取公告列表/详情，模拟正常缓存节奏与开服突发。
8. **重连风暴**：已有在线玩家集中断线，在抖动退避约束下重新登录或重新连接，验证 session、ticket、proxy 路由和房间恢复。

## 11. 协议与传输复用要求

### 11.1 玩家游戏协议

- 包头、magic、version、flags、message type、sequence 和 body length 必须与正式协议一致。
- 请求与响应按 sequence 关联，push 独立计量；超时后到达的响应标记为 late response，不能计入新的请求。
- KCP 使用与 `game-proxy` 正式 frontend 一致的配置，包括 stream 模式和 no-delay 策略。
- `AuthReq`、ticket ownership、character-bound ticket 和协议版本规则遵循当前服务实现。
- 场景运行前执行协议兼容校验；共享 proto 变化后压测工具必须随仓库生成流程同步构建。

### 11.2 服务地址

- `auth-http`、`game-proxy` 使用稳定玩家入口。
- `chat-server`、`mail-service` 等正式玩家可达地址优先使用 auth 响应下发的公开 descriptor。
- 内部服务专项测试通过 Redis service registry endpoint 发现目标实例，不从 `apps/port.txt` 推断线上地址。
- 本地固定端口只作为 development/local 默认值。
- 任意环境的玩家游戏场景都禁止配置 `game-server` 玩家端口作为目标。

## 12. 指标与结果模型

### 12.1 客户端指标

- 当前、已启动、已完成和失败的虚拟玩家数。
- 请求/操作吞吐、字节吞吐、新建连接率和活跃连接数。
- P50、P90、P95、P99、最大值和 HDR histogram 等可合并延迟分布。
- HTTP 状态码、gRPC status、协议业务错误码、断线原因和超时分类。
- 登录、签票、鉴权、进房、首帧、匹配、聊天 push、邮件通知和领取的端到端耗时。
- `scheduler_lag`、任务队列深度、客户端编码/解码耗时和本地丢弃数。

### 12.2 负载发生器指标

- 进程 CPU、工作集/常驻内存、线程数和句柄数。
- 网络收发字节、UDP/TCP socket 错误和可用端口压力。
- Tokio 调度延迟、worker 队列积压和指标通道丢弃数。
- 指标采集本身的 CPU 与写盘耗时。

Windows 首版至少采集进程级资源；无法可靠获得的系统指标必须在报告中标记 `unavailable`，不得默认为零。

### 12.3 服务端关联

运行器不应把服务端监控数据混进客户端测量值。报告通过统一时间戳和 `run_id` 并列展示：

- admin-api/metrics-collector 提供的服务级和实例级 metrics 快照。
- game-proxy 连接、鉴权、路由和转发指标。
- game-server 在线玩家、房间、tick、消息和业务拒绝指标。
- chat 队列、NATS push、mail outbox/claim、match 排队等专题指标。
- PostgreSQL、Redis、NATS 和宿主机资源指标由部署监控提供；缺失时明确记录观测空洞。

### 12.4 输出

每次运行建立独立结果目录：

```text
reports/<run-id>/
├── run.json             # 配置摘要、版本、目标、状态和结论
├── metrics.json         # 可合并直方图与计数器
├── timeseries.csv       # 时间序列
├── errors.jsonl         # 有界、脱敏的错误样本
└── summary.md           # 人类可读摘要
```

报告记录工具 Git commit、场景 hash、开始/结束时间、环境名称、目标地址脱敏摘要、安全预算、账号批次、压测机信息和自动中止原因。禁止保存密码、access token、ticket、内部管理 token 和完整个人信息。

## 13. 容量判定与基线

测试结果应区分：

- **负载发生器容量**：本机在不超过资源阈值、`scheduler_lag` 阈值和指标丢失阈值时可生成的最大稳定负载。
- **服务稳定容量**：在持续观察窗口内满足延迟、错误率、资源、积压和业务正确性阈值的最大负载。
- **系统突发容量**：短时间流量峰值下不会雪崩且能在规定时间恢复的负载。

首次运行某场景前执行 calibrate：使用本地或隔离目标逐级增加虚拟玩家，找到发生器稳定上限，并为正式测试保留资源余量。建议发生器 CPU 或内存持续超过预算、调度延迟超过一个业务节拍、指标发生丢弃时立即判定本机成为瓶颈。

阈值必须在场景中显式配置。平均延迟只作辅助展示，不能作为通过标准；至少使用 P95/P99、错误率、业务成功率和持续时间共同判断。

## 14. 线上安全门禁

### 14.1 默认行为

- 默认只允许 loopback 和明确标记的 local profile。
- 远程运行必须同时提供 `--allow-remote`、环境 profile、目标白名单和非空变更/审批引用。
- 启动前打印环境、解析后的 IP/域名、账号批次、最大并发、最大速率、持续时间和写操作摘要，并要求输入环境名称确认。
- DNS 解析结果必须在运行前和运行中校验；解析到白名单外地址时拒绝继续，避免 DNS rebinding 或配置漂移。
- production profile 禁止无限时长、无上限并发、无上限到达率和无阈值运行。

### 14.2 强制预算

每个远程场景必须同时具有：

- 最大虚拟玩家数。
- 最大登录 QPS。
- 最大新连接速率。
- 最大业务消息速率和单连接消息速率。
- 最大持续时间和最大总操作数。
- 最大允许错误率、连接失败率和 P99。
- 最大测试数据写入量。

命令行只能收紧 profile 中的预算，不能放宽；放宽必须修改受版本控制或受审批的环境策略。

### 14.3 自动中止

以下条件达到连续窗口后自动中止：

- 错误率、超时率、连接失败率或 P99 超过阈值。
- 服务 readiness/health 恶化、关键依赖不可用或监控数据变 stale。
- 压测机 CPU、内存、调度延迟或指标丢失超过阈值。
- 收到本机停止文件、Ctrl+C、controller abort 或预设停止时间。
- 目标地址、证书、服务 descriptor 或环境身份发生非预期变化。

自动中止采用 fail-closed：无法确认线上保护状态时停止加压，而不是继续运行。

### 14.4 线上场景限制

- 默认只允许带明确测试标识的专用账号；真实账号必须逐项列入 allowlist。
- 邮件发放、公告 CRUD、GM、封禁、踢人、发奖、角色修改和运维控制接口默认禁止。
- 不执行故障注入、kill、网络阻断、数据库写入脚本或 registry 篡改。
- 只读接口也必须限速，避免审计查询或大分页拖垮数据库。
- 测试窗口、观察人、停止责任人和回滚/清理方式应在运行前确定。

## 15. 分布式扩展设计

首版不实现分布式执行，但代码边界应支持后续演进：

当前代码已经实现并测试进程内可复用的 `RunPlan`、`WorkerAssignment`、
`MetricBatch`、`WorkerHeartbeat`、`AbortSignal` 和 `RunSummary` 契约，以及计划
切片、账号分片、批次 checksum/去重/缺口、有限 pending、凭证状态校验和中止
收敛状态机。这些是离线契约和确定性测试，不等同于下面所述的网络化多 worker
实现；mTLS、worker 注册和跨进程验收仍属于后续阶段。

```text
                 Controller
        计划切片 / 门禁 / 聚合 / 中止
           /           |           \
       Worker A     Worker B     Worker C
       独立账号段    独立账号段    独立账号段
           \           |           /
           MetricBatch + Heartbeat
```

### 15.1 Controller 职责

- 校验全局安全预算并把负载切分为 worker assignment。
- 为账号池分配互斥分片和租约，不向 worker 广播全部密钥。
- 统一阶段起止时间，聚合可合并直方图、计数器和时间序列。
- 根据全局与单 worker 阈值发出 abort，并等待有界确认。
- 保存 worker 身份、版本、时钟偏差、丢失区间和最终状态。

### 15.2 Worker 职责

- 执行不可再拆分的虚拟玩家分片。
- 周期发送 heartbeat、资源状态和有界 `MetricBatch`。
- controller 失联后 fail-closed，停止增压并在租约到期后结束已有会话。
- 本地持久化未上报结果，恢复连接后按 batch sequence 去重补交。

### 15.3 一致性与时间

- 以 controller 下发的逻辑阶段为准，worker 使用单调时钟执行并报告 wall clock 映射。
- 聚合直方图必须使用相同边界和 schema version，不能聚合各节点计算后的百分位数。
- 每个 `MetricBatch` 携带 `run_id`、`worker_id`、sequence、时间窗口和 checksum。
- worker 丢失时报告必须标注数据不完整，不把剩余 worker 的吞吐外推为全局结果。

### 15.4 传输与安全

未来 controller/worker 可采用 mTLS gRPC；控制协议独立于被测业务协议。worker 使用短期凭证注册，只能读取自己的 assignment、上报指标和接收停止信号。账号 secret 按分片下发或由 worker 从受控 secret provider 获取，不写入 controller 日志。

## 16. 测试与验收策略

框架自身需要以下验证层次：

1. **单元测试**：配置拒绝规则、预算合并、状态机、直方图合并、账号租约、脱敏和中止判定。
2. **协议兼容测试**：共享 proto 生成、包头、消息类型、KCP 配置、ticket 和版本策略与生产代码一致。
3. **确定性假服务测试**：HTTP/KCP/WSS/gRPC 假服务返回成功、慢响应、错误、断连和乱序 push，验证统计分类。
4. **本地真实服务冒烟**：经用户确认并启动依赖后，以极小负载走完整入口链路。
5. **单机场景校准**：确认发生器资源采样和 `scheduler_lag` 能识别客户端瓶颈。
6. **安全门禁测试**：验证远程默认拒绝、白名单、预算不可放宽、DNS 变化、自动中止和报告脱敏。
7. **结果稳定性测试**：同一稳定环境重复执行，比较吞吐与分位延迟偏差，并记录允许波动范围。

截至当前实现，单元测试、协议兼容测试、确定性假服务、离线校准/soak/baseline、
预算/中止、报告脱敏和分布式契约状态机均可在 Windows 工作区离线运行；真实服务冒烟仅在
用户明确确认并启动依赖后执行。真实聊天服务端持久化、匹配玩家完整闭环、邮件
outbox/NATS 通知、公告缓存行为、registry/实例 metrics、浸泡/重连风暴和重复
运行基线验收仍需独立记录环境、目标、账号批次、预算和观察空洞，不能用离线测试代替。

按照仓库协作约定，开发完成后不得自动启动 Redis、PostgreSQL、NATS 或应用服务，也不得直接执行集成压测；应先列出需要的服务、数据和预计负载，待用户确认后运行。

## 17. 建议开发阶段

本文覆盖全量服务，后续开发拆分为两份 checklist，每份固定三个阶段。第一层是 checklist 文件，第二层是文件内的开发阶段；每个阶段都应能够独立实现、验证和提交。

建议文件名遵循 `{中文文件名}_checklist.md` 约定：

1. `压力测试框架01_核心链路_checklist.md`
2. `压力测试框架02_全量服务与扩展_checklist.md`

### 17.1 checklist01：核心框架与玩家主链路

目标是交付一个可以在开发机上运行、具备安全门禁和报告能力，并能完成 `auth-http -> game-proxy -> game-server` 正式玩家链路压测的 Rust 工具。

#### 阶段 1：共享协议、运行骨架与安全基线

实现范围：

- 建立 `tools/load-test` Rust workspace/package、`loadtest` 与 `account-prepare` 二进制入口。
- 确定并实现共享 Protobuf、玩家协议包头和正式 KCP 配置的复用边界，禁止复制生产协议实现。
- 建立严格配置 schema、环境 profile、运行状态机、固定并发/到达率/阶梯/突发调度骨架。
- 建立远程默认拒绝、目标白名单、硬预算、停止信号、自动中止和敏感信息脱敏。
- 建立客户端指标、发生器资源采样、JSON/CSV/Markdown 报告以及有界错误样本。

阶段验证出口：

- 配置、预算合并、状态机、指标聚合、报告脱敏和远程拒绝具备单元测试。
- HTTP、KCP 和协议层具备确定性假服务或测试替身，能够验证成功、超时、错误、断连和 late response 分类。
- Windows 下可以执行 `validate` 和无真实服务的最小 dry-run，不启动 Redis、PostgreSQL、NATS 或应用服务。

#### 阶段 2：账号准备与 auth-http 压测

实现范围：

- 实现独立账号准备器的 `plan`、`apply`、`verify` 和 `export`，支持已有真实账号与批量测试账号。
- 实现账号批次标识、manifest、secret 引用、互斥租约、幂等续跑和角色准备。
- 实现登录、`me`、角色列表/创建/选择、ticket 签发或刷新、登出、失败登录和限流场景。
- 确保账号注册与角色准备指标不进入正式登录压测统计。
- 实现 HTTP 固定到达率、阶梯升压、突发登录和同账号显式并发场景。

阶段验证出口：

- 账号 manifest、租约、secret 脱敏、部分失败续跑和 prepare/run 指标隔离具备单元测试。
- auth 假服务覆盖正常、限流、业务错误、超时和无效响应。
- 经用户确认并启动所需依赖后，以极小负载完成本地 `auth-http` 冒烟；未确认时保留为待验证项。
- 报告能够输出登录 QPS、P50/P95/P99、状态码/业务码、ticket 成功率和发生器资源。

#### 阶段 3：game-proxy 接入与 game-server 玩家行为

实现范围：

- 通过正式 KCP 入口连接 `game-proxy`，实现 AuthReq、心跳、连接保持、断线、退避重连和无效/过期 ticket 场景。
- 在配置和运行时双重拒绝任何 `game-server` 玩家端口目标，本地与线上均不得绕过 `game-proxy`。
- 打通账号租约、登录、选角、ticket、proxy 鉴权和正常退出的完整入服状态机。
- 实现房间创建/加入/离开/重连、移动、帧同步、战斗、背包和代表性游戏业务场景。
- 复用 `tools/lockstep-client` 可下沉的帧同步能力，建立空闲、普通和高频合法玩家画像。
- 实现单机 calibrate、重连突发和 `scheduler_lag` 判定，区分发生器瓶颈与服务端瓶颈。

阶段验证出口：

- KCP 配置、包头、消息类型、sequence 关联、push、ticket 和协议版本与生产代码完成兼容验证。
- 假服务覆盖建连、鉴权、消息转发、乱序 push、断线、重连和慢响应。
- 经用户确认并启动完整依赖后，以极小负载完成 `auth-http -> game-proxy -> game-server` 本地主链路冒烟。
- 报告能够区分登录、建连、鉴权、进房、首帧和业务操作耗时，并记录连接、帧、吞吐和发生器资源。

实现范围：

## 18. 完成定义

压力测试框架整体完成需同时满足：

- 所有玩家游戏场景只通过 `game-proxy` 进入，不存在直连 `game-server` 的正式模式。
- auth、proxy、game、chat、match、mail、announce 和完整玩家链路均有可重复场景。
- admin-api 和辅助服务具备明确的只读或专项覆盖边界。
- 账号准备与压测运行完全分离，账号池可标识、校验、租约和受控清理。
- Rust 引擎复用共享协议与正式 KCP 约定，不维护独立手写协议副本。
- 固定并发、固定到达率、阶梯、突发和浸泡负载可表达。
- 客户端、服务端和压测机指标能够关联，报告可比较且不泄露敏感信息。
- 本地运行可校准单机极限，结果不会把发生器瓶颈误判为服务容量。
- 远程目标默认拒绝，线上运行具备白名单、硬预算、逐级升压、自动中止和人工紧急停止。
- controller/worker 数据契约可序列化并带版本，后续能够扩展为分布式执行。
