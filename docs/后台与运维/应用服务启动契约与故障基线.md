# 应用服务启动契约与故障基线

## 1. 文档范围

本文定义 `game-server`、`match-service`、`game-proxy` 的应用启动收敛契约，并记录改造前可重复验证的故障基线。第 2、3 节是提交 `2099771` 的历史基线；当前实现状态以第 7、8 节和代码为准。

基础设施仍可作为进程启动的硬前置。应用服务 endpoint 暂缺、registry 短时不可用或连接尚未建立必须由 readiness 和依赖状态表达，不能用固定应用启动顺序或 restart loop 表达。

## 2. 阶段 1 基线启动与退出盘点

本节冻结提交 `2099771` 建立的改造前故障基线，用于说明第 3 阶段仍需消除的首次 discovery fail-fast 边界。第 2 阶段已经新增动态健康状态，实际接口与配置见第 7 节。

### 2.1 game-server

当前实际顺序如下：

1. `main.rs` 加载配置、日志和 CSV。
2. 创建 registry client，立即注册标记为 healthy 的 instance，并启动 heartbeat。此时业务 listener、worker lease 和依赖尚未就绪。
3. 初始化 CSV reload、审计存储和 metrics task。
4. `server::run` 依次绑定玩家 TCP、admin TCP、`proxy-local` socket 和 `internal` socket。
5. 连接 Redis，通过一次 `SET ... NX` 获取 global-ID worker lease，并启动 renewal task。
6. `MatchClientConfig::from_env().await` 执行首次 `match-service.grpc` discovery；随后才尝试建立 gRPC client并启动 rediscovery task。
7. 初始化玩家和游戏数据存储、共享运行时、admin/local/internal/NATS tasks。
8. 最后绑定当前固定的 `/readyz` listener，并进入玩家 TCP accept loop。
9. active loop 退出后 abort 后台 task，compare-and-delete worker lease，关闭数据存储；返回 `main` 后停止 registry heartbeat 并 deregister。

重要现状：首次 match endpoint 为空时不是 `init_match_client` 的可恢复连接错误。`MatchClientConfig::from_env` 在 `resolve_match_service_addr(...).await` 后显式 `panic!`。panic 发生时两个 TCP listener、两个 local socket、worker lease 和 renewal task 已经存在，且不会进入 `server::run` 尾部或 `main` 的正常清理路径。

改造前没有独立 liveness endpoint，`/readyz` 固定返回成功；第 2 阶段已替换为动态 `/livez` 和 `/readyz`。

### 2.2 match-service

当前实际顺序如下：

1. 加载配置与日志，立即注册 healthy instance 并启动 heartbeat。
2. `server::run` 连接 Redis、获取 worker lease并启动 renewal。
3. 创建 matcher/runtime store，恢复匹配运行态，创建 cleanup task。
4. 解析 gRPC 地址并由 tonic 绑定/serve。
5. SIGINT 或 lease loss 触发 gRPC shutdown；退出后停止 renewal 并 compare-and-delete 自己的 lease。
6. 返回 `main` 后停止 heartbeat 并 deregister。

`game-server.internal` discovery 位于匹配业务请求路径，不是当前进程 bootstrap 的直接步骤。目标契约把它定义为 optional/request-level capability：没有可用 internal endpoint 时拒绝或冻结建房并进入 degraded，但不阻止 `match-service.grpc` readiness、healthy endpoint 发布或无关查询运行。NATS metrics 同样是 optional capability。

改造前 `match-service` 没有独立 liveness/readiness listener；第 2 阶段已补齐监听器，并把 `game-server.internal` 保持为 optional capability。

### 2.3 game-proxy

当前实际顺序如下：

1. 加载配置、日志、route store、Redis 鉴权/维护状态，并注册 healthy instance和启动 heartbeat。
2. 启动 admin task。
3. `proxy_server::run` 校验 discovery 配置，创建 registry client并执行首次 `game-server.proxy-local` discovery。
4. registry client 创建或 discovery 错误通过 `?` 返回；endpoint 数为零时显式返回 `Err`。此时玩家 KCP/TCP frontend 和 readiness 尚未绑定。
5. 首次 discovery 成功后启动后台 discovery，随后绑定 KCP、TCP fallback 和 `/readyz`，进入 accept loop。
6. `proxy_server::run` 返回后，`main` abort admin/route-store task，停止 heartbeat并 deregister，最后返回原始结果。

改造前没有独立 liveness endpoint；第 2 阶段已让后台 discovery 丢失全部 upstream 时转为 degraded/not-ready。

## 3. 依赖分类

`required` 表示该依赖缺失会阻止 readiness，但不应仅因暂缺而结束进程。`optional` 表示缺失时进入 degraded，关闭依赖它的能力并保留无关业务。

| 服务 | 依赖或本地资源 | 分类 | 缺失时目标行为 |
|------|----------------|------|----------------|
| `game-server` | Redis registry、自身 instance/heartbeat | required | `WaitingDependencies`、not-ready、重试 |
| `game-server` | Redis worker lease | required ownership | 有界等待；lease lost 属于不可继续运行的 fatal ownership error |
| `game-server` | 玩家/admin/local/internal listener | required local | 启动阶段失败并统一 rollback；socket 冲突使用稳定错误码 |
| `game-server` | `match-service.grpc` | required readiness | 保持存活并持续发现；匹配通知能力冻结 |
| `game-server` | PostgreSQL gameplay store | required when corresponding DB capability enabled | not-ready；非法配置或不兼容 schema 可 fatal |
| `game-server` | NATS metrics、session kick、GM broadcast | optional | degraded；无关玩家主链路继续 |
| `match-service` | Redis runtime/worker lease/registry | required | not-ready并重试；lease lost fatal |
| `match-service` | gRPC listener | required local | 启动失败并 rollback |
| `match-service` | `game-server.internal` | optional request capability | 保持 gRPC ready，进入 degraded，拒绝/冻结建房并持续发现 |
| `match-service` | NATS metrics | optional | degraded；匹配主链路继续 |
| `game-proxy` | Redis auth/route store/registry | required | not-ready并重试；非法 route-store 配置可 fatal |
| `game-proxy` | `game-server.proxy-local` | required readiness | 保持入口进程存活但不接玩家流量，持续发现 |
| `game-proxy` | KCP/TCP/admin listener | required local | 启动失败并 rollback |

required application dependency 超过启动收敛窗口后仍保持进程存活和 not-ready，由发布门禁报警或回滚。optional dependency 暂缺不阻止无关流量；readiness 是否成功只由 required blockers 和本地接流量资源决定，degraded 状态必须同时输出具体 capability。

三服务的应用依赖图必须无 required 环：`match-service` 在 registry、lease 和 gRPC listener 就绪后即可发布 healthy `grpc` endpoint；`game-server` 发现该 required endpoint 后进入 Ready 并发布 `internal` endpoint；`match-service` 随后发现 optional `game-server.internal`，恢复建房 capability。任意一方先启动都能沿该方向收敛，不会出现双方等待对方 healthy 的循环。

## 4. 统一状态机

```text
Starting -> WaitingDependencies -> Ready <-> Degraded -> ShuttingDown
    |                 |              |          |
    +-----------------+--------------+----------+
                              fatal/stop
```

- `Starting`：校验配置并取得实例身份、listener、lease 等本地所有权；不得宣称 healthy。
- `WaitingDependencies`：本地 bootstrap 可继续运行，但至少一个 required dependency 尚未收敛；liveness 成功，readiness 失败。
- `Ready`：required dependency、本地资源、自身 registry identity 与稳定窗口全部满足，可以接流量。
- `Degraded`：运行期能力部分丢失或 optional dependency 不可用。是否 ready 由 required blocker 独立决定，诊断必须列出受影响 capability。
- `ShuttingDown`：停止接新流量，drain，并只清理当前实例拥有的 registry、lease、listener 和 socket。

合法转换由 `service_registry::startup_contract::StartupState` 固化。配置非法、lease ownership 丢失、无法保证唯一性或不可恢复的本地资源错误可以转入 `ShuttingDown`；dependency pending/timeout 和 registry 短时失败不能直接成为进程退出理由。

## 5. 稳定错误码与观测字段

稳定错误码：

| 错误码 | 含义 |
|--------|------|
| `DEPENDENCY_PENDING` | required/optional dependency 尚未出现或未连接 |
| `DEPENDENCY_TIMEOUT` | 超过有界收敛窗口，进程仍应存活并保持 not-ready |
| `REGISTRY_UNAVAILABLE` | registry client 创建、读写或 watch 暂时不可用 |
| `LEASE_UNAVAILABLE` | 目标 worker lease 当前由其他 owner 持有 |
| `LEASE_LOST` | 当前实例不再拥有已取得的 lease，必须停止使用对应 ID generator |
| `SOCKET_CONFLICT` | 当前实例 socket 路径被占用且不能安全接管 |
| `STARTUP_PHASE_FAILURE` | 无更具体错误码的本地 bootstrap 阶段失败 |

所有状态转换、readiness 原因和发布诊断统一输出以下字段：

```text
service instance_id lifecycle_state startup_phase
dependency endpoint dependency_requirement error_code
retry_count elapsed_ms last_success_at_ms
```

字段不得包含 URL userinfo、token、密码、私钥、完整 Redis/数据库连接串或其他可复用凭据。人类可读 message 可以变化，自动化只依赖稳定错误码和字段。

其中 `endpoint` 只表示 `grpc`、`proxy-local`、`internal` 等逻辑 endpoint 名称；连接地址、socket 路径或带 userinfo 的 URL 不得写入该字段。

## 6. 可重复故障基线

`tests/fixtures/startup-convergence-baseline.json` 固化无环依赖契约和四个输入场景。`tests/registry/startup-convergence-baseline.test.mjs` 只校验场景清单、依赖图和当前源码资源顺序；实际错误行为由对应 Rust 单元测试复现：

| 场景 | 当前 HEAD 结果 | 退出传播点 |
|------|----------------|------------|
| match 尚未注册 | `game-server` panic；lease/socket 已创建 | `MatchClientConfig::from_env` 的显式 `panic!`，不是相邻的 `init_match_client` 错误日志，也不是 `?` |
| worker lease 未过期 | `game-server` bootstrap 返回错误 | `WorkerLease::acquire_redis(...).await.map_err(...) ?`；Redis `SET NX` 返回未取得 |
| 残留两个 local socket | 首个冲突处立即返回错误，后续资源不统一回收 | `create_listener_pair(...) ?` 内按 local/internal 顺序 bind；当前没有 stale reclaim |
| proxy 找不到 endpoint | `game-proxy` 返回错误并进入 main 清理 | `validate_initial_upstream_routes` 对 `initial_routes == 0` 显式返回 `Err`；registry client/discovery 错误另由 `?` 返回 |

- `global_id::tests::occupied_requested_worker_lease_is_unavailable` 直接把 Redis `SET NX` 的 `Ok(None)` 结果送入生产分类函数并断言 `WorkerLeaseUnavailable`。
- `local_socket::tests::listener_pair_stops_at_the_first_injected_socket_conflict` 在所有平台执行可注入的 bootstrap 冲突分支；Unix 额外由 `two_occupied_socket_paths_reproduce_the_first_bootstrap_conflict` 真实占用两个唯一 socket 并清理自身路径。
- `proxy_server::tests::zero_initial_routes_reproduce_required_upstream_startup_error` 直接调用生产校验函数并断言当前错误。
- `match_client::tests::missing_initial_match_discovery_panics_before_client_initialization` 直接断言当前 panic 边界。

这些测试均不需要外部服务，用于在后续阶段逐步把预期从“当前 fatal”改为“存活并等待收敛”。真实 Redis TTL、Windows named-pipe 多实例语义、SIGTERM/SIGKILL 和 Compose 随机启动顺序的动态演练在后续阶段执行。

## 7. 第 2 阶段动态健康契约

`service-registry::HealthState` 是三个 Rust 服务共享的进程内状态源。依赖记录包含逻辑 dependency/endpoint、`pending | ready | degraded | failed`、当前错误码、最近错误码、重试次数、最近成功时间和最近更新时间。它不存储原始错误文本、URL、host:port、socket 路径、token、密码或连接串。

三个服务通过仅内网监听的 HTTP endpoint 暴露状态：

- `GET /livez`：runtime 尚未进入 shutdown 时返回 HTTP 200，与依赖 readiness 独立。
- `GET /readyz`：全部 required dependency ready 并连续满足稳定窗口后返回 HTTP 200；否则返回 503。optional dependency 不可用时 `state=degraded`，但不会单独阻断 readiness。
- 其他 path 或非 GET method 返回 404。

`/readyz` 的安全 JSON schema 如下，数组元素只使用逻辑名称和稳定枚举：

```json
{
  "service": "game-server",
  "instance_id": "game-server-1",
  "state": "waiting_dependencies",
  "live": true,
  "ready": false,
  "elapsed_ms": 1200,
  "startup_timed_out": false,
  "dependencies": [
    {
      "dependency": "match-service",
      "endpoint": "grpc",
      "requirement": "required",
      "status": "pending",
      "error_code": "DEPENDENCY_PENDING",
      "last_error_code": "DEPENDENCY_PENDING",
      "retry_count": 1,
      "last_success_at_ms": null,
      "updated_at_ms": 0
    }
  ]
}
```

窗口统一由以下环境变量控制。变量未设置时使用默认值；只要显式设置，非数字、零、乘法溢出、超过上限或窗口关系不合理都属于非法配置，三个目标服务必须启动失败，不得静默回退：

| 环境变量 | production 默认值 | 合法范围 | 语义 |
|----------|-------------------|----------|------|
| `MYSERVER_STARTUP_CONVERGENCE_WINDOW_SECS` | `120` | `1..=600` | required dependency 尚未收敛的启动告警窗口 |
| `MYSERVER_READY_STABILITY_WINDOW_SECS` | `10` | `1..=120` | required dependency 恢复后连续稳定多久才重新 Ready |
| `MYSERVER_DEPENDENCY_STALE_WINDOW_SECS` | `60` | `1..=600` | 已成功依赖超过多久未刷新视为 degraded |

窗口关系还必须满足 `ready stability <= startup convergence` 且 `dependency stale > ready stability`。

启动窗口超时只产生一次 `Starting/WaitingDependencies -> Degraded` 转换、一次 `startup_convergence_timeout_total` 计数和一条结构化日志；进程继续存活并保持 not-ready。只有仍为 `DEPENDENCY_PENDING` 的等待会提升为 `DEPENDENCY_TIMEOUT`，`REGISTRY_UNAVAILABLE`、ownership/fatal 和启动阶段错误码不得被覆盖。required 依赖在运行期丢失或过期会立即 degraded/not-ready，恢复后重新经过稳定窗口。registry heartbeat 结果通过不含底层错误文本的 observer 更新 `self-registration`，持续失败会使 readiness 失败，成功后重新进入稳定窗口。`game-server -> match-service.grpc`、`game-proxy -> game-server.proxy-local` 为 required；`match-service -> game-server.internal` 为 optional，required 图无环。

`match-service` 的 optional `game-server.internal` 在建房请求路径更新：registry 不可用、endpoint 缺失、连接或请求失败时 degraded；成功解码的业务成功或业务拒绝都证明传输/协议能力正常并恢复 Ready。它不会阻止 match gRPC readiness，也不会建立反向 required watch。

第 2 阶段保留的首次 discovery fail-fast 边界已在第 3 阶段消除，当前行为见下节。

## 8. 第 3 阶段异步发现与健康发布契约

`packages/service-registry` 提供统一 convergence runner。首次 attempt 立即执行；失败从 250ms 起指数退避，最大 10 秒，默认加入不超过 20% 的 jitter，单次 attempt 默认 5 秒超时；成功后清零失败计数并按服务既有 rediscovery 周期刷新。runner 的 snapshot 只包含阶段、稳定错误码、计数和下次延迟，不保存 URL、host、socket、token 或底层错误文本。

- `game-server` 的 `MatchClientConfig::from_env` 只解析配置，不执行网络 discovery。registry 模式从空 MatchClient 启动统一收敛任务；endpoint 暂缺、Redis 短时不可用或 gRPC 连接失败只维持 `match-service.grpc` pending/degraded 和 not-ready，endpoint 迟到、变化或恢复后原子替换 client。
- `game-proxy` 先绑定 KCP/TCP frontend，再启动同一模型的 `game-server.proxy-local` 收敛任务。成功空快照会冻结已消失 route；registry 错误保留 route 元数据但标记 `Unavailable`。两种情况都禁止选择旧 route，迟到或迁移 endpoint 可在后续成功快照中恢复。
- `match-service -> game-server.internal` 仍是请求级 optional capability。local socket 连接、写入或读取失败会失效 discovery cache，下一请求重新发现；已发送请求不会自动重放，避免重复建房。

三个目标服务统一使用 unhealthy-first registry publication：首次注册时 instance 和全部 endpoint 均为 `healthy=false`。记录与 heartbeat 成功后 `service-registry.self-registration` 才 Ready；只有全部 required dependency 经过稳定窗口后才覆盖发布 `healthy=true`。required dependency 丢失会覆盖回 unhealthy；register/heartbeat 失败会进入同一有界退避并强制重新注册，不依赖进程重启恢复。这个顺序避免 self-registration 门槛形成自循环，也保证启动中的 listener、lease 或 required dependency 未就绪实例不会被 proxy 发现。

第 3 阶段只调整必要的 listener/discovery/publication 顺序。第 4 阶段进一步收敛 `game-server` 资源生命周期，见下节。

## 9. 第 4 阶段启动事务与资源回收契约

`game-server` 当前按 `配置和实例身份 -> CSV/数据库/Redis 外部初始化 -> global-ID worker lease -> TCP/local socket listener -> readiness/registry publication/后台任务 -> active accept loop` 启动。`main` 不再提前启动 readiness、registry publication、CSV reload 或 metrics task；所有长期资源都由 `server::run` 的 `GameServerResources` 记录。

worker lease 等待配置如下，三项均严格校验；非法、越界或 initial 大于 max 属于启动配置错误：

| 变量 | 默认值 | 范围 | 说明 |
|---|---:|---:|---|
| `GLOBAL_ID_WORKER_LEASE_WAIT_TIMEOUT_SECS` | `120` | `1..=600` | 等待前实例释放或 TTL 到期的总窗口，包含单次 Redis attempt |
| `GLOBAL_ID_WORKER_LEASE_RETRY_INITIAL_MS` | `250` | `1..=30000` | 首次重试间隔 |
| `GLOBAL_ID_WORKER_LEASE_RETRY_MAX_MS` | `5000` | `1..=30000` | 指数退避上限 |

等待期间仅记录 `LEASE_UNAVAILABLE`、retry count、elapsed 和 next delay，不记录 Redis URL、lease token 或凭据。Ctrl-C/SIGTERM 可取消等待；超时或取消经过统一 rollback 后返回原始启动错误，不形成快速抢占或无限等待。只有 token compare-and-delete 成功才视为 lease 已释放；token 不匹配会记录 cleanup failure，不删除当前 owner 的 key。

`StartupOwnership` 明确拒绝在未持有 worker lease 时取得 TCP/local socket 所有权。两个 local socket 逐个 bind，每个成功路径都会在下一个 bind 前立即登记到事务 owner；第二个 bind 失败时，第一个 listener 随 bootstrap future 退出而 drop，随后由统一 cleanup 删除已登记路径并报告删除错误。正常、信号、lease lost、关键 listener task 异常和 accept 错误都进入同一清理顺序：停止并等待后台任务，释放 listener/socket，注销自身 registry instance，compare-and-delete 自身 lease，最后关闭全部数据库 pool。每步都执行，前一步失败不会跳过后续项；后台或连接任务已发生的 panic 会聚合为 cleanup failure，主动 abort 的 cancellation 属于预期。若 active/bootstrap 已有原始错误则保留原始错误，cleanup failure 单独结构化记录，只有原运行成功而清理失败时才返回清理错误。

`match-service.grpc` pending 仍是可恢复 not-ready 状态，只启动 convergence task，不触发 rollback。readiness bind、数据库初始化、配置解析和 listener bind 失败属于 bootstrap failure并统一回收已取得资源。

第 4 阶段完成时仍使用配置中的固定两个 socket 名称；该限制已经由第 5 阶段消除，当前契约见下节。

## 10. 第 5 阶段实例 socket 与滚动发布契约

`game-server` 不再读取 `GAME_LOCAL_SOCKET_NAME` / `GAME_INTERNAL_SOCKET_NAME`。两个 socket 由 `GAME_SOCKET_ROOT`、`GAME_SOCKET_BASENAME` 和 `SERVICE_INSTANCE_ID` 确定性派生：Unix 为 `<root>/<basename>-<instance-id>.sock` 和 `<root>/<basename>-<instance-id>-internal.sock`，Windows 为带相同实例成分的 named pipe。production root 默认 `/run/myserver`，local 默认 `/tmp/myserver`。basename、instance id、root、组件长度和最终路径长度均在 bind 前严格校验，拒绝分隔符、控制字符、非 ASCII、`.` / `..` 逃逸和超长值。

stale reclaim 必须同时满足“已经取得当前 worker lease”和“目标恰好属于当前实例派生的两个路径”。Unix 只检查单个路径的 `symlink_metadata`，只允许 socket 文件；普通文件、目录、symlink 和其他实例路径均拒绝删除。探测到活动 listener 时返回冲突；只有明确的 `ConnectionRefused` / `NotFound` 才视为 SIGKILL 后残留，探测超时、权限错误和其他不确定错误一律拒绝回收。整个创建/重试受 `GAME_SOCKET_RECLAIM_TIMEOUT_MS` 限制，spin 和 probe 分别由 `GAME_SOCKET_RECLAIM_SPIN_MS`、`GAME_SOCKET_PROBE_TIMEOUT_MS` 控制，不执行递归删除。Windows named pipe 在最后一个 handle 关闭后自动消失，只执行有界重试。

registry 发布的 `internal` 和 `proxy-local` endpoint 使用本实例实际派生路径。strict/test/staging/production 下，`game-proxy` 只消费 registry 中 `healthy=true`、合法且名称为 `proxy-local` 的 endpoint `socket` 字段；静态 `UPSTREAM_LOCAL_SOCKET_NAME` 只保留在显式 local/development fallback。旧、新实例使用不同 `SERVICE_INSTANCE_ID`、`GLOBAL_ID_WORKER_ID` 和 socket 路径，因此可同时注册和存活，互不回收对方资源。

线上滚动发布顺序固定为：

1. 为新实例分配唯一 instance ID、worker ID、build version 和 rollout epoch，启动后先取得 lease 并只处理自己的 stale socket。
2. 新实例先以 unhealthy 注册精确 endpoint；required readiness 经过稳定窗口后发布 healthy，proxy 才把新路径加入可选 route。
3. 控制面开启旧实例 drain。旧实例把 required `server-listeners` 标记 degraded，使 registry publication 转为 unhealthy，proxy 不再把它用于新的默认路由；玩家 TCP 和 `proxy-local` listener 仅为旧 room 的离线成员保留鉴权和 reconnect transport，`AuthReq` 会拒绝不属于本实例离线 room 的新角色并返回 `SERVER_DRAINING_REJECT_NEW_SESSION`，业务层同时拒绝创建新 room、匹配建房等新分配。已有连接任务、房间和 internal/admin 控制通道继续运行。
4. 普通 drain 只负责摘流，不会自动退出。正式入口是 admin-api 的 `POST /api/v1/rollouts/game-server/:instanceId/drain`，必须显式提供 instance ID，并只允许从 Redis registry 中解析该实例的 `game-server.admin` endpoint；固定内部地址和调用者传入的 endpoint override 都不能进入该路径。该写操作使用 Bearer/JWT 权限校验、`game.config.write` 权限，并由控制面绑定 `worldId=*`、`serviceName=game-server` 和显式 instance，再进入 high-risk preflight/execute 二阶段确认、独立审批、签名断言和脱敏审计。`auth-http` 的历史 `/api/v1/internal/game-server/config` 写接口继续返回 `410 CONTROL_PLANE_ONLY`。
5. 控制面随后调用 admin-api 的 `POST /api/v1/rollouts/game-server/:instanceId/shutdown`，使用 emergency-only 的 `service.shutdown`，按 `serviceName=game-server`、同一 instance ID、registry-only 和 high-risk preflight/execute 边界转发已签名的 `RequestServerShutdownReq`；执行还要求独立审批和匹配目标的有效 break-glass grant。无 blocker 时保持 `ok=true` 并立即触发 graceful shutdown；存在 blocker 时保持原有 `ok=false`、稳定 error code 和计数，同时以 `shutdown_armed=true` 明确表示已接受有界等待。`auth-http` 的历史 `/api/v1/internal/game-server/shutdown-if-drained` 写接口同样保持 `410 CONTROL_PLANE_ONLY`。
6. 显式 arm 后，进程内 watcher 按 `GAME_DRAIN_SHUTDOWN_POLL_MS` 轮询已有连接退出以及 room 迁移或释放，并受 `GAME_DRAIN_SHUTDOWN_TIMEOUT_SECS` 限制。三项归零后触发 graceful shutdown；运行中重复请求不重置 deadline。超时只记录并保持 drained、不强杀活跃 session，超时之后的新显式请求可以重新 arm。
7. shutdown 进入统一 cleanup，依次停止任务、释放 listener 和本实例 socket、deregister、本实例 lease compare-and-delete、关闭 store。SIGKILL 无法执行 cleanup 时，由 heartbeat TTL 摘流；同一实例再次取得 lease 后才可受控回收自己的残留 socket。

production compose 提供 `GAME_SERVER_INSTANCE_ID` 和 `GAME_SERVER_WORKER_ID` 覆盖入口；发布系统必须为并存实例注入不同值。自动创建 old/new 两套实例、批量启动应用、部署平台 preStop/stop hook 和镜像发布编排属于后续部署阶段，不由本阶段应用改造代替。
