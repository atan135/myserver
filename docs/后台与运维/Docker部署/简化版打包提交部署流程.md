# 简化版打包、交付与部署流程

适用于已完成服务器初始化的常规发布。业务代码和 CSV/场景配置修改必须先提交并推送到 Git；WSL 工作区必须位于 Linux 原生文件系统（例如 `~/src/MyServer`），且 Docker Registry 登录状态有效。

下文中的 `<release-id>` 必须使用第一步输出的实际值，并在后续两步保持完全一致。

## 0. 前置检查

开始发布前，必须先确认以下四项：

| 项 | 检查命令（Windows PowerShell） | 期望输出 |
|---|---|---|
| Windows 工作区干净 | `git status` | `nothing to commit, working tree clean` |
| Windows HEAD 与 origin/main 同步 | `git fetch origin main` 然后 `git status -uno` | `Your branch is up to date with 'origin/main'` |
| Rust 格式 | `npm run fmt:rust:check` | `Rust format check passed; skipped generated Rust outputs.` |
| WSL 工作区干净（publish-release.sh 会再做一次） | `wsl -d Ubuntu-24.04 -- bash -lc "cd ~/src/MyServer && git status --porcelain"` | 空输出 |

`fmt:rust:check` 失败时不要自动跑 `npm run fmt:rust`——按 AGENTS.md 先确认变更再决定是否统一格式。

## 1. WSL 构建并推送镜像

打开 WSL Ubuntu-24.04：

```bash
cd ~/src/MyServer

# 脚本内部会：git fetch + pull --ff-only origin main → 校验 → 构建 11 个镜像 → push → 生成 images.lock.json → commit + push release
bash scripts/docker/publish-release.sh
```

该步骤会拉取最新代码、构建并推送镜像，提交镜像 digest 锁定文件。首次构建或依赖缓存失效时耗时会较长。

成功后记录末尾输出的 release ID（**后续两步都要用这个值**）：

```text
release_id=v0.1.0-<short-commit>
revision=<full-sha>
```

## 2. WSL 上传 Release Bundle

WSL 中需要准备权限为 `600` 的 Linux 原生 SSH 私钥，例如 `~/.ssh/myserver_gameops_rsa`。

```bash
cd ~/src/MyServer

bash scripts/docker/upload-release-bundle.sh \
  --release-id 'v0.1.0-<short-commit>' \
  --host '103.47.81.222' \
  --port '28451' \
  --user 'gameops' \
  --identity ~/.ssh/myserver_gameops_rsa \
  --caddy-landing-host 'bevy.zergzerg.cn' \
  --caddy-auth-host 'api.bevy.zergzerg.cn' \
  --caddy-admin-host 'admin.bevy.zergzerg.cn' \
  --caddy-chat-host 'chat.bevy.zergzerg.cn' \
  --caddy-email '<ops-email>' \
  --game-proxy-host 'bevy.zergzerg.cn'
```

`--caddy-landing-host`（主站）、`--caddy-chat-host`（聊天 WSS）、`--caddy-auth-host`（auth HTTP 入口）、`--caddy-admin-host`（admin 后台）、`--game-proxy-host`（玩家 KCP/UDP 入口）必须全部提供，缺一会被脚本拒绝（exit 64）。

成功标志：输出 `uploaded_release=/data/myserver/release/<release-id>`。

## 3. 服务器应用 Release

以部署用户登录服务器后执行。**当前推荐用 gameops 直接跑（不用 sudo）**——`server-apply-release.sh` 自 commit `e30226a` 起已自动 `sudo "$vector_preflight"`，对 gameops 调用者透明：

```bash
ssh -i ~/.ssh/myserver_gameops_rsa -o IdentitiesOnly=yes -p 28451 gameops@103.47.81.222 \
  "/data/myserver/apply-release.sh --release-id 'v0.1.0-<short-commit>' --rollback-db-compatible --actor gameops@\$(hostname -s)"
```

如果已经 ssh 进 gameops 终端（`gameops@<host>:/data/myserver$`），直接跑：

```bash
/data/myserver/apply-release.sh \
  --release-id 'v0.1.0-<short-commit>' \
  --rollback-db-compatible \
  --actor gameops@$(hostname -s)
```

`--rollback-db-compatible` 表示"承诺本次前向 migration 后，旧版本应用仍能正常读写数据库"。前向兼容的具体含义与数据库 migration 边界见[数据库部署准入说明](../../数据库/数据库部署准入说明.md)。未做此承诺时**不得**传该参数；脚本仍会运行，但前一次 release 出错时不会被自动回滚。

成功标志：输出 `current_release=/data/myserver/release/<release-id>`，并列出运行中的 Compose 服务。

部署脚本会自行按 digest 拉取应用镜像，在 migration 前 fail-closed 验证既有 PostgreSQL、Redis、NATS 容器唯一、running/healthy 且运行 digest 与目标 schema v2 lock/Compose 精确一致；常规应用更新和 rollback 不会创建或重建基础设施。随后执行 migration gate、单批启动应用服务并等待 required readiness 连续覆盖 registry TTL 加稳定窗口，再启动 Caddy；不要额外执行 `docker compose down`、`up -d postgres redis nats` 或手工修改服务器 secret。

执行期间不要 Ctrl+C：`apply-release.sh` 用 `flock` 持有 `/data/myserver/run/operations.lock`，强中断会留下 pending journal，导致后续 apply 必须先 `--recover`。

## 4. Windows 工作区收尾

Step 1 的 `publish-release.sh` 会**额外 commit + push 一个 release commit** 到 origin/main（更新 `deploy/docker/images.lock.json`）。Windows 工作区会落后于 origin，按 AGENTS.md 约定必须 fast-forward：

```bash
cd D:\project\myserver
git fetch origin main
git merge --ff-only origin main
```

完成后 `git log --oneline -1` 应显示 `build(release): 锁定 <新 short-commit> 镜像摘要`。**不** fast-forward 会让 Windows 工作区与 origin 长期分叉，下一次发布 `publish-release.sh` 的 `git pull --ff-only` 会失败。

## 5. 验证清单

发布完成后必须确认：

```bash
# 5.1 current 软链是否切到新 release
ssh ... "readlink -f /data/myserver/release/current"
# 期望：/data/myserver/release/v0.1.0-<short-commit>

# 5.2 Vector 服务 active
ssh ... "systemctl is-active vector.service"
# 期望：active

# 5.3 vector preflight 通过
ssh ... "sudo /data/myserver/release/current/scripts/vector-preflight.sh \
  --release-dir /data/myserver/release/current --allow-missing | tail -3"
# 期望最后一行：vector_preflight=passed version=0.47.0 ...

# 5.4 业务服务健康
ssh ... "docker ps --format 'table {{.Names}}\t{{.Status}}'"
# 期望：9 个业务服务 Up，admin-api / auth-http 显示 (healthy)，基础设施不变
```

## 6. 常见失败模式速查

| 错误 | 原因 | 修复 |
|---|---|---|
| `Refusing to publish from a dirty worktree` | WSL 工作区不干净 | WSL 里 `git status` 看是否还有未提交；WSL 端**只能**产生 `images.lock.json` 相关 commit，其他业务改动必须在 Windows 工作区先 commit + push |
| `Updates were rejected because the remote contains work...` | Windows 端有未推送的本地 commit 阻碍 WSL 端 fast-forward | 先在 Windows `git push`，或在 WSL `git pull --ff-only origin main`；**严禁** `git push --force` |
| `denied: unknown manifest class for application/vnd.oci.empty.v1+json` | 用了 `mode=max` 旧逻辑（已修，不应再出现） | 重新 `git pull` 最新 main（当前 commit `2be1093` 后已用 `--provenance=false --sbom=false --push`） |
| `vector_preflight=failed reason=unsafe_or_missing_directory_/var/lib/vector/buffer` | Vector 未首次初始化（`/var/lib/vector` 子目录缺失） | 按 [Vector 首次初始化操作指南](./Vector首次初始化操作指南.md) §3.3 + §4.2 |
| `Error response from daemon: pull access denied ... 'docker login'` | root 无 registry 凭据（用 sudo 跑 apply-release.sh 时） | 改用 gameops 直接跑（不用 sudo）；或临时 `sudo cp /home/gameops/.docker/config.json /root/.docker/config.json` |
| `Error response from daemon: ... database is being accessed by other users` | 上一次 apply 仍在跑或锁未释放 | 等 30 秒后重试；查 `ls /data/myserver/run/` 看是否有残留 journal |
| `directory_mode_/var/lib/vector` (mode 0755 not 0750) | 有人把 `/var/lib/vector` chmod 改成 0755 后被 vector preflight 拒绝 | `sudo chmod 0750 /var/lib/vector /var/lib/vector/buffer /var/lib/vector/checkpoints /var/lib/vector/queue`，再跑 apply |
