# 自动化发布脚本

这三份脚本把正式 release 拆成构建、交付和服务器应用三个明确阶段。它们面向已完成首次初始化的服务器；首次创建 secret 和空数据库初始化仍按[正式 Release 上线说明](./正式Release上线说明.md)执行。

## 1. WSL 发布镜像

在 WSL 原生文件系统中的干净 Git 工作区执行：

```bash
cd ~/src/MyServer
bash scripts/docker/publish-release.sh
```

业务代码和配置表变更应先由开发者正常提交；该脚本不会替你提交业务改动。脚本执行 `fetch + pull --ff-only`，推送当前代码分支，使用 `v<package-version>-<short-commit>` 构建并推送 11 个应用镜像，生成、校验、提交并推送唯一的发布记录 `deploy/docker/images.lock.json`。它拒绝 `/mnt/*` 路径和脏工作区，避免把未提交资产或 Windows 换行符带入 release。

## 2. WSL 交付 Bundle

WSL 必须有 Linux 原生私钥，不能直接使用 `/mnt/c/...` 的 Windows 私钥。一次性准备示例：

```bash
install -d -m 700 ~/.ssh
install -m 600 /mnt/c/Users/<Windows用户名>/.ssh/id_rsa ~/.ssh/id_rsa_gameops
```

以发布脚本输出的 `release_id` 调用：

```bash
bash scripts/docker/upload-release-bundle.sh \
  --release-id v0.1.0-<short-commit> \
  --host 103.47.81.222 \
  --port 28451 \
  --user gameops \
  --identity ~/.ssh/id_rsa_gameops \
  --caddy-auth-host api.game.zergzerg.cn \
  --caddy-admin-host admin.game.zergzerg.cn \
  --caddy-email ztxzerg@163.com \
  --game-proxy-host game.zergzerg.cn
```

脚本从提交了当前 `images.lock.json` 的 Git commit 创建临时 worktree，确保 CSV、场景、迁移、Compose 与镜像 digest 属于同一 release。它会校验 bundle、上传 tar 包，在服务器校验后解压到 `/data/myserver/release/<release-id>/`，并使用 `sudo -n install` 更新 `/data/myserver/apply-release.sh`；不会创建或覆盖服务器 secret。服务器初始化时应已创建 `/data/myserver/release/`，且该目录必须对发布用户可写。

上传使用仅私钥认证、15 秒连接超时和 `StrictHostKeyChecking=accept-new`：第一次连接会记录服务器主机指纹，之后指纹变化会拒绝上传，需要人工核验原因。

## 3. 服务器应用 Release

登录服务器后执行：

```bash
/data/myserver/apply-release.sh \
  --release-id v0.1.0-<short-commit> \
  --actor gameops@$(hostname -s)
```

该脚本会重新校验 bundle、校验 Compose、按 digest pull，先启动并确认 PostgreSQL、Redis、NATS 健康，再执行 migration preflight/apply，随后分阶段更新应用服务、执行 required readiness postflight，最后更新 Caddy 与 `/data/myserver/release/current` 软链。它不会执行 `docker compose down`、不会删除 volume、不会重新生成 `/data/myserver/secrets/` 中的密码。

若 preflight、apply 或 postflight 失败，脚本会非零退出并停止后续阶段；检查对应 release 目录、`docker compose ps` 和容器日志后再决定修复或回滚。
