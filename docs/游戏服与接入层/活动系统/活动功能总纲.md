# 活动功能总纲

## 1. 文档定位

本文是 MyServer 活动功能的总体设计和边界说明，描述活动配置、运行、领奖、发奖、安全、运营后台、扩展接口和演进路径。

本文同时记录目标边界和当前首期实现。`login_reward`、`lottery`、PostgreSQL 事实仓储、Redis 缓存、运营控制面和玩家协议已落地；真实外部依赖、多实例和客户端验收状态以本文第 14 节及专项 checklist 为准。如果代码与本文冲突，以当前代码和配置为准，并在需要时更新本文。

活动系统的首期目标是支持两类活动：

- 登录奖励：支持连续登录、阶段奖励、周期领取和手动/自动领取策略。
- 随机抽奖：以活动界面为入口，支持抽奖消耗、随机奖池、概率校验和即时发奖。

活动系统必须让运营人员通过后台创建、发布和下线活动，而不要求为每一个活动重新发布服务端代码。新增活动类型时，只实现类型专属配置校验、展示、进度和动作判断接口，复用统一的活动生命周期、幂等、限流、事务、发奖和审计能力。

### 1.1 当前仓库相关能力

当前仓库已有一个角色进度奖励入口，但它属于任务/成就等系统内置进度模块，不是本文所定义的运营活动系统：

- `apps/game-server/csv/CharacterProgressTable.csv` 是系统内置进度和奖励配置表，服务于任务、成就等固定业务进度；其中出现的 `activity` `source_type` 只表示奖励来源标签或历史示例，不代表活动运营配置模型。
- `ApplyCharacterProgressReq/Res(1433/1434)` 是角色进度奖励触发入口，调用方提交已配置的 `progress_id`，不能承载本文要求的活动草稿、发布时间、阶段周期、随机奖池或运营发布流程。
- `RewardSource`、`RewardDeliveryService` 和统一资产流水是跨业务的奖励来源与资产交付基础能力；它们可以被活动模块调用，但不等于已经存在活动管理或活动运行时。
- 当前没有完整的活动列表、活动详情、活动调度、登录周期、阶段领取、随机奖池和活动运营后台页面。
- 当前也没有本文建议的独立活动配置版本、活动玩家状态和活动领奖记录模型。

活动系统应在这些通用资产交付能力旁边建立独立的活动领域，不把运营活动压缩成任务模块的单个 `progress_id`。活动产生的奖励可以调用统一资产交付入口；只有在明确的业务事件集成场景下，活动才可以向任务模块发布进度事件，不能反向复用任务表作为活动配置或领奖事实源。

### 1.2 活动与任务/进度模块边界

| 维度 | 任务/进度模块 | 活动模块 |
| --- | --- | --- |
| 业务性质 | 游戏内置的任务、成就和固定进度规则 | 运营可创建、定时发布和下线的限时业务 |
| 配置来源 | 随服务或配置表发布，例如 `CharacterProgressTable.csv` | `admin-api/admin-web` 创建草稿、发布活动版本 |
| 生命周期 | 通常随游戏版本或系统配置生效 | 草稿、发布、进行中、结束、下线、归档 |
| 主要入口 | `ApplyCharacterProgressReq/Res` 等进度触发接口 | `ActivityEngine` 的活动列表、详情、领取、抽奖入口 |
| 进度事实 | 角色任务/成就进度和奖励日志 | 活动版本、阶段/周期状态、领奖记录和抽奖记录 |
| 规则变更 | 开发或配置表变更，受版本发布约束 | 运营后台发布新版本，无需修改活动代码 |
| 奖励关系 | 任务或成就完成后产生奖励 | 活动资格、阶段或随机结果产生奖励 |

两者可以共享 `RewardDeliveryService`、资产流水和通用鉴权能力，但不共享活动配置、阶段状态或领奖唯一键。任务模块的 `progress_id` 不能作为活动 ID，活动 ID 也不能直接写入任务进度表代替活动领奖记录。

### 1.3 阶段 1 冻结的首期业务边界

以下是首期公共活动领域的实现契约。它们是后续数据库、领域对象和协议实现的约束，但本节不表示对应代码已经落地；实现状态仍以代码、迁移和专项验收记录为准。

1. **状态 owner**：首期所有活动使用 `scope=character`，以可信会话中的 `character_id` 作为玩家活动状态、资格和领奖语义键的 owner。账号级活动不是首期的兼容别名；未来引入 `scope=account` 时必须新增账号级状态、并发锁和资产交付边界，不能把同一资格复制到多个角色。
2. **时间语义**：数据库中的活动时间使用 UTC `TIMESTAMPTZ` 保存；活动配置必须携带合法 IANA 时区标识，周期和自然日规则按该时区计算，不使用服务器本地时区。活动有效区间固定为 `[start_at, end_at)`，`now == end_at` 已结束，不能通过边界重试参与。
3. **生命周期迁移**：只允许 `draft -> published -> running -> ended -> archived`，以及 `published -> offline -> archived`、`running -> offline -> archived`。`ended` 和 `offline` 都禁止新参与；`offline` 立即禁止领取，保留查询和审计；不能把已发布版本重新改回草稿或直接清除历史记录。恢复运营必须创建新版本并重新发布。
4. **结束后的领取**：`ended` 只允许领取活动时间窗内已经产生、但尚未领取的资格，不允许产生新进度、消耗或抽奖结果。每个发布版本必须显式保存 UTC `claim_deadline`（可等于 `end_at` 表示无宽限期）；当前首期平台策略允许在 `claim_deadline` 前完成这类领取，超过截止时间统一返回已过期。`offline` 不适用该宽限策略，任何领取均拒绝。
5. **配置与任务隔离**：活动公共配置、活动版本快照、阶段/奖励定义、玩家活动状态、领奖记录和审计记录属于独立活动领域，事实源为 PostgreSQL；Redis 只能缓存、限流和发送刷新通知。`CharacterProgressTable.csv`、`progress_id`、任务/成就进度表及其领奖日志既不是活动配置来源，也不是活动资格或领奖事实。活动发奖只能调用统一资产交付能力，公共活动模块不内置登录奖励或抽奖算法分支。

## 2. 设计原则

### 2.1 服务端权威

- 活动状态、时间、资格、进度、次数、消耗和奖励结果全部由服务端判定。
- 客户端只能提交活动 ID、动作类型、阶段标识和幂等请求号，不能提交玩家 ID、奖励内容、概率结果、进度值或服务器时间。
- 活动配置必须经过服务端类型校验和发布前校验；前端表单校验不能作为安全边界。

### 2.2 先模块化，后服务化

首期活动运行时放在 `game-server` 内部的独立活动领域模块中；`admin-api/admin-web` 作为控制面管理活动配置。活动模块通过稳定的领域接口隔离自身与房间、角色和资产实现，未来可以在不改变玩家动作语义的前提下迁移到独立服务。

活动不放在 `admin-api` 内执行玩家领奖。后台是控制面，游戏服是玩家请求和发奖的权威执行面。

### 2.3 来源与资产交付分离

活动负责说明“为什么产生奖励、玩家是否有资格、奖励是什么”；背包和资产系统负责“如何安全地交付奖励”。活动不得直接修改 `PlayerData.inventory`、货币快照或邮件附件。

活动奖励应生成服务端权威 `RewardOrder`，并调用统一奖励交付入口。奖励交付必须遵循[统一资产事务与奖励交付运行边界](../背包与物品/统一资产事务与奖励交付运行边界.md)：

- 普通活动奖励默认优先进入背包，确定的容量不足可以转奖励邮件。
- 需要和消耗、扣款严格同步的抽奖动作使用 `INVENTORY_REQUIRED` 或等价的原子资产事务策略。
- 发奖使用稳定 `request_id`，失败、超时和重试不能产生第二份奖励。

### 2.4 发布版本不可变

已发布活动配置形成不可变版本。运行中不得静默修改奖励、概率、阶段条件或领取周期。需要修改时创建新草稿和新版本；历史领奖记录必须保留原配置版本，以便重放和审计。

### 2.5 数据库是事实源

PostgreSQL 保存活动配置版本、玩家活动状态、领奖记录、抽奖结果、发奖流水和审计记录。Redis 只用于缓存、限流、短期幂等辅助和配置刷新通知，不作为唯一业务状态来源。

## 3. 服务边界与部署形态

### 3.1 首期推荐拓扑

```text
admin-web
    |
admin-api  -----> PostgreSQL
    |                  |
    |                  +-- 活动草稿、发布版本、运营审计
    |
    +---- 发布通知/缓存失效 ----> Redis

玩家协议 -> game-server ActivityEngine
                              |
                              +-- 活动配置快照
                              +-- 玩家进度与领奖记录
                              +-- RewardDeliveryService
                              +-- inventory / mail
```

`admin-api` 创建和修改草稿，发布时写入不可变版本并发出缓存失效或版本刷新通知。`game-server` 从 PostgreSQL 或 Redis 读取已发布快照；玩家领奖、抽奖和状态变更始终在 `game-server` 的活动入口完成。

### 3.2 为什么首期不拆独立 `activity-service`

独立服务的优点是可单独扩容、独立发版和跨游戏复用，但首期会引入以下成本：

- 活动状态、角色状态、货币扣除和背包发奖跨服务提交。
- RPC 超时后无法直接判断是否已经扣款或发奖。
- 需要 Outbox、幂等发奖、补偿任务、死信和对账能力。
- 需要新的服务注册、部署、监控、权限和容量管理边界。
- 登录、抽奖和领取请求增加跨服务网络延迟。

当前活动奖励与 `game-server` 角色资产事务联系紧密，先在游戏服内模块化更容易保证一致性，也符合当前多服务数量已经较多的现状。

### 3.3 未来拆分条件

满足以下一项或多项时，可以把活动运行时抽为独立服务：

- 多个游戏或多个大区共用同一套活动。
- 活动读写流量需要独立于游戏房间和帧循环扩容。
- 运营要求活动独立发布，不能随游戏服版本发布。
- 背包、货币和订单已经由独立服务拥有，活动天然通过幂等接口发奖。
- 活动配置、规则和报表已经成为独立业务域。

拆分时，`ActivityEngine` 的玩家动作契约、活动版本模型、领奖语义键和 `RewardGrantPort` 应保持稳定；跨服务访问必须按服务注册中心发现 endpoint，不得依赖固定内部端口。

## 4. 活动生命周期

### 4.1 状态

首期状态定义如下（与 1.3 的冻结契约一致）：

| 状态 | 说明 | 玩家行为 |
| --- | --- | --- |
| `draft` | 草稿，配置尚未对玩家生效 | 不可参与；后台可编辑 |
| `published` | 已发布但尚未到开始时间 | 可按配置展示，不能领取 |
| `running` | 当前时间位于活动时间窗内 | 可按类型规则参与和领取 |
| `ended` | 已超过结束时间 | 不接受新参与；只允许领取截止时间前已产生的资格 |
| `offline` | 运营主动下线或紧急关闭 | 不接受新参与和领取；保留查询和审计 |
| `archived` | 历史归档状态 | 只读 |

状态由服务端根据发布版本、服务器时间和运营开关计算。不能由客户端传入。通常只允许以下迁移：

```text
draft -> published -> running -> ended -> archived
                         \-> offline -> archived
```

后台下线不删除活动配置、玩家进度、领奖记录或发奖流水。重新开启应创建新版本或经过明确的恢复策略，不能直接清除历史状态。

### 4.2 时间和时区

- 数据库统一保存 UTC 时间。
- 活动配置明确保存 IANA 时区，例如 `Asia/Shanghai`。
- 展示层将时间转换为运营用户时区或活动时区；规则计算使用活动配置的时区。
- 登录奖励的“天”默认按活动时区的自然日计算，不使用服务器本地时区。
- 开始时间和结束时间采用左闭右开区间 `[start_at, end_at)`，避免边界重复。
- 活动详情可以配置是否在开始前展示，但提前展示不等于可以领取。

### 4.3 发布和版本

发布操作必须执行完整预检：

- 时间、时区和状态合法。
- 活动类型已注册。
- 类型配置符合服务端 schema。
- 阶段编号、周期和领取次数无冲突。
- 奖励道具、货币和消耗项存在且数量合法。
- 随机奖池权重、保底、限量和重复规则可以计算。
- 发布版本具有唯一配置摘要。

发布成功后写入 `activity_version`，再通过 Redis 通知各 `game-server` 刷新缓存。刷新失败不应回滚已经发布的数据库版本；实例必须在读取旧版本和读取新版本之间保持一个明确的版本状态，并上报刷新失败指标。

## 5. 活动领域模型

以下是建议模型，实际表名和字段应在数据库设计阶段与现有 schema、migration 约定合并。

### 5.1 活动主表 `activity`

建议字段：

- `activity_id`：稳定业务 ID。
- `activity_key`：运营可读的唯一键。
- `activity_type`：例如 `login_reward`、`lottery`。
- `scope`：`character` 或 `account`，首期默认使用 `character`。
- `status`：草稿、发布、下线等运营状态。
- `start_at`、`end_at`、`timezone`。
- `claim_deadline`：结束后已产生资格的最晚领取时间（UTC，必须不早于 `end_at`；等于 `end_at` 表示无宽限期）。
- `show_before_start`、`claim_mode`。
- `title_key`、`description_key`、图标和展示资源引用。
- `current_version`、创建人、发布时间和下线原因。

活动奖励默认绑定 `character_id`，因为背包、物品资产和进度数据当前以角色为边界。若未来支持账号级活动，必须在配置中明确 `scope=account`，并为账号级领奖记录、并发锁和奖励交付设计单独边界，不能简单把 `player_id` 混入角色资产表。

### 5.2 不可变版本 `activity_version`

保存发布时的完整快照：

- 公共活动配置。
- `start_at`、`end_at`、活动时区和 `claim_deadline` 的发布时快照。
- 类型配置 JSON。
- 阶段和周期配置。
- 奖励组与奖池版本。
- 规则版本、配置摘要和发布操作信息。

领奖记录必须引用 `activity_version`，不能只引用当前活动 ID。

### 5.3 阶段 `activity_stage`

阶段用于表达“第几天、第几档、第几次里程碑”等领取单元。建议包含：

- `stage_id`、`stage_no`。
- 资格条件或进度门槛。
- 周期策略：一次性、自然日、自然周或活动阶段。
- 奖励组。
- 每个周期领取次数上限。
- 断签、补领、重置和过期策略。

重复周期阶段不能只用 `stage_no` 作为唯一键，必须把周期键纳入领奖语义键。

### 5.4 玩家状态 `player_activity_state`

建议保存：

- `character_id` 或 `player_id`，取决于活动 scope。
- `activity_id`、`activity_version`。
- 当前阶段、连续登录天数、最近事件周期。
- 已完成次数、已消耗次数和类型专属状态 JSON。
- 状态版本、更新时间和最后一次处理请求号。

类型专属状态可以使用 JSONB，但必须由活动类型处理器做 schema 校验；不能让客户端直接覆盖状态 JSON。

### 5.5 领奖记录 `activity_claim_record`

领奖记录是防重、幂等、恢复和审计的核心。建议字段包括：

- `claim_id`。
- `character_id`、`activity_id`、`activity_version`、`activity_type`。
- `action_type`：`claim`、`draw` 等。
- `stage_id`、`period_key`、`draw_request_id`。
- `semantic_claim_key`：服务端生成的唯一语义键。
- `client_request_id`：用于客户端重试的请求号。
- `status`：`processing`、`granted`、`retryable_failure`、`permanent_failure`、`manual_review` 等。
- 奖励快照、消耗快照、规则摘要和错误分类。
- 创建时间、完成时间和最后重试时间。

建议为 `(scope_owner_id, activity_id, activity_version, semantic_claim_key)` 建立唯一约束。客户端请求号不能替代这项约束。

### 5.6 奖励和审计

- 奖励组保存固定奖励或随机奖池定义。
- 奖励项只引用已登记的道具、货币和资产模板，不接收任意客户端 payload。
- `reward_grant_ledger` 记录实际发奖请求、资产交付方式、资产流水 ID、邮件 ID 和结果。
- `activity_audit_log` 记录草稿编辑、发布、下线、奖励配置修改、权限主体和操作原因。
- 资产流水和发奖流水遵循 append-only 原则，纠正使用新 request ID 的补偿操作，不能改写历史证据。

## 6. 统一运行入口

### 6.1 玩家动作

概念上的玩家动作包括：

| 动作 | 用途 |
| --- | --- |
| `list` | 查询当前可展示活动 |
| `detail` | 查询单个活动和本人进度 |
| `claim` | 领取已满足条件的阶段奖励 |
| `draw` | 消耗资格并执行一次随机抽奖 |
| `progress` | 查询活动专属进度，必要时由详情统一返回 |
| `history` | 查询当前角色的历史领取/抽奖事实，使用服务端签发游标分页 |

玩家协议的具体消息号和字段以 `packages/proto` 为准；当前 `history` 已落地为 `ActivityClaimHistoryReq/Res`（`1445/1446`），其余领域语义仍以本总纲为准。

### 6.2 统一处理流程

```text
玩家请求
  -> ticket/session 鉴权
  -> 读取已发布活动版本
  -> 校验活动时间和运营状态
  -> 校验动作类型和请求号
  -> 限流、防重放和玩家状态锁
  -> 调用 ActivityTypeHandler
  -> 返回资格、消耗、奖励和状态变更决定
  -> 写领奖记录和资产交付意图
  -> 执行统一 RewardDeliveryService
  -> 提交资产流水和活动状态
  -> 返回确定结果并发送提交后的 push
```

引擎必须先处理已存在的同一 `client_request_id` 或 `semantic_claim_key`。如果上一次响应丢失，重试应返回原结果，不能再次随机或再次发奖。

### 6.3 类型处理器边界

建议每个活动类型实现以下接口：

```text
validate_config(config, reward_catalog)
build_player_view(activity_snapshot, player_state)
evaluate_action(action, player_context, player_state)
apply_action(decision, transaction_context)
on_player_event(event, player_state)  // 可选
```

处理器不得自行绕过统一入口执行资产修改。`evaluate_action` 应尽可能是可测试的规则判断；随机选择、状态更新和资产交付必须由引擎提供受控的事务和随机源。

## 7. 首期活动类型

### 7.1 登录奖励 `login_reward`

推荐首期定义：玩家完成角色登录或进入游戏服后产生登录事件；同一活动 scope 在活动时区的一个自然日内只产生一次进度。

可配置字段：

- 登录事件来源：`game_entry`，认证成功事件作为后续扩展。
- 周期单位：自然日。
- 连续登录是否断签重置。
- 断签后的下一阶段。
- 是否允许补签。
- 领取方式：自动领取或手动领取。
- 阶段数量和每阶段奖励组。
- 活动结束后已产生资格的领取窗口。

推荐首期默认策略：

- 服务端按活动时区计算日期。
- 同一日期重复登录不重复增加进度。
- 阶段进度由服务端计算，客户端不能提交“第几天”。
- 手动领取使用 `stage_id + period_key` 生成语义领取键。
- 普通奖励使用 `PREFER_INVENTORY`；背包容量不足时按资产边界转奖励邮件。
- 断签重置策略做成配置，但暂不引入复杂补签商城。

必须明确“账号多角色是否共享登录进度”。首期若奖励进入角色背包，推荐使用 `character` scope；账号级共享登录奖励属于独立规则，不能通过重复写入角色状态实现。

### 7.2 随机抽奖 `lottery`

抽奖是一次有明确请求号的活动动作，包含资格检查、消耗、随机选择和发奖。

首期可配置：

- 单抽消耗：免费、道具或货币。
- 每日次数上限和活动总次数上限。
- 奖池版本和奖池项。
- 整数权重。
- 奖励重复策略。
- 是否允许保底；保底可以作为后续扩展字段。
- 奖励交付策略。

概率计算使用整数权重，不使用浮点数。服务端安全随机源在 `[0, total_weight)` 范围内取样，根据累计权重选择结果。抽奖记录保存活动版本、奖池版本、权重摘要、结果奖励、消耗、随机算法版本和请求号。

抽奖与消耗的边界：

- 若消耗必须和即时发奖同事务完成，使用 `INVENTORY_REQUIRED` 或等价原子事务；背包不足时整个抽奖失败，不应先扣消耗再补偿。
- 若产品明确允许奖励进入邮件，可使用 `PREFER_INVENTORY`，但必须通过统一 outbox 和邮件幂等流程，不能由抽奖处理器直接创建邮件。
- 同一请求号重试必须返回同一奖品；新的请求号才代表新的抽奖。

发布前必须校验奖池非空、权重为正、奖励存在、数量合法，并检查保底、限量和重复规则是否互相矛盾。

## 8. 后台控制面

### 8.1 首期功能

`admin-web` 和 `admin-api` 首期至少提供：

- 创建活动草稿。
- 选择活动类型并编辑公共字段。
- 编辑类型专属配置。
- 配置开始时间、结束时间和时区。
- 配置阶段、领取方式、奖励组和奖池。
- 保存、预览和发布前校验。
- 发布活动。
- 下线活动。
- 查询活动状态、版本和更新时间。
- 查询领奖记录、抽奖记录、发奖流水和失败原因。
- 查看活动配置、发布和下线审计。

### 8.2 表单和版本规则

- 公共表单字段由活动平台统一维护。
- 类型专属表单由类型 schema 描述，前端只负责提升填写体验。
- `admin-api` 先做格式和权限检查，发布前由活动运行时再次做权威校验。
- 已发布版本默认不可编辑；编辑动作创建新草稿。
- 已产生玩家进度的版本不得更换奖励语义、阶段编号或周期规则。
- 删除动作使用下线或归档，不做物理删除。
- 生产环境的发布、下线和高风险奖励调整应接入现有管理员权限和审计体系；是否增加双人审批作为第二阶段能力。

## 9. 一致性、并发和恢复

### 9.1 事务边界

同一 PostgreSQL 事务内应尽量完成：

1. 锁定或校验玩家活动状态。
2. 校验资格、周期和次数。
3. 插入或读取幂等领奖记录。
4. 扣除抽奖消耗。
5. 写入标准化 `RewardOrder` 和发奖流水。
6. 更新玩家活动状态。
7. 提交资产事务。

如果资产交付跨服务，活动记录必须先保存发奖意图和 outbox；消费者使用稳定 `grant_id/request_id` 幂等处理，并回写明确状态。超时结果必须查询原请求，禁止直接新建一份奖励。

### 9.2 并发控制

- 数据库唯一约束是防重复的最终保障。
- 玩家活动状态使用行锁或版本号进行并发更新。
- Redis 分布式锁只能用于削峰和减少冲突，不能代替数据库约束。
- 同一玩家的同一活动动作应具备有限串行化能力；不同玩家之间保持可水平扩展。
- 配置缓存刷新失败必须可观测，不能让实例使用部分字段的新配置。

### 9.3 状态和恢复

建议领奖记录支持：

```text
processing
granted
retryable_failure
blocked_capacity
reconciliation_pending
permanent_failure
manual_review
```

恢复 worker 只使用原活动版本、原领奖键、原奖励快照和原 request ID。禁止在不确认原请求结果时重新抽奖、重新扣款或创建第二份邮件。

## 10. 安全与反刷

### 10.1 请求安全

- 通过现有 game ticket/session 鉴权，玩家身份来自服务端连接上下文。
- 检查 ticket 版本、角色绑定和账号状态。
- 客户端请求号绑定玩家和活动，防止跨玩家复用。
- 对领奖、抽奖、活动详情和列表分别配置限流。
- 按角色、账号、IP、设备、活动和动作类型记录频率指标。
- 对明显重放、频率异常、失败率异常和大量高价值中奖行为进行标记。

### 10.2 规则和奖励安全

- 所有奖励引用服务端资产目录。
- 客户端不能指定奖励 ID、数量、概率、阶段进度或消耗结果。
- 服务端使用服务器时间和活动时区。
- 随机结果只由服务端安全随机源产生。
- 运营配置不执行任意脚本。
- 领奖结果、发奖流水和配置版本可按 request ID 追溯。
- 异常账号处置和补偿使用独立后台权限和审计，不提供“修改历史领奖记录”的入口。

## 11. 缓存、事件和可观测性

### 11.1 Redis 使用边界

Redis 可以缓存：

- 当前已发布活动列表和版本快照。
- 活动配置刷新通知。
- 细粒度限流计数。
- 短期请求去重辅助信息。

Redis 不能作为以下数据的唯一来源：

- 玩家连续登录进度。
- 领奖成功事实。
- 抽奖结果。
- 奖励交付结果。
- 运营审计。

### 11.2 事件来源

登录奖励可以通过 `game_entry` 事件触发。后续任务、充值、消费、在线时长和排行榜活动需要统一的领域事件适配器，例如：

```text
PlayerLogin
PlayerLevelChanged
RechargeSucceeded
ItemConsumed
OnlineDurationReached
RankingSettled
```

首期不建议为每一种活动提前建设完整事件总线；但类型处理器应预留 `on_player_event` 边界，未来可接入现有 NATS 或可靠 outbox。事件处理必须使用事件 ID 幂等，不能因重复消费重复增加进度。

### 11.3 指标和审计

当前 `game-server` 已观测：

- 固定 `list/detail/progress/claim/draw/game_entry/unknown` 动作集合的请求、成功、资格不足、重复和限流窗口计数。
- 统一奖励交付平均延迟和交付次数。
- 奖励邮件 outbox 中可自动恢复记录的 backlog gauge。
- 活动缓存读取、写入和刷新失败分类，以及兼容的缓存失败总计数。
- 既有资产版本冲突、容量 fallback、奖励邮件投递/重试/人工复核指标。

活动指标使用编译期固定字段，不把角色/账号 ID、原始活动 ID、request ID、claim ID、token 或版本拼入字段名或标签。详细主体信息只写入受权限保护的审计或流水表。指标由 `game-server` 每个实例按 5 秒窗口通过 Core NATS 上报；窗口计数不能当作进程生命周期累计值，backlog 是实例查询到的当前 gauge。

## 12. 扩展新活动类型

新增活动类型应按以下边界接入：

1. 定义类型标识和版本化配置 schema。
2. 实现配置校验。
3. 实现活动详情和玩家进度展示。
4. 实现资格判断和动作决定。
5. 实现必要的玩家事件处理。
6. 声明消耗、奖励组和交付策略。
7. 编写规则、并发、幂等和异常恢复测试。
8. 将类型 schema 接入后台表单和发布预检。

类型处理器不应修改统一入口、资产事务或运营审计的公共逻辑。若新类型需要全新的资产、计费或结算能力，应先扩展公共领域接口，再实现类型规则。

可扩展类型示例：

- 运营配置的累计目标活动（不等同于任务模块的系统内置任务）。
- 累计充值和累计消费。
- 等级或战力达成。
- 在线时长。
- 排行榜结算。
- 兑换码或外部资格兑换。
- 世界事件和跨服进度。

## 13. 分阶段路线

### 阶段一：首期最小闭环

- `game-server` 活动领域模块和统一入口。
- `admin-api/admin-web` 草稿、发布、下线。
- 登录奖励和随机抽奖。
- 活动列表、详情、领奖和抽奖动作。
- 活动配置版本、玩家状态、领奖记录和发奖流水。
- PostgreSQL 事实存储，Redis 缓存和限流。
- 统一资产交付、请求幂等、并发控制和基础审计。

### 阶段二：运营增强

- 活动复制、模板和预览。
- 多语言展示和资源管理。
- 补签、保底、重复奖励和限量库存。
- 玩家分群、灰度、白名单和资格快照。
- 失败重试、补发、人工复核和对账页面。
- 双人审批、配置差异比较和发布回滚策略。

### 阶段三：平台化和服务化

- 事件驱动的任务、充值、消费、在线时长和排行活动。
- 跨游戏、跨大区活动配置。
- 活动独立扩容和独立发布。
- 在满足服务拆分条件后，将运行时迁移为独立 `activity-service`。

## 14. 验收标准

当前离线测试已覆盖协议路由、配置摘要/schema、登录与抽奖规则、并发幂等、限流、PostgreSQL store 契约、Redis 失败回退、奖励 unknown 恢复、邮件 fallback 和人工复核。以下真实环境项目仍是首期最终验收门禁：空数据库完整迁移；真实 PostgreSQL、Redis、NATS 和 service registry 联调；Redis 中断演练；至少两个 `game-server` 实例的配置刷新和领奖一致性；外部客户端端到端流程。执行这些项目会创建临时活动、玩家状态、领奖/抽奖、奖励流水和审计数据，必须预先指定测试环境、数据前缀和清理方案。

### 14.1 功能验收

- 运营人员无需修改代码即可创建、发布和下线登录奖励与随机抽奖活动。
- 活动可以配置开始时间、结束时间、时区、阶段、领取方式和奖励。
- 活动开始前、进行中、结束后和下线后的展示及动作行为符合定义。
- 登录奖励按服务器时间和活动时区正确计算周期。
- 每个阶段和周期只能领取一次。
- 抽奖使用服务端奖池和随机结果，客户端不能指定奖品。

### 14.2 一致性验收

- 同一请求重试返回原确定结果。
- 并发领取不会重复发奖。
- 并发抽奖不会突破次数或消耗限制。
- 资产交付失败、超时或进程中断后可以恢复或进入明确人工处理状态。
- 领奖记录、发奖流水和资产流水可以使用 request ID 对账。

### 14.3 安全验收

- 伪造玩家 ID、阶段、奖励、时间和概率不会生效。
- 重放请求、快速刷请求和跨角色复用请求号会被拒绝或幂等返回。
- 运营发布、下线和奖励调整均可审计。
- 限流、异常中奖和发奖失败有低基数指标及可查询明细。

### 14.4 扩展验收

- 新增一种活动类型只需实现有限的类型处理器和后台 schema。
- 新类型可以复用统一的活动状态、幂等、事务、发奖和审计流程。
- 多个 `game-server` 实例使用共享数据库和缓存时，结果一致且不依赖本地内存。

## 15. 当前策略与后续开关

首期代码已经冻结以下策略：

- 登录进度由服务端可信 `game_entry` 事件推进，周期按活动 IANA 时区计算。
- 登录奖励使用 `PREFER_INVENTORY`，明确的背包容量不足进入确定性奖励邮件 fallback。
- 抽奖奖励使用 `INVENTORY_REQUIRED`；道具券消耗和奖励在统一资产批次中原子处理，容量不足不改走邮件，也不保留已扣消耗。
- 玩家只提交动作和幂等 request ID，不能选择奖励、概率、进度或交付策略。

同类型活动并行时的跨活动互斥，以及生产发布、下线和紧急奖励调整的双人审批仍属于后续平台治理。新增开关必须写入版本化类型配置或平台策略，不能在客户端或不同实例中隐式决定。
