# 聊天系统 + 邮件系统 统一架构设计

## 1. 核心定位

聊天系统和邮件系统有高度相似的架构模式：

| 特性 | 聊天 | 邮件 |
|------|------|------|
| 发送者 → 接收者 | ✅ | ✅ |
| 离线存储 | ✅ (离线消息) | ✅ (未读邮件) |
| 持久化存储 | ✅ | ✅ |
| 群组模式 | ✅ (群聊) | ❌ |
| 实时性 | ✅ | 部分支持：新邮件通过 Core NATS 通知在线玩家 |
| 频率/连接限制 | 已有单连接入站限流、单 IP / 单账号本实例连接数限制，默认关闭 | ❌ |

**结论**：两者可以共用一套消息存储层，但在业务逻辑上保持独立。

当前仓库实现状态说明：

物品奖励邮件、附件领取、冻结重试和服务发现的当前运行边界见[统一资产事务与奖励交付运行边界](../游戏服与接入层/统一资产事务与奖励交付运行边界.md)。

- `chat-server` 已作为独立 Rust TCP 服务落地
- 公网聊天 WSS 的服务端 adapter、生产 listener、内部 registry endpoint、Caddy 静态入口和按部署配置的 auth descriptor 均已落地；真实发布状态与正式客户端迁移仍须分别按部署和客户端清单验收，不能仅凭代码描述为已经上线
- `chat-server` 认证阶段已复用 game ticket，并检查签名、过期时间、Redis `ticket:<sha256(ticket)>` 归属和 `player-ticket-version:<playerId>`；Redis key 均受 `REDIS_KEY_PREFIX` 影响
- `chat-server` 的生产 `TICKET_SECRET` 必须与 `auth-http` / `game-server` 的 ticket 签发和校验侧保持一致，且不能使用默认值或 `.env.example` 占位值
- `chat-server` 已支持认证后的单连接入站消息频率限制，`CHAT_MSG_RATE_MAX=0` 默认关闭；启用后在业务 handler 前返回 `ErrorRes(MSG_RATE_EXCEEDED)`，不断开连接
- `chat-server` 已支持 ticket 校验通过后的单账号 / 单 IP 本实例连接数限制，`CHAT_MAX_CONNECTIONS_PER_PLAYER=0` 与 `CHAT_MAX_CONNECTIONS_PER_IP=0` 默认关闭；超限时在注册 session 和 online route 前返回失败 `ChatAuthRes` 并关闭新连接
- 私聊和群聊在 PostgreSQL 保存成功后按 Redis `chat:online:{playerId}` 路由：本实例目标直接写当前 session 队列，远端目标发布到实例级 Core NATS subject `myserver.chat.push.instance.<instance_id_token>`；NATS、路由和 session 队列失败只跳过在线提示，不回滚已保存消息或改写成功响应
- `chat-server` 可在统一 service registry 中注册 schema v2 的 `chat-server.tcp` 和启用时的 `chat-server.ws` endpoint，二者均为 `visibility=internal`；metadata 包含 transport capability、协议版本、frame/body 上限、`build_version` 等，严格环境下 `DISCOVERY_REQUIRED=true` 要求 `REGISTRY_ENABLED=true`
- `chat:online:{playerId}` 与配对的 `chat:online-owner:{playerId}` 是玩家在线实例路由和连接 owner token，均受 `REDIS_KEY_PREFIX` 影响，TTL 默认来自 `CHAT_ONLINE_ROUTE_TTL_SECS=60`；连接存活期间只允许 owner-fenced 续期，旧连接不能覆盖新实例 route。它们不并入 service registry，也不由 registry heartbeat 替代
- `chat-server` 当前不消费 service registry。它自身可以注册 TCP endpoint；私聊、群聊和邮件在线通知都使用 Redis route + owner token + Core NATS + 当前实例内存 session map。目标实例在入队前重新读取 route，要求 instance、owner token 和本地 session token 同时匹配，迁移/摘流中的旧 route 一律跳过
- Caddy 对 WebSocket 新连接的负载均衡只决定连接落点，不提供跨实例消息扇出；生产扩容必须依赖上述 NATS 数据面，不能仅凭 Caddy upstream 数量判定多实例聊天已完成
- `mail-service` 已作为独立 Node.js HTTP 服务落地，并已实现附件领取；玩家邮件 HTTPS 的 Caddy 白名单入口和按部署配置下发的 `services.mail` descriptor 已落地
- `mail-service` 玩家读邮件、邮件详情、标记已读和领取附件已复用 game ticket 做第一阶段 HTTP 鉴权，并检查 ticket 签名、过期时间、Redis `ticket:<sha256(ticket)>` 归属和 `player-ticket-version:<playerId>`；Redis key 均受 `REDIS_KEY_PREFIX` 影响
- `mail-service` 系统发信入口 `POST /api/v1/mails` 已通过 `MAIL_SERVICE_TOKEN` 做内部 service token 鉴权
- `mail-service` 可在统一 service registry 中注册 schema v2 的 `mail-service.http` endpoint，`visibility=internal`；endpoint metadata 包含服务身份、`build_version`、`zone`，实例 metadata 还包含 `player_auth_required`、`service_token_enabled` 等当前实现信息
- `mail-service` 发送在线通知时先读取 Redis `chat:online:{playerId}`，命中后发布到实例级 NATS subject `myserver.mail.notify.instance.<instance_id_token>`；缺路由或查询失败时回退到 legacy `myserver.mail.notify.<player_id_token>`。service registry 不替代 NATS，也不替代 chat 在线路由
- `mail-service` 领取附件调用 `game-server.admin` 时通过 registry 发现 endpoint；`GAME_SERVER_ADMIN_HOST` / `GAME_SERVER_ADMIN_PORT` 只允许 development/local 且 discovery 非 required、registry disabled 的本地 fallback。此时固定 endpoint 只是传输地址，仍必须读取 Redis v2 在线权威路由并携带 generation/token，不能把合成标签 `local-fallback` 当作 game-server 实例身份。strict/test/prod 中 registry disabled、发现不到 endpoint 或旧直连变量存在都会明确失败，不静默直连
- 多 `game-server` 实例时，`grantMailAttachments()` 使用 game-server 维护的 Redis 在线权威路由选择实例并与 registry endpoint 交叉验证；玩家不能指定目标。`targetInstanceId` 只保留为 development/local 且 discovery 非 required 的受限调试能力；registry disabled 的单机 fallback 下只接受当前 route 的真实 `instance_id`，不接受 `local-fallback` 伪身份
- `announce-service` 已作为独立 Node.js HTTP 服务落地，支持公告 CRUD、有效公告查询、Redis 注册与 NATS metrics 上报
- `metrics:heartbeat:*` 或 NATS metrics 只是指标 / 事件新鲜度通道，不是 registry heartbeat，不能替代 service discovery
- “聊天与邮件共用同一套存储层”目前仍未实现
- 离线聊天当前更接近“历史可查询”，未实现“登录后自动补发离线消息”的完整闭环

## 2. 当前消息系统架构

当前仓库没有把聊天、邮件、公告统一挂到 `game-proxy` 后面，也没有实现共用 `message-store`。实际链路是：

```
Client
  -> auth-http 登录/签票，获取 game-proxy 入口和按部署配置下发的公网 services.chat / services.mail
  -> 本地显式 chat-server:9001/TCP + Protobuf（development/local）
  -> 生产 wss://chat.game.zergzerg.cn/ -> Caddy:443 -> chat-server WebSocket listener
  -> 本地显式 mail-service:9003 HTTP（development/local 内部联调）
  -> 生产 https://api.game.zergzerg.cn/api/v1/mails/... -> Caddy:443 -> mail-service HTTPS player route
  -> announce-service HTTP 公告接口（可选内部 endpoint，不是生产默认直连入口）

mail-service
  -> Redis: chat:online:{playerId}
  -> Core NATS: myserver.mail.notify.<player_id_token>
  -> Core NATS: myserver.mail.notify.instance.<instance_id_token>
  -> chat-server mail_subscriber
  -> 在线聊天 TCP 或 WSS 连接推送 MailNotifyPush

chat-server
  -> Redis: chat:online:{playerId} + chat:online-owner:{playerId}
  -> Core NATS: myserver.chat.push.instance.<instance_id_token>
  -> 目标 chat-server 当前有效 TCP 或 WSS session

mail-service
  -> service registry: discover game-server.admin
  -> game-server admin (GrantItemsReq / GrantItemsRes)
  -> player inventory updated

chat-server -> PostgreSQL chat_messages / chat_groups / chat_group_members
mail-service -> PostgreSQL mails 或内存存储
announce-service -> PostgreSQL announcements 或内存存储
```

`game-proxy` 当前只承担游戏流量接入，不负责聊天、邮件或公告 HTTP/TCP 转发。`auth-http` 可选暴露 `chat-server.tcp` / `mail-service.http` / `announce-service.http` 内部 endpoint 时，必须在允许的非生产场景并且通过 registry 发现；生产环境和正式客户端不得返回这些内网 endpoint。正式 `services.chat` 是由部署配置提供的公网 WSS descriptor，不从 `chat-server.tcp` 或后续 `chat-server.ws` registry endpoint 推导。

## 3. 聊天系统设计

### 3.1 支持范围

- **单聊**：用户A ↔ 用户B
- **群聊**：用户群组内共享消息
- **聊天与房间解耦**：聊天不依赖游戏房间
- **历史查询**：支持私聊 / 群聊历史消息分页查询
- **邮件通知**：订阅 `myserver.mail.notify.*` 并向在线聊天连接推送 `MailNotifyPush`
- **跨实例在线 push**：私聊、群聊和邮件通知都只投递到当前 Redis route owner；Core NATS 仅承担尽力在线提示，历史/邮件列表仍是离线权威数据
- **认证边界**：首包必须是 `ChatAuthReq`，ticket 被单张 revoke 或 owner 不匹配时拒绝认证
- **服务发现边界**：自身可注册 `chat-server.tcp` 内部 endpoint，但当前不通过 service registry 发现其他服务；玩家在线路由继续写 Redis `chat:online:{playerId}`

### 3.2 群组管理

群组是独立的，需要：

```rust
pub struct ChatGroup {
    pub group_id: String,
    pub name: String,
    pub owner_id: String,
    pub members: Vec<String>,       // 成员列表
    pub created_at: i64,
}
```

群聊操作：
- `CREATE_GROUP` - 创建群组
- `JOIN_GROUP` - 加入群组
- `LEAVE_GROUP` - 离开群组
- `DISMISS_GROUP` - 解散群组（仅群主）

### 3.3 聊天协议

#### 3.3.1 TCP 与 WSS 并行期拓扑和责任边界

公网 WSS 是现有聊天协议的传输适配层，不是第二套聊天协议或业务实现。并行期固定拓扑如下：

```text
development/local
  mock-client / client
    -> 127.0.0.1:9001/TCP
    -> chat-server 共用鉴权、会话、限流和聊天业务处理器

production target
  mybevy
    -> auth-http 登录或签票响应中的 services.chat
    -> wss://chat.game.zergzerg.cn/（默认 443/TCP）
    -> Caddy（TLS 终止和 WebSocket reverse proxy）
    -> chat-server:9011/WS（Docker internal network）
    -> 同一个共用鉴权、会话、限流和聊天业务处理器
```

端口和暴露边界：

| 地址/端口 | 用途 | 暴露策略 |
| --- | --- | --- |
| `127.0.0.1:9001` 或内部 `chat-server:9001` | 现有原始 TCP listener | 保留用于 development/local 显式联调和内网诊断；不作为正式客户端地址 |
| `chat-server:9011` | 默认 WebSocket listener | 仅在配置启用后监听 Docker internal network；不做宿主机端口映射，不直接暴露公网 |
| `wss://chat.game.zergzerg.cn/` | 正式客户端稳定聊天入口 | 公网只暴露 Caddy `443/TCP`，由 Caddy 终止 TLS 并转发 WebSocket |

`CHAT_WS_ENABLED` 的本地默认值必须保持关闭，生产部署才显式开启；启用 WSS 不替换或删除 `CHAT_BIND_ADDR` 对应的 TCP listener。`chat-server.tcp` 和启用 WSS 时注册的 `chat-server.ws` 都是 `visibility=internal` 的 registry endpoint，只供内部发现和运维，不是公网 descriptor。

各层责任固定如下：

- Caddy 只处理 TLS、HTTP Upgrade、必要代理头和连接转发，不解析 `14` 字节包头或 Protobuf，不执行 ticket 鉴权，也不承载聊天业务。
- WebSocket adapter 只校验 frame 类型、大小和完整包边界，在 binary frame 与现有完整协议包之间做一一映射。
- TCP 与 WSS 必须进入同一个鉴权、会话、限流、在线路由、聊天、历史和邮件通知处理器；不得复制业务 handler。
- `game-server` 不转发聊天流量，`game-proxy` 也不新增聊天转发职责。

#### 3.3.2 包结构和 WebSocket frame 边界

TCP 与 WSS 复用同一个现有包结构，所有多字节整数继续使用网络字节序：

```text
| magic(2) | version(1) | flags(1) | messageType(2) | sequence(4) | bodyLength(4) | Protobuf body(N) |
```

- 固定包头长度为 `14` 字节。
- `magic=0xCAFE`、`version=1`、`flags=0`。
- `messageType` 是现有聊天消息号，`sequence` 用于关联请求与响应，`bodyLength` 是 Protobuf body 的字节数。
- 每个 WebSocket binary frame 必须恰好包含一个完整包，即 frame 长度必须等于 `14 + bodyLength`。
- `bodyLength=0` 本身是合法的空 Protobuf body，例如已定义的空请求仍发送完整 `14` 字节包头；它不同于长度为 `0` 的空 binary frame。
- 不允许一个包跨多个 binary frame，不允许一个 binary frame 拼接多个包，也不允许只发送裸 Protobuf body。
- 服务端产生的每个完整响应或异步 push 包也必须各自编码为一个 binary frame；不能把多个出站包合并到同一 frame。
- frame 上限必须为有界配置，且至少同时受 `14 + maxBodyLength` 和 WebSocket library frame/message 上限约束；检查上限后才能按声明长度分配 body 缓冲。

WSS 只增加 transport framing，不改变 `packages/proto/chat.proto`。现有 magic、version、flags、message type、sequence、body length 的语义保持不变，所有 Protobuf 字段编号保持不变；若未来修改字段，仍必须遵守协议兼容流程，不能借 WSS 接入重新编号。

#### 3.3.3 WebSocket 错误和控制帧契约

畸形 transport frame 不进入 Protobuf 解码或业务处理器。能够安全解析出包头和 `sequence` 的应用层错误才使用现有 `ErrorRes(9000)`；无法信任包边界时只发送 WebSocket Close。Close reason 必须是有界、无敏感数据的稳定分类，不回显原始 frame、ticket 或聊天正文。

| 输入/事件 | 处理结果 |
| --- | --- |
| 文本帧 | 不进入业务处理器；发送 Close `1003`（unsupported data），结束该连接 |
| 空 binary frame 或少于 `14` 字节的 binary frame | 发送 Close `1002`（protocol error），结束该连接 |
| 错误 magic、非 `1` 的 version 或非 `0` 的 flags | 不尝试 Protobuf 解码；发送 Close `1002`，结束该连接 |
| frame 实际 body 长度与包头声明 `bodyLength` 不一致，包括截断包和多包拼接 | 发送 Close `1002`，结束该连接 |
| frame、message 或声明 body 超过配置上限 | 在进入业务处理前发送 Close `1009`（message too big），结束该连接 |
| 已认证连接发送语法有效但未知的 `messageType` | 返回单个完整 `ErrorRes(error_code=UNKNOWN_MESSAGE_TYPE)` binary frame，沿用请求 `sequence`，当前连接保持；仍受消息限流约束 |
| 首包使用未知消息号或不是 `ChatAuthReq` | 可在包边界可信时返回 `ErrorRes`，随后发送 Close `1008`（policy violation）；不得进入已认证业务状态 |
| Ping | 作为 WebSocket 控制帧处理，回复相同 payload 的 Pong；不得交给聊天协议处理器 |
| Pong | 仅用于连接活性观测，不产生聊天协议响应，不进入业务处理器 |
| 合法 Close | 回复 Close handshake 后结束读写任务，执行与 TCP 断连相同的 session 和在线路由清理；不得额外发送应用包 |
| 非法控制帧或底层 WebSocket 协议错误 | 由成熟 WebSocket library 按 RFC 6455 拒绝，通常使用 Close `1002`，只终止对应连接 |

TCP 是字节流，仍按 `14` 字节包头和声明 body 长度读取；WSS 是消息边界传输，禁止把 TCP 的半包累积或多包拆分逻辑搬到 WebSocket adapter。两种 transport 在得到一个完整包之后的应用层错误响应必须保持一致。

#### 3.3.4 地址下发、鉴权和敏感信息边界

正式客户端必须从 `auth-http` 的登录或签票响应读取公网 `services.chat`，目标 descriptor 为：

```json
{
  "host": "chat.game.zergzerg.cn",
  "port": 443,
  "protocol": "wss"
}
```

固定 WebSocket path 为 `/`。该 descriptor 来自部署配置；未配置时 `services.chat` 保持 `null`，不能回退为 registry 中的 Docker host、`9001/TCP` 或 `9011/WS`。development/local 可以忽略 descriptor 并显式使用 `127.0.0.1:9001/TCP`，以保证现有脚本和 mock-client 默认流程不迁移。

ticket 仍只放在第一个完整 binary frame 的 `ChatAuthReq.token` 中，不放在 WebSocket URL、query string、subprotocol、cookie 或自定义握手日志字段中。Caddy access log、服务日志和指标标签不得记录 ticket、token、聊天正文或完整 frame；日志只允许记录受限 peer、transport、消息类型和错误分类。

Caddy 对聊天域名只代理 `GET /` 的合法 WebSocket Upgrade，其它 HTTP 方法、普通 HTTP 或错误路径返回 `426`。边缘覆盖外部 `X-Request-ID`，客户端地址使用 Caddy 直连 peer 生成的代理头；访问日志删除完整 URI 和可能携带凭证的握手字段。HTTP 握手和 header 上限由 Caddy 约束，升级后的空闲连接由 `chat-server` 的 `HEARTBEAT_TIMEOUT_SECS` 约束。

当部署拓扑提供多个 `chat-server` DNS A 记录时，Caddy 使用 `dynamic a chat-server 9011` 和 `round_robin` 仅为**新的** WebSocket Upgrade 选择上游；一条已升级的 WebSocket 在其整个生命周期固定连接到这次选择的实例。该策略不使用跨请求 cookie，也不承诺重连回到原实例。它只解决新连接接入均衡，不能替代 Redis owner-fenced online route 和实例级 Core NATS push：私聊、群聊和邮件通知仍必须按 `chat:online:{playerId}` 的当前 owner 投递，历史和邮件列表仍是离线权威数据。

客户端必须把 Caddy reload、容器替换、证书维护和上游替换视为可恢复断线，使用带随机抖动的指数退避重新建立 WSS；ticket 已失效时重新向 `auth-http` 签票。聊天重连不能触发游戏 KCP 重连，也不能把 `game-proxy` 作为聊天 fallback。

#### 3.3.5 单实例容量门槛与告警

当前生产 Compose 的 `chat-server` 是受门禁保护的单副本部署，内存上限为 `256MiB`。以下参数是该单实例上线门槛，不是建议值；变更任一参数前必须按新的容量预算完成压测并更新告警：

| 范围 | 生产配置 | 行为与预算 |
| --- | --- | --- |
| 总连接 | `CHAT_MAX_CONNECTIONS=500` | TCP 与尚在 Upgrade 的 WSS 均占一个实例级 permit，达到上限立即关闭新 socket；`connection_capacity_current` 是容量 gauge。 |
| WSS 握手 | `CHAT_WS_HANDSHAKE_RATE_MAX=120` / `CHAT_WS_HANDSHAKE_RATE_WINDOW_SECS=1`，`CHAT_WS_MAX_PENDING_HANDSHAKES=64`，`5s` timeout | 每实例最多接纳 `120` 次 Upgrade/s，且最多 `64` 个未完成握手；超过速率或并发门槛在 Upgrade 前拒绝。 |
| 入站消息 | `CHAT_MSG_RATE_MAX=20` / `CHAT_MSG_RATE_WINDOW_MS=1000` | 每个已认证连接最多 `20` 条业务消息/s，超过返回稳定 `MSG_RATE_EXCEEDED` 错误；只有错误无法入队或出站队列已满时才关闭对应会话。 |
| 会话与慢客户端 | 每玩家 `2`、每 IP `50`、`CHAT_OUTBOUND_QUEUE_CAPACITY=32` | 单条完整包最大 `4110` bytes；单连接出站最坏约 `32 * 4110` bytes，队列满时以 `OUTBOUND_QUEUE_FULL` 关闭慢客户端，不能无限积压。 |
| WSS 桥接与跨实例队列 | `CHAT_WS_BRIDGE_CAPACITY=8192` bytes，`CHAT_PUSH_PUBLISH_QUEUE_CAPACITY=128`，`CHAT_PUSH_MAX_PAYLOAD_BYTES=8192` | WebSocket duplex bridge 和 Core NATS publish queue 均有固定上限；在线提示丢失不回滚已持久化聊天或邮件。 |
| 内存 | Compose `mem_limit=256m` | `500 * 32 * 4110` 的理论聊天出站包上界约为 `63MiB`，其余预算留给 socket、任务、WebSocket 缓冲、存储 client 和运行时；RSS 不得以取消队列/连接上限的方式处理。 |

监控按 5 秒 bucket 读取无身份 metrics hash，连接 gauge 不做 bucket 累加：

- `connection_capacity_current >= 450` 连续 1 分钟告警并停止扩大接入；`connection_capacity_rejected_total > 0` 立即告警并先摘除接新流量。
- `websocket_handshake_success_total + websocket_handshake_failure_total >= 480` / 5 秒连续 1 分钟告警；`websocket_handshake_rate_limited_total > 0` 立即告警，检查重连风暴和边缘流量。
- `tcp_outbound_queue_failure_total + websocket_outbound_queue_failure_total > 10` / 5 分钟告警；优先处理慢客户端或缩减接入，不能提高 queue 容量绕过 `256MiB` 预算。
- Docker RSS `>= 205MiB` 持续 5 分钟告警，`>= 230MiB`、OOM 或重启立即升级；先停止接新连接并保留现有阈值。
- `chat_push_publish_queue_depth >= 96`（`128` 的 75%）连续 3 个 bucket，或 `chat_push_remote_queue_failed > 0`，告警检查 NATS/Redis；`chat_push_publish_failed` 占 `chat_push_published + chat_push_publish_failed` 超过 1%（最少 100 次）/ 5 分钟时暂停扩容和灰度。
- `chat_push_stale_skipped` 占 `chat_push_received` 超过 5%（最少 100 次）/ 5 分钟时检查 route owner、连接替换与实例摘流；它在受控重连期间可短暂出现，但不能长期增长。`chat_push_session_queue_failed > 10` / 5 分钟按慢客户端告警处理。

这些在线 push 指标只衡量尽力投递；消息持久化和邮件列表可用性必须另行由 PostgreSQL/outbox 指标判定。

## 4. 邮件系统设计

### 4.1 与聊天系统共用部分

邮件系统可以复用聊天系统的：
- 消息存储表结构
- 用户收件箱查询逻辑
- 离线未读推送机制

当前仓库实现说明：
- `mail-service` 已独立落地为 Node.js HTTP 服务
- 新邮件通知通过 Redis 在线路由和 Core NATS 下发：优先按 `chat:online:{playerId}` 路由到 `myserver.mail.notify.instance.<instance_id_token>`，缺路由时回退到 `myserver.mail.notify.<player_id_token>`
- 附件领取由 `mail-service` 发现并调用内网 `game-server.admin` endpoint 完成真实发奖；调用 `AdminAuthReq` 时使用 service actor，兼容 game-server 控制面审计
- 当前未与 `chat-server` 共用同一套存储表

### 4.2 邮件特有字段

邮件 `mail_id` 使用全局 ID 字符串格式 `mail_<base32>`，与通知 outbox、附件领取和审计幂等键保持同一业务 ID。

```sql
CREATE TABLE mail_messages (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    mail_id varchar(64) UNIQUE NOT NULL,
    sender_type varchar(32) NOT NULL,       -- system / player
    sender_id varchar(64) NOT NULL,         -- 玩家侧看到的发件人ID；系统固定为 "system"
    sender_name varchar(128),               -- 玩家侧看到的发件人名称
    receiver_id varchar(64) NOT NULL,       -- 收件人
    subject varchar(256),                   -- 邮件主题
    content text,                           -- 邮件正文
    attachments jsonb,                      -- 附件 (物品/货币奖励)
    created_by_type varchar(32) NOT NULL,   -- system / admin / player / service
    created_by_id varchar(64),              -- 实际触发方，用于审计
    created_by_name varchar(128),           -- 实际触发方展示名
    is_read boolean DEFAULT false,          -- 是否已读
    created_at bigint NOT NULL,
    expires_at bigint                       -- 过期时间 (可选)
);

CREATE INDEX IF NOT EXISTS idx_mail_messages_receiver ON mail_messages (receiver_id);
CREATE INDEX IF NOT EXISTS idx_mail_messages_created ON mail_messages (created_at);
```

建议约定：
- 面向玩家展示的发件人，固定使用 `sender_type / sender_id / sender_name`
- 面向后台审计的操作者，固定使用 `created_by_type / created_by_id / created_by_name`
- 系统奖励邮件不需要真实可登录账号，系统发件人统一保留值 `sender_id = "system"`

### 4.3 邮件 HTTP 路由盘点与公网契约

本节记录当前内网实现与已落地的玩家 HTTPS 公网契约。`CADDY_AUTH_HOST` 已在 auth-http catch-all 之前对白名单玩家邮件路径进行本地校验并反代；生产 Compose 将 `CADDY_AUTH_HOST` 和 443 注入 `auth-http`，由它下发 `services.mail`。这些代码与静态验证不等同于已完成真实发布、证书可用性和客户端联调；正式客户端仍不得把 `mail-service` 内部 endpoint、registry endpoint 或本机 loopback 当作邮件地址。

#### 4.3.1 内网边界与已落地公网路由

`mail-service` 本地默认监听端口为 `9003`，注册的 `mail-service.http` endpoint 始终为 `visibility=internal`。正式环境不通过 registry 将它下发给客户端；development/local 可以显式访问 `http://127.0.0.1:9003` 做内部联调。`CADDY_AUTH_HOST` 已在 auth-http catch-all 之前处理玩家邮件白名单路径，拒绝内部控制面与非白名单请求，并只将允许的玩家请求反代到内部邮件服务。

| 分类 | 当前 method / path | 当前认证与输入 | 当前下游副作用 | 公网边界 |
| --- | --- | --- | --- | --- |
| 健康与开发文档 | `GET /healthz`、Swagger 注册的 `/api/docs` | 无应用层认证；健康响应包含存储与领取开关摘要 | 只读 | 不作为邮件公网 API 路由；不能反代至 `mail-service` |
| 玩家读取 | `GET /api/v1/mails?status&limit&offset`、`GET /api/v1/mails/:mailId` | 默认 game ticket；当前接受 `Authorization: Bearer` 或 `X-Game-Ticket`，并校验签名、过期、Redis ownership 与 ticket version | 查询邮件、未读数 | 仅按 4.3.2 的精确 GET 路由公开 |
| 玩家变更 | `PUT /api/v1/mails/:mailId/read`、`POST /api/v1/mails/:mailId/claim` | 同上；当前 body 中的 `player_id` 只能等于 ticket 玩家，领取角色取 ticket claim | 标记已读；创建/推进领取工作流并可能调用 `game-server.admin` 发奖 | 仅按 4.3.2 的精确 PUT/POST 路由公开 |
| 服务发信 | `POST /api/v1/mails` | `MAIL_SERVICE_TOKEN`，当前可由 Bearer、`X-Service-Token` 或 `X-Admin-Token` 提供；body 包含接收玩家、标题、正文、附件及可审计的发件人字段 | PostgreSQL 邮件和通知 outbox 同事务写入，并尝试在线通知 | 永不经玩家域名转发 |
| 服务奖励投递 | `POST /api/v1/mails/reward-deliveries` | `MAIL_SERVICE_TOKEN`；body 包含 `delivery_request_id`、`mail_id`、玩家/角色、来源、`MAIL_ONLY`、操作者和附件 | 以 delivery request 创建或幂等重放奖励邮件与 outbox | 永不经玩家域名转发 |
| 运维领取控制面 | `GET /api/v1/internal/mail-operations/claims`；`POST /api/v1/internal/mail-operations/claims/:mailId/{reconcile,retry-original,manual-recover}`；`POST /api/v1/internal/mail-operations/outbox/:eventId/replay` | `MAIL_OPERATIONS_TOKEN`；`manual-recover` 额外要求 `MAIL_HIGH_RISK_TOKEN`。查询要求精确筛选；写入要求 `operation_request_id`、actor、reason | 查询受限工作流，安排恢复或重放通知，并写 append-only 审计 | `/api/v1/internal/*` 永不经玩家域名转发 |

`MAIL_PLAYER_AUTH_REQUIRED=false` 只保留给 development/local 兼容调试；production 配置已拒绝关闭。当前 Caddy 白名单、可信代理头重建、请求边界、无敏感访问日志与私有响应禁缓存已覆盖下述公网入口；真实发布、TLS 可达性和客户端全链路仍按独立阶段验收。

当前领取链路的权威边界保持不变：

```text
client
  -> POST /api/v1/mails/:mailId/claim
  -> mail-service
  -> service registry: game-server.admin
  -> game-server admin (GrantItemsReq / GrantItemsRes)
  -> player inventory updated
  -> mail status = claimed
```

`mail-service` 首次领取时会创建唯一 `mail_claim_workflows`，冻结 ticket 绑定的角色、规范化附件、canonical SHA-256 指纹和稳定 `claim_request_id = mail_claim:<mail_id>`，并把邮件置为 `claiming`。明确未写出下游请求的临时失败为 `retryable_failure`；下游请求写出后读超时、断线或结果无法验证时为 `reconciliation_pending`，不能据超时推断未发奖。容量不足当前使用 `blocked_capacity`，玩家清理背包后才可以以同一工作流重试。所有这些状态继续复用既有 PostgreSQL、outbox、租约 fencing 与 game-server 幂等状态机；公网接入不改造为 game-server 玩家协议。

#### 4.3.2 冻结的玩家 HTTPS 公网 API（已实现的服务端契约）

正式客户端的唯一邮件 base URL 固定为 `https://api.game.zergzerg.cn/api/v1/mails`。`auth-http` 只从部署配置下发如下 descriptor，未配置时为 `null`；不得从 `mail-service.http` registry endpoint、Docker DNS、内部默认端口或 `AUTH_EXPOSE_INTERNAL_SERVICE_ENDPOINTS` 推导：

```json
{
  "host": "api.game.zergzerg.cn",
  "port": 443,
  "protocol": "https"
}
```

客户端把 descriptor 与固定 path `/api/v1/mails` 组合，不能接受服务端或配置给出的任意 base path。生产请求必须携带恰好一个 `X-Game-Ticket: <game_ticket>`；ticket 不得出现在 URL、query、cookie、`Referer`、日志或指标。公网契约不支持 `Authorization`、`X-Service-Token`、`X-Admin-Token`、query token 或 body token 作为玩家身份。Caddy 和 `mail-service` 都必须拒绝重复的 credential header，以及同一请求同时携带 `X-Game-Ticket` 与任意其他认证 header。

ticket 必须经 `mail-service` 校验签名、过期时间、Redis `ticket:<sha256(ticket)>` ownership 和 `player-ticket-version:<playerId>`。邮件读取身份只使用 ticket `playerId`；领取角色只使用同一张 ticket 的 `characterId`。客户端不得提供或覆盖 `player_id`、`character_id`、`target_instance_id`、附件、发奖 source、`request_id`、指纹或任何内部路由字段，提供即为 `400 INVALID_PLAYER_MAIL_REQUEST`。角色切换后，已开始的领取工作流仍绑定首次领取的角色；以另一角色 ticket 访问返回 `409 MAIL_CLAIM_CHARACTER_MISMATCH`，不重新发奖。

所有时间字段使用 RFC 3339 UTC 字符串，缺失值为 `null`。公共邮件对象绝不返回 `id`、`to_player_id`、`created_by_*`、`delivery_*`、`origin_*`、`operator_json`、领取租约、内部错误、Redis/registry endpoint、token 或完整 outbox 数据。

| Method / exact path | 输入 | 成功响应与分页 | 幂等和状态语义 |
| --- | --- | --- | --- |
| `GET /api/v1/mails` | 可选 `status`：`unread`、`read`、`claiming`、`claimed`；`limit`：1--50，默认 50；`offset`：0--10000，默认 0。无 body，未知 query key 拒绝。 | `200 { ok, mails, unread_count, pagination }`。`mails` 只包含摘要 `{ mail_id, sender:{type,id,name}, title, mail_type, status, has_attachments, created_at, read_at, claimed_at, expires_at }`；`pagination={ limit, offset, next_offset }`，不返回总数。 | 只读；可按客户端重试规则重试。列表是 PostgreSQL 权威事实，`MailNotifyPush` 只触发刷新。 |
| `GET /api/v1/mails/:mailId` | `mailId` 为现有稳定 ASCII 标识符 `[A-Za-z0-9:_-]{1,64}`，兼容现有 `mail_` 和奖励 `rw_` 前缀；无 query/body。 | `200 { ok, mail }`。`mail` 为上述摘要加 `content`、`attachments` 和当前 `claim` 摘要 `{ claim_status, already_claimed, processing, retryable, player_retryable, attempts, result_state, error }`；附件只返回邮件权威快照中的 `{ type, id, count, binded }`。 | 只读；不属于当前 ticket 玩家时统一按 `404 MAIL_NOT_FOUND` 处理，避免枚举其他玩家邮件。 |
| `PUT /api/v1/mails/:mailId/read` | `Content-Type: application/json` 时 body 必须为空对象 `{}`；不带 body 也允许。 | `200 { ok:true, mail_id, status:"read", read_at, already_read }`。 | 已读重复请求返回相同成功语义，不产生其他副作用；不能借 body 指定玩家。 |
| `POST /api/v1/mails/:mailId/claim` | `Content-Type: application/json` 时 body 必须为空对象 `{}`；不带 body 也允许。 | `200` 已领取，或 `202` 为 `processing` / `reconciliation_pending`。响应固定为 `{ ok, mail_id, claim_status, claimed, already_claimed, processing, retryable, player_retryable, request_id, attempts, result_state, error, message, status, attachments, read_at, claimed_at, completed_at }`。 | 领取幂等键固定为服务端生成的 `mail_claim:<mail_id>`，不是客户端提供的 Idempotency-Key 或 HTTP request ID。重复、并发与恢复都冻结首次角色和附件，不能重复发奖。 |

公共错误 body 固定为 `{ ok:false, error, message }`；边缘拒绝可以省略 `message`，但不得回显原始 URL、header 或 upstream 诊断。错误分类冻结如下：

| HTTP | 稳定分类 | 客户端动作 |
| --- | --- | --- |
| `400` / `413` / `414` / `431` | 无效字段、body、URL 或 header 过界 | 修正请求；不重试 |
| `401` | 缺失、畸形、过期、撤销或 version 不匹配的 ticket，统一为 `MAIL_PLAYER_TICKET_INVALID` | 重新登录或签票；不暴露 Redis 判定细节 |
| `403` | ticket 身份可确认但违反受保护的角色/安全策略 | 不重试；不返回其他玩家数据 |
| `404` / `405` | 邮件不存在、无 ownership 或非白名单 path/method | 不重试；白名单拒绝不得到达 upstream |
| `409` / `410` / `422` | 无附件、角色不匹配、容量阻塞、过期或永久业务失败 | 按稳定状态提示玩家；只允许后续有条件的同一领取重试 |
| `429` | 玩家或可信客户端 IP 限流 | 遵守 `Retry-After`，不并发绕过 |
| `503` | ticket backend、PostgreSQL、权威 game route 或上游暂不可用，且可以证明未完成 | 有限退避后重试读取或同一领取 |
| `202` | `processing` 或 `reconciliation_pending`，尤其是下游结果未知 | 不把它当作未执行；只查询同一 `mailId` 收敛状态，不自动创建或重发领取 |

领取的 `claim_status` 包括 `claimed`、`processing`、`retryable_failure`、`blocked_capacity`、`permanent_failure`、`reconciliation_pending` 和 `manual_review`。`200` 表示已确认幂等成功，`202` 表示已有持久工作流仍在处理或对账；`503 retryable_failure` 只表示确认未应用时可以使用同一 `mailId` 重试。公网响应不得把内部 `error_category`、下游实例、socket/Redis/PostgreSQL 错误、token-like 文本或持久化错误摘要暴露给客户端。

#### 4.3.3 边缘请求约束、请求 ID、超时与重试

`CADDY_AUTH_HOST` 已在 auth-http catch-all 之前处理邮件 path，先按 HTTP method 和规范化后的精确路径白名单匹配，才允许转发到内部邮件服务。允许集合只有：

```text
GET  /api/v1/mails
GET  /api/v1/mails/{mailId}
PUT  /api/v1/mails/{mailId}/read
POST /api/v1/mails/{mailId}/claim
```

`POST /api/v1/mails`、`POST /api/v1/mails/reward-deliveries`、全部 `/api/v1/internal/*`、`/healthz`、`/api/docs`、额外子路径和不在集合中的 method 均返回 `404` 或 `405`，不建立到 mail-service 的 upstream 请求。白名单的正向断言不足以代替拒绝规则：Caddy 静态测试必须证明这些拒绝请求不会落入 auth-http catch-all 或 mail-service。

下列边缘规则已由 Caddy 入口实现；mail-service 的 Fastify `64KiB` body limit 和原始 request log 不替代这些边缘约束：

- 只接受规范 ASCII path；拒绝双斜杠、反斜杠、点段、分号参数、编码或双重编码的 `/`、`\\`、`.`，以及 decode 后不等于白名单模板的 path。`%2F`、`%5C`、`%2E` 和其大小写/重复编码变体不能通过路由匹配。
- 只接受实际 HTTP method。存在 `X-HTTP-Method-Override`、`X-Method-Override`、`_method` query/body 字段时拒绝；不得让 proxy、框架或客户端重写 method。
- URL（path 加 query）最大 2048 bytes，header 总量最大 16KiB，单个 `X-Game-Ticket` 最大 4096 bytes；读取请求无 body，两个玩家变更 body 最大 1024 bytes。超限在边缘以 `413`、`414` 或 `431` 拒绝，且不转发 upstream。
- `X-Game-Ticket`、`Authorization`、`Content-Length`、`Transfer-Encoding`、`Host`、`X-Request-ID` 与所有 `X-Forwarded-*` 均按 singleton 处理。重复 credential、多个/冲突 `Content-Length`、`Transfer-Encoding` 与 `Content-Length` 同时出现、或畸形 forwarded header 必须拒绝，不能依赖 Node/Fastify 的合并行为。
- Caddy 从公网直连 peer 重新生成客户端地址链，删除客户端提供的 `X-Forwarded-For`、`X-Forwarded-Proto`、`X-Real-IP` 和 `X-Request-ID`，再写入自己的 `X-Forwarded-For`、`X-Forwarded-Proto=https`、`X-Real-IP` 与随机 `X-Request-ID`。mail-service 只在 TCP peer 属于配置的 Caddy internal CIDR 时使用这些代理头；直连、未知 peer 或不可信 proxy 一律使用 socket peer，不能伪造玩家 IP、TLS 状态或审计关联。
- Caddy access log 删除 URI/query、`X-Game-Ticket`、`Authorization`、cookie、邮件标题/正文和附件；mail-service 日志只记录经校验的 request ID、受限 method/path 模板、结果分类、延迟及限流维度，永不记录 ticket、完整 body 或完整邮件。玩家私有响应设置 `Cache-Control: private, no-store`；在完成专门评估前，邮件路由不启用响应压缩。

边缘连接上游的目标上限为 3 秒建连、5 秒响应头；mail-service 对 game-server.admin 已有独立 3 秒 connect/write/read 上限，领取路由还必须保留足够时间将“结果未知”持久化为 `202 reconciliation_pending`，不能由 proxy 抢先断开后伪装为未执行。客户端连接加 TLS 上限 3 秒；列表、详情和已读的完整请求上限 8 秒，领取为 12 秒。Caddy、mail-service 和客户端均使用边缘生成的 `X-Request-ID` 关联一次 HTTP 尝试，该 header 只用于诊断，不能代替领取幂等键，也不由客户端决定。

读取和标记已读可以仅对连接建立前失败、`502/503/504` 或 `429` 做最多两次带随机抖动的指数退避；`429` 优先遵守 `Retry-After`。领取一旦请求 body 已写出，或客户端在收到合法响应前超时/断线，客户端不得自动再次 POST，更不能生成新 request ID；应在 1、2、4 秒的有界退避后查询同一 `mailId`，以 `claim_status` 收敛。只有玩家随后明确重试且状态为可重试/容量阻塞时，才允许再次 POST 同一 path；服务端仍使用原工作流。

#### 4.3.4 组件责任与故障语义

| 组件 | 必须负责 | 不负责或不得假设 | 失败语义 |
| --- | --- | --- | --- |
| Caddy | TLS、host/path/method 白名单、大小/重复 header 拒绝、可信代理头重写、request ID、无敏感访问日志、无缓存和受限超时 | 不验证 game ticket、不判断邮件 ownership、不决定领取成功 | 未匹配请求本地 `404/405`；无健康 upstream 或代理失败返回统一可重试边缘 `503`，不泄露容器地址 |
| `mail-service` | 最终 ticket/Redis ownership/version 校验、邮件 ownership、角色绑定、DTO 投影、输入校验、玩家/IP 限流、领取状态机、公开错误映射和脱敏日志 | 不信任 Caddy 就可替代鉴权；不信任 body/query/客户端 request ID；不直接写背包 | Redis ticket backend 不可用为 `503 MAIL_AUTH_UNAVAILABLE` 且无副作用；领取结果未知持久为 `202`，已确认未写出的暂时错误才是可重试 `503` |
| `auth-http` | 为已选角色签发包含 `playerId`、`characterId`、version 的短期 ticket，维护 Redis ownership/version，按部署配置返回 `services.mail` 或 `null` | 不从 registry 暴露 mail internal endpoint，不代理邮件 CRUD，不把 descriptor 当作鉴权成功 | 签票、Redis 或 descriptor 配置失败时不下发内网 fallback；ticket revoke/version 更新在下一邮件请求生效 |
| `game-server` | 维护在线角色权威 route/fence，校验来自 mail-service 的 admin 身份、冻结 request/fingerprint/角色并原子写入背包与幂等结果 | 不接受玩家 HTTP 邮件请求，不让客户端选择实例，不修改邮件记录 | route 缺失、迁移或 fence 不匹配返回未应用的可重试路由失败；写出后结果不明时供 mail-service 对账，不能推断未发奖 |
| 客户端 | 从 descriptor 组合固定 base URL，使用 `X-Game-Ticket`，处理 ticket 更新、`Retry-After`、`202` 与安全重试；收到 `MailNotifyPush` 后刷新列表 | 不硬编码 `9003`、不信任 push 摘要为邮件权威、不传玩家/角色/附件/实例、不以 HTTP request ID 做幂等 | ticket 无效时重新登录/签票；领取超时只查询同一邮件状态，不能盲目创建或假设第二次领取 |

邮件 Caddy route 与 `services.mail` 下发的服务端代码和部署配置均已完成。实际启用仍取决于真实发布、TLS 证书和 HTTPS 联调；客户端迁移由独立客户端 checklist 验收。内网发信、奖励投递、operations 控制面、PostgreSQL 邮件权威、通知 outbox 与领取幂等数据不会因为关闭或回滚公网入口而回滚或清理。

### 4.4 三服务可靠交互契约

本节是 `mail-service`、`chat-server` 与 `game-server` 邮件链路的稳定契约。契约中的“当前实现”用于说明改造起点；标记为“目标契约”的字段和状态是后续实现必须收敛到的行为，不表示当前代码已经全部具备。

#### 4.4.1 权威数据与成功边界

| 数据或动作 | 权威方 | 成功边界 |
|------|------|------|
| 邮件内容、未读/已读状态、附件快照和领取进度 | `mail-service` PostgreSQL | 邮件记录和通知 outbox 在同一事务提交后，邮件创建即业务成功 |
| 在线新邮件提示 | `chat-server` 当前有效 session | 只做尽力在线推送，不属于邮件创建事务，也不改变邮件状态 |
| 角色背包和附件发放结果 | `game-server` PostgreSQL | 背包变更与幂等结果在同一事务提交后，资产发放才成功 |

必须遵守以下边界：

- Core NATS 只承担在线提示。`publish` 成功只表示消息已交给 Core NATS，不表示 `chat-server`、玩家 session 或客户端已收到。
- `chat-server` 离线、玩家离线、session 队列已满、Redis 在线路由缺失或 NATS 丢消息，都不得回滚邮件，也不得把邮件创建接口改成失败。
- `mail-service` 不直接写角色背包，也不能根据调用超时或连接断开推断“game-server 没有发放”。
- 只有 `game-server` 返回与本次 `request_id + request_fingerprint` 匹配的首次成功或幂等成功，`mail-service` 才能把邮件更新为 `claimed`。
- 在线背包 push 是资产事务提交后的派生提示。push 失败不得回滚已经提交的资产，也不得把确定成功降级为结果未知。

##### 奖励来源、邮件托管与 inventory 结算

目标奖励交付模型区分三层概念：

| 层次 | 含义 | 示例 |
|------|------|------|
| `origin` | 奖励产生原因和业务单号 | 成就、任务、战斗结算、场景拾取、活动、排行榜、GM 补偿 |
| `delivery_method` | 奖励在结算前采用的交付方式 | `direct` 或 `mail` |
| `settlement_target` | 道具最终写入的权威资产位置 | 固定为 `inventory` |

邮件不是第二套加道具实现，而是延迟交付和奖励托管方式。直接交付与邮件领取最终都必须调用同一个 inventory 资产事务；`ItemObtainPush`、`InventoryUpdatePush` 和新邮件通知都只是权威状态提交后的派生提示。

来源模块只提交服务端权威奖励单和 `MAIL_ONLY`、`PREFER_INVENTORY`、`INVENTORY_REQUIRED` 之一，不直接写背包或自行实现邮件重试。`PREFER_INVENTORY` 明确收到 `INVENTORY_CAPACITY_FULL/not_applied` 时，通过可靠 outbox 幂等创建一封奖励邮件；若原资产请求为 `unknown`，必须先查询结果，禁止直接 fallback。

邮件领取已经处于邮件托管中。领取时容量不足必须保持原 `mail_id`、冻结附件、指纹和 `claim_request_id`，目标 workflow 进入 `blocked_capacity`，玩家清理背包后重试原请求；不得再创建一封邮件。系统奖励邮件的未领取附件不能因普通邮件过期、硬删除或邮箱容量清理而失去领取入口，必须禁止过期、延长托管或迁移到等价的长期奖励保管状态。

任何一笔奖励在任意时刻必须至少存在于来源模块待结算、已提交 inventory 或已持久化奖励邮件之一。来源模块只能在 inventory 成功证据或奖励邮件持久化成功证据确定后，把原奖励标记为已交付。

#### 4.4.2 当前邮件创建与在线通知时序

当前代码锚点：

| 环节 | 当前实现 |
|------|------|
| 邮件与 outbox 原子写入 | `apps/mail-service/src/db-store.js` 的 `createMailWithNotificationOutbox()` |
| outbox 扫描、租约、重试 | `apps/mail-service/src/mails/mails.service.ts` 的 `processPendingNotificationOutbox()` 及 `db-store.js` 对应方法 |
| Redis 在线路由和 NATS 发布 | `apps/mail-service/src/pubsub-client.js` 的 `PubSubClient` |

```text
上游服务
  -> POST /api/v1/mails（MAIL_SERVICE_TOKEN）
  -> mail-service 校验发信参数并生成 mail_id
  -> PostgreSQL transaction
       INSERT mails
       INSERT mail_notification_outbox(payload)
     COMMIT
  -> 尝试立即领取一条 outbox
  -> Redis GET chat:online:{player_id}

```

当前实现已经保证 PostgreSQL 模式下邮件和 outbox 同事务，但仍有一个需要收敛的响应窗口：事务提交后，创建接口会同步调用一次 outbox 扫描；如果领取 outbox 或更新 outbox 状态本身抛出异常，HTTP 调用可能返回错误，而邮件实际已经落库。目标契约要求数据库事务提交后始终按邮件创建成功响应，通知处理只能影响 outbox 指标和日志。

#### 4.4.3 当前附件领取持久状态机与恢复边界

当前代码锚点：

| 环节 | 当前实现 |
|------|------|
| 玩家身份、邮件归属和附件校验 | `apps/mail-service/src/mails/mails.service.ts` 的 `claim()` |
| 工作流预占、租约 fencing、失败记录和 `claiming/claimed` 条件更新 | `apps/mail-service/src/db-store.js` 的 `reserveMailClaimWorkflow()`、`recordMailClaimWorkflowFailure()` 和 `completeMailClaimWorkflow()` |
| game-server endpoint 发现和 admin TCP 请求 | `apps/mail-service/src/game-admin-client.js` |
| `GrantItemsReq` 校验和发放响应 | `apps/game-server/src/admin_server/gm.rs` |
| 背包变更与幂等记录事务 | `apps/game-server/src/core/player/player_manager.rs`、`db_player_store.rs` |

```text
玩家
  -> POST /api/v1/mails/:mailId/claim（game ticket）
  -> mail-service 从认证上下文取得 player_id 和 character_id
  -> 校验邮件归属、过期时间和附件格式
  -> PostgreSQL transaction + row lock
       INSERT mail_claim_workflows（唯一 mail_id/request_id、冻结附件、指纹、角色、attempt=1、lease）
       UPDATE mails unread/read -> claiming
  -> 发现 game-server.admin endpoint
  -> AdminAuthReq(service actor)
  -> GrantItemsReq(request_id + mail_id + request_fingerprint + trace_id)
  -> game-server 独立重算指纹，原子写背包和 character_inventory_grants
  -> GrantItemsRes(ok=true, applied=true|false, 首次结果摘要)
  -> mail-service 以当前 lease_token 条件更新 workflow -> claimed、mails -> claimed
```

当前分阶段实现状态如下，后续实现不得忽略剩余缺口：

- `mail-service` 已禁止 strict/test/staging/production 从领取 HTTP body 覆盖 `targetInstanceId`；development/local 调试目标也必须通过 registry endpoint 校验。角色、邮件、附件、`request_id`、source、指纹和内部目标均从认证上下文或持久邮件生成，不能由玩家覆盖。
- `game-server` 已按 4.4.5 实现 canonical JSON + SHA-256 独立重算，并在 `character_inventory_grants` 中保存请求指纹和首次结果；相同 `request_id` 的角色、附件、绑定状态或 source 冲突会返回 `REQUEST_FINGERPRINT_CONFLICT`。
- game admin 客户端已补齐 `mail_id`、canonical SHA-256 指纹和 32 位 `trace_id`，并校验响应包 sequence、消息类型、大小限制、错误码以及 `GrantItemsRes` 的 `request_id + request_fingerprint + trace_id + result_summary`。连接建立失败或明确 `ROUTE_UNAVAILABLE/not_applied` 时会重新发现权威实例，重试保持同一请求身份；请求写出后的读超时、protobuf 解码失败或成功证据不匹配统一标记为 `RESULT_UNKNOWN/unknown`，不在客户端内盲目重发。
- `mail-service` 已使用独立 `mail_claim_workflows` 持久化状态机。一封邮件只有一个工作流和一个 request id；附件、角色和指纹在首次预占时冻结，后续邮件内容修改、过期或硬删除都不改变已经开始的发放请求。工作流表不使用指向 `mails` 的级联删除外键，确保硬删除后仍保留资产侧对账证据。
- `processing` 尝试使用 `lease_owner + lease_token + lease_expires_at` fencing；玩家并发请求返回 202 processing，过期尝试沿用原工作流接管并递增 attempts，旧 token 不能写入失败或成功。
- 明确 `not_applied` 按稳定分类持久化为 `retryable_failure` 或 `permanent_failure`，邮件继续保持 `claiming`；`RESULT_UNKNOWN/unknown` 持久化为 `reconciliation_pending`，不会释放或由玩家请求再次发奖。
- 容量不足当前仍复用 `permanent_failure`；目标态新增 `blocked_capacity`，把可由玩家清理背包后恢复的容量条件与配置错误、指纹冲突和人工恢复彻底分开。
- game-server 已在受 admin token 保护的内部通道提供按 `request_id` 查询首次结果的接口；`mail-service` 在启动时立即扫描、之后周期扫描，并用独立 recovery lease 接管超时记录。恢复 worker 与玩家领取 lease 相互 fencing，晚到结果必须同时匹配 recovery token 和未过期租约才能落库。

工作流字段和邮件状态的职责分离如下：

| 持久状态 | 含义 | 玩家再次领取 |
|------|------|------|
| `mails.status = unread/read` | 尚未开始领取 | 校验邮件并创建唯一工作流 |
| `mails.status = claiming` + workflow `processing` | 当前发奖尝试持有有效租约或等待租约恢复 | 有效租约返回 202；过期租约以同 request id 接管 |
| workflow `retryable_failure` | game-server 明确保证未执行，条件可重试 | 以同角色、冻结快照和 request id 新建一次 attempt |
| workflow `permanent_failure` | 业务条件当前不满足，错误原因已保存 | 玩家/配置修正后仍以同工作流重试 |
| workflow `blocked_capacity`（目标态） | game-server 明确保证资产未提交，且唯一阻塞条件是背包容量不足 | 保留原邮件附件；不自动轮询发奖，玩家清理背包后以同 request id 重试 |
| workflow `reconciliation_pending` | 请求可能已提交，结果未知 | 返回 202，不再次发奖，等待恢复 worker 查询 |
| workflow `manual_review` | 自动恢复达到上限、指纹冲突或确定的永久恢复错误 | 返回受限错误；保持 `mails.status = claiming`，等待后续受保护的人工处理 |
| `mails.status = claimed` + workflow `claimed` | 首次成功或幂等成功证据已确认 | 返回幂等已领取结果 |

自动恢复规则：

- `processing` 玩家 lease 超时后先原子转为 `reconciliation_pending` 并取得独立 recovery lease；旧玩家请求和旧 worker 的晚到结果都不能覆盖新 owner。
- `processing` 超时和 `reconciliation_pending` 必须查询 `GrantItemsResultQueryReq`。查询是只读控制调用，不依赖在线角色 route，也不接受玩家提供实例；mail-service 并发查询 service registry 中全部健康 `game-server.admin` endpoint，并校验每个响应的 `request_id`、指纹、trace、结果摘要和实例来源。
- 只有全部健康 endpoint 一致返回 `not_seen` 才能发起写请求；任一 endpoint 不可用、响应损坏或多实例结果不一致都按 `result_unavailable` fail closed 并退避。全部 endpoint 返回同一成功摘要时补写 workflow 和存量 mail 为 `claimed`，不会再次发奖；明确指纹冲突进入 `manual_review`。
- `retryable_failure/not_applied` 到期后可直接准备原请求重试。准备动作先把 workflow 切为 `reconciliation_pending` 并递增 grant attempts，再发送冻结的 `claim_request_id + character_id + attachments_snapshot + attachments_fingerprint`；因此进程在写前或写后崩溃时，下一个 owner 都会先查询结果。
- `blocked_capacity/not_applied` 不进入后台自动重试，避免在玩家未清理空间时持续写请求；玩家再次领取时重新校验邮件归属和当前角色，并复用冻结请求进入 query-first / grant 流程。
- 查询或写调用暂不可用时按有上限指数退避安排 `next_recovery_at`，邮件持续保持 `claiming`。达到 `MAIL_CLAIM_RECOVERY_MAX_ATTEMPTS` 后进入 `manual_review`，保留冻结请求、最近查询状态/指纹/实例、结果分类、错误和时间证据。

#### 4.4.4 邮件通知事件 v1

目标通知使用版本化 JSON 事件信封。新旧格式兼容窗口内，`chat-server` 同时接受当前扁平 payload 和下述 v1 信封；新生产者只发布一份事件，不能为了兼容同时向两个 subject 发布同一事件。

```json
{
  "event_id": "mail.notify:mail_01ABC",
  "event_type": "mail.created",
  "version": 1,
  "occurred_at": 1783931896000,
  "player_id": "plr_01ABC",
  "mail": {
    "mail_id": "mail_01ABC",
    "title": "系统奖励",
    "from_player_id": "system",
    "from_name": "系统",
    "mail_type": "system",
    "created_at": 1783931896000
  },
  "trace_id": "0123456789abcdef0123456789abcdef"
}
```

| 字段 | 类型与约束 | 语义 |
|------|------|------|
| `event_id` | 非空字符串，最多 128 字节 | 一条通知事件的稳定 ID；首次写 outbox 时确定，所有发布重试保持不变。存量 outbox 升级可使用 `mail.notify:<mail_id>` 确定性补齐 |
| `event_type` | 固定 `mail.created` | 未知类型拒绝处理，但不能退出订阅任务 |
| `version` | 整数，当前为 `1` | 未知版本记录兼容失败并跳过 |
| `occurred_at` | Unix epoch 毫秒整数 | 邮件与 outbox 原子创建的业务发生时间，不是某次重试发布时间 |
| `player_id` | 非空字符串，最多 128 字节 | 通知目标；必须与 outbox 的 `to_player_id` 一致 |
| `mail.mail_id` | 非空字符串，最多 64 字节 | 邮件权威 ID |
| `mail.title` | 字符串，最多 256 字节 | push 摘要，不包含正文和附件 |
| `mail.from_player_id` | 非空字符串，最多 128 字节 | 展示发件人；系统邮件固定为 `system` |
| `mail.from_name` | 字符串，最多 128 字节 | 展示名称 |
| `mail.mail_type` | 非空字符串，最多 32 字节 | 邮件类型 |
| `mail.created_at` | Unix epoch 毫秒整数 | 邮件创建时间，供 `MailNotifyPush` 使用 |
| `trace_id` | 32 位小写十六进制字符串 | 由 `mail-service` 生成并持久化；重试保持不变，只用于关联日志和指标 |

`event_id` 用于 `chat-server` 的有界短期去重，不是永久 inbox。玩家离线时不保存事件，不在重新上线后补投；客户端应通过邮件列表读取权威数据。

`chat-server` 的消费边界如下：

- 灰度期间可通过独立的 `CHAT_MAIL_ACCEPT_LEGACY_PAYLOAD` 接受既有扁平 payload；development/local 默认 `true`，strict/test/staging/production 或显式 `DISCOVERY_REQUIRED=true` 未配置开关时默认 `false`。严格策略下要开启时还必须设置未来的 `CHAT_MAIL_LEGACY_COMPAT_UNTIL_EPOCH_SECONDS`，进程运行跨过截止时间后也立即拒绝旧 payload，并增加 `mail_notification_legacy_rejected`。该开关只控制 payload 解析，不取消两条 subject：v1 信封在实例定向 subject 与 legacy player subject 上仍共享 `event_id` 去重。只有 v1 信封具有 `event_id`，旧 payload 不伪造事件 ID，也不承诺跨消息幂等。
- 实例定向 subject 与 legacy player subject 共用同一个进程内去重器；默认容量 `10000`、TTL `300` 秒，按首次接收时间过期，容量满时确定性淘汰最早事件。对应配置为 `CHAT_MAIL_NOTIFY_DEDUP_CAPACITY` 和 `CHAT_MAIL_NOTIFY_DEDUP_TTL_SECS`。
- `CHAT_MAIL_NOTIFY_MAX_PAYLOAD_BYTES` 默认 `4096`。消费者必须先检查原始 payload 字节数，再解析 JSON，并按本节字段上限检查 UTF-8 字节长度；非法 payload 的日志只记录路由类型、错误码和 payload 大小，不记录 payload 或玩家、邮件、事件标识。
- 通知只尝试写入 Redis 当前 route 所属实例且 owner token 匹配的 chat session 队列。玩家离线、route 查询失败或不匹配、队列已满或连接已关闭都安全跳过，不写回邮件状态；同账号旧连接退出时不得删除覆盖它的新 session 或新 session 的在线路由。
- NATS 连接或订阅中断后重新建立两个订阅，退避由 `CHAT_MAIL_NOTIFY_RECONNECT_BASE_MS` 和 `CHAT_MAIL_NOTIFY_RECONNECT_MAX_MS` 控制；服务停机时会取消订阅任务并在有界时间内 drain NATS 客户端。
- 消费指标按上报窗口聚合 `mail_notification_received`、`mail_notification_parse_failed`、`mail_notification_version_rejected`、`mail_notification_legacy_rejected`、`mail_notification_deduplicated`、`mail_notification_pushed`、`mail_notification_offline_skipped` 和 `mail_notification_queue_failed`，不使用 `player_id`、`mail_id` 或 `event_id` 作为标签。

通知 outbox 的运行状态固定为：

```text
pending -> sending -> sent
                   -> failed -> sending
                   -> terminal
```

- `sending` 使用数据库租约，持久化 `lease_owner / lease_token / locked_until`；完成、失败和终止更新必须匹配当前 `lease_token`。租约过期后其他 `mail-service` 实例可以接管，因此发布语义是至少一次，`chat-server` 仍需按 `event_id` 做有界去重。
- `attempts` 表示已经开始的发布次数，第 `MAIL_OUTBOX_MAX_ATTEMPTS` 次允许发布；该次失败或发布结果因进程崩溃而未知时转为 `terminal`，不得开始第 `max_attempts + 1` 次发布。
- `failed` 只表示 Core NATS 临时发布失败，按带抖动且有上限的指数退避重试。
- 永久无效 payload 不继续重试，直接转为 `terminal` 并保存最多 512 字节的错误摘要。
- `sent` 只表示 Core NATS `publish` 已成功返回，不表示 `chat-server`、玩家 session 或客户端确认收到。
- 默认保留已发布记录 7 天、终止记录 30 天，后台按批清理；分别由 `MAIL_OUTBOX_SENT_RETENTION_DAYS`、`MAIL_OUTBOX_TERMINAL_RETENTION_DAYS` 和清理批次配置控制。
- 运行指标覆盖积压数、最老事件年龄、发布延迟、重试数、终止数和过期租约接管数。

#### 4.4.5 附件发放请求 v1

附件领取工作流的稳定幂等键固定为：

```text
request_id = mail_claim:<mail_id>
source     = mail-claim
```

目标 admin 请求在当前 `GrantItemsReq` 基础上补齐以下语义字段。JSON 兼容入口沿用 camelCase；Protobuf 字段使用对应 snake_case 名称。

```json
{
  "requestId": "mail_claim:mail_01ABC",
  "mailId": "mail_01ABC",
  "characterId": "chr_01ABC",
  "items": [
    { "itemId": 1001, "count": 2, "binded": false }
  ],
  "requestFingerprint": "sha256:0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef",
  "source": "mail-claim",
  "reason": "claim mail mail_01ABC",
  "traceId": "0123456789abcdef0123456789abcdef"
}
```

| 字段 | 类型与约束 | 稳定性与信任边界 |
|------|------|------|
| `requestId` | `mail_claim:<mail_id>`，最多 128 字节 | 在首次领取、超时恢复、人工对账和所有跨实例重试中保持不变，由 `mail-service` 生成 |
| `mailId` | 邮件 ID，最多 64 字节 | 来自 `mail-service` 权威邮件记录，不接受玩家覆盖 |
| `characterId` | 非空角色 ID，最多 128 字节 | 来自已验证 game ticket 和服务端角色关系，不接受请求 body 覆盖 |
| `items` | 1 个以上标准化物品项 | 来自预占时冻结的邮件附件快照，不在恢复时重新读取可变请求参数 |
| `requestFingerprint` | `sha256:` 加 64 位小写十六进制 | 由 `mail-service` 按下述规范计算，`game-server` 必须独立重算并比较 |
| `source` | 固定 `mail-claim` | 参与指纹，其他值拒绝 |
| `reason` | 最多 512 字节 | 审计展示，不参与指纹，不得影响幂等判定 |
| `traceId` | 32 位小写十六进制 | 首次预占时生成并持久化，恢复重试保持不变，不参与指纹 |

`source = mail-claim` 表示本次 inventory 结算动作来自邮件领取，不等同于奖励最初来源。目标邮件记录和资产流水还必须保留由可信上游写入的 `origin_type`、`origin_id`、`delivery_request_id` 和操作者上下文。例如成就奖励经邮件领取时，业务来源仍是 `achievement + achievement_id`，交付方式是 `mail`，最终结算动作才是 `mail-claim -> inventory`。

现有 v1 指纹保持兼容，不直接改变 canonical JSON。把来源元数据纳入 game-server 请求和指纹时必须升级为版本化 v2 契约，并在 mail-service、game-server、fixture、结果查询和滚动升级兼容窗口中同步实施；玩家请求始终不能覆盖这些字段。

附件项标准化和指纹算法固定如下，Node.js 与 Rust 必须使用同一测试 fixture 验证：

1. 只接受 `type` 缺省或为 `item` 的附件；把 `id` / `item_id` / `itemId` 统一为十进制 `item_id`，把 `binded` 缺省为 `false`。
2. 校验 `item_id` 为正的 int32、`count` 为正的 uint32、`binded` 为布尔值。
3. 按 `item_id` 升序、`binded` 的 `false` 在 `true` 前排序；相同 `item_id + binded` 合并并对 `count` 做溢出检查。原始附件顺序不影响指纹。
4. 构造无额外空白、UTF-8 编码且键顺序固定的 JSON：

```json
{"mail_id":"mail_01ABC","character_id":"chr_01ABC","source":"mail-claim","items":[{"item_id":1001,"count":2,"binded":false}]}
```

5. 对上述字节计算 SHA-256，编码为 `sha256:<lowercase_hex>`。

`request_id`、`reason`、`trace_id` 和目标实例不进入指纹。`mail_id` 已隐含在 `request_id` 中，但仍显式进入指纹，便于 game-server 查询结果时校验完整业务意图。相同 `request_id` 只有在已存记录的 `request_fingerprint` 完全一致时才能返回幂等成功；任何字段冲突都返回 `REQUEST_FINGERPRINT_CONFLICT`，不得再次发放，也不得把邮件标记为 `claimed`。

#### 4.4.6 附件发放权威路由与调用安全

`game-server` 当前维护独立于 `game-proxy` Room/重连偏好路由的在线资产路由。`game-proxy` 的 `CharacterRouteRecord` 用于接入和 Room owner 选择，不是离线资产写 owner，不能被 `mail-service` 当作安全离线分片依据。

在线路由使用以下 Redis 契约：

```text
key   = <REDIS_KEY_PREFIX>game:online-route:<sha256(character_id)>
value = { version: 2, character_id, instance_id, session_id, authority_generation, authority_token }
TTL   = max(60, 3 * HEARTBEAT_TIMEOUT_SECS)
owner = <REDIS_KEY_PREFIX>game:online-route-owner:<sha256(character_id)>
owner TTL = 3 * route TTL
generation = <REDIS_KEY_PREFIX>game:online-route-generation:<sha256(character_id)>
fence = <REDIS_KEY_PREFIX>game:online-route-fence:<sha256(character_id)>
fence TTL = owner TTL
```

- 只有 game ticket 完整校验成功的连接才能申请权威 generation。Redis Lua 通过 `INCR generation` 产生跨实例可比较的单调代际，并原子写入 `generation:authority_token` fence；申请新代际时立即使旧 route/owner 失效。各 game-server 进程自己的 `session_id` 只用于本地 registry fencing，不能作为跨实例顺序。
- route 发布必须以刚申请的 fence 做 Lua CAS；如果另一个实例已经申请更高代际，延迟的旧发布返回 superseded，不能进入本实例可写 registry。route、owner witness 和 fence 的刷新、恢复、删除也都要求同一 generation/token，旧 owner 不能覆盖、续期或删除新 owner。
- owner TTL 长于 route 但有界，给 route 单独 eviction/过期保留恢复窗口；generation 计数器不参与在线存活判断，用于保证 Redis 正常运行周期内代际单调。Redis 重启导致 route/owner/fence 丢失时，存量连接不得按本地 session 猜测 owner，必须重新认证。
- 刷新区分 `Refreshed`、`Missing` 和 `OwnershipChanged`。只有本实例 registry 仍指向当前 session、fence 与 owner witness 都精确匹配时才能恢复 missing route；检测到 ownership changed、无法证明 owner 或本地 session 已被替换时，旧连接立即从 `PlayerRegistry` 注销并安全断开，不再作为本实例可写会话运行。
- `mail-service` 读取路由后重新扫描 registry，只有 `instance_id` 对应健康且 visibility 为 admin 的 `game-server.admin` endpoint 才允许调用；路由缺失、格式错误、Redis 不可用或实例已摘流统一归入可重试路由失败。
- `mail-service` 把本次解析到的 `authority_generation + authority_token` 随发放请求传给目标实例。`game-server` 在创建 UID、写背包或写幂等成功记录之前，必须同时验证请求 fencing、本地 `PlayerRegistry` handle 以及 Redis route/owner/fence 仍完全一致。目标已切换时返回 `MAIL_CLAIM_ROUTE_MISMATCH / ROUTE_UNAVAILABLE / not_applied`；调用方重新解析 endpoint 和新 fencing，但保持原 `request_id`、指纹和 `trace_id`。
- development/local 的显式调试实例也不能绕过 fencing；调试目标必须同时是 Redis 当前权威 owner。
- 资产事务成功后的 `ItemObtainPush` 和 `InventoryUpdatePush` 直接发送到 `PlayerRegistry` 中当前 session，不依赖角色是否已经进入 Room；旧 session 不会成为推送目标。push 失败仍遵守 4.4.1，不回滚资产事务。
- admin 调用使用 `GAME_ADMIN_TOKEN` 和规范化 service actor，分别限制连接、写入和读取超时，并限制单响应最大字节数。日志只包含实例、`request_id`、`trace_id`、错误码和调用阶段，不记录 token、完整附件或邮件正文。

#### 4.4.7 发放结果与邮件状态决策

目标 game-server 结果必须能够表达以下四种状态：

| 结果 | 含义 | mail-service 动作 |
|------|------|------|
| 首次成功 | 本次请求已经原子提交资产和幂等记录 | 条件更新 `claiming -> claimed` |
| 幂等成功 | 同一 `request_id + request_fingerprint` 的首次成功记录已存在，返回首次结果摘要 | 条件更新 `claiming -> claimed`，不得再次发放 |
| 明确未执行 | game-server 明确保证资产事务没有提交 | 保持同一领取工作流；临时错误退避，容量不足进入 `blocked_capacity` 等待玩家清理，确定的配置 / 契约错误再进入人工处理 |
| 结果未知 | 请求可能已经到达并提交，但调用方没有获得可验证结果 | 保持 `claiming`/待对账，先按 `request_id` 查询，不能释放为 `unread/read` |

game-server 返回成功时至少关联 `request_id`、`request_fingerprint`、`applied`（首次为 `true`、幂等命中为 `false`）和首次结果摘要。仅有 `ok=true, applied=false` 而没有匹配指纹证据，不足以让邮件进入 `claimed`。

#### 4.4.8 稳定错误分类

三服务内部错误统一携带 `error_code`、`error_category`、`result_state` 和 `retryable`。`error_code` 保留具体原因；调用方依据稳定分类做状态转换，不解析错误文本。

`result_state` 只允许：

- `not_applied`：权威服务明确保证资产未提交。
- `applied`：存在匹配 `request_id + request_fingerprint` 的成功记录。
- `unknown`：无法证明已提交或未提交。

| `error_category` | 代表错误 | `result_state` | 自动处理 |
|------|------|------|------|
| `INVALID_REQUEST` | `INVALID_CHARACTER_ID`、`EMPTY_ITEMS`、`INVALID_ITEM_COUNT`、`INVALID_REQUEST_ID`、`INVALID_FINGERPRINT` | `not_applied` | 不自动重试；记录安全/契约错误 |
| `PERMISSION_DENIED` | game ticket 无效、邮件不属于玩家、admin service actor/token 无效 | `not_applied` | 不重试；HTTP 返回 401/403，记录受限审计 |
| `ROUTE_UNAVAILABLE` | `SERVICE_DISCOVERY_UNAVAILABLE`、`GAME_SERVER_ADMIN_ENDPOINT_NOT_FOUND`、权威角色实例不可确定 | `not_applied` | 保持领取工作流并退避重试，不随机选择 endpoint |
| `TIMEOUT` | registry 查询超时、连接建立超时且确认请求尚未写出 | `not_applied` | 保持同一 `request_id` 退避重试 |
| `RETRYABLE_FAILURE` | game-server 明确返回过载、数据库事务失败或临时内部错误且保证未提交 | `not_applied` | 保持同一请求和冻结快照退避重试 |
| `CAPACITY_BLOCKED`（目标态） | `INVENTORY_CAPACITY_FULL`；game-server 明确保证未写入任何附件 | `not_applied` | workflow 进入 `blocked_capacity`；不自动重试、不转新邮件，玩家清理背包后重试原领取 |
| `PERMANENT_FAILURE` | `ITEM_NOT_FOUND`、不支持的附件类型、`REQUEST_FINGERPRINT_CONFLICT` | `not_applied` | 停止自动发放；等待配置修复或人工处理。指纹冲突必须安全告警 |
| `RESULT_UNKNOWN` | 请求写出后的读超时、连接重置、响应损坏、game-server 提交后崩溃、结果查询暂不可用 | `unknown` | 进入待对账；先查询结果，绝不释放领取预占 |

目标内部错误响应至少包含以下字段；Protobuf 使用对应 snake_case 字段，JSON 兼容入口使用 camelCase。不能只返回自由文本 `message`。

```json
{
  "ok": false,
  "requestId": "mail_claim:mail_01ABC",
  "errorCode": "GAME_SERVER_RESPONSE_TIMEOUT",
  "errorCategory": "RESULT_UNKNOWN",
  "resultState": "unknown",
  "retryable": true,
  "playerRetryable": false,
  "traceId": "0123456789abcdef0123456789abcdef"
}
```

目标响应增加 `player_retryable` / `playerRetryable`，用于区分后台自动重试和需要玩家改变条件后主动重试。`blocked_capacity` 固定为 `retryable=false, player_retryable=true, result_state=not_applied`。

玩家 HTTP 接口不暴露内部 endpoint、token 或底层数据库错误。领取工作流尚未持久化时，`INVALID_REQUEST` 返回 400，`PERMISSION_DENIED` 返回 401/403，`ROUTE_UNAVAILABLE` / `TIMEOUT` / `RETRYABLE_FAILURE` 返回 503/504。领取已经持久化后，自动重试或待对账状态返回 202，并给出稳定业务状态和同一 `request_id`；`blocked_capacity` 返回 409 和稳定的背包空间不足提示；`PERMANENT_FAILURE` 返回 409 或 422。`RESULT_UNKNOWN` 必须返回 202，不能返回暗示“可以重新开始一次领取”的普通失败。

同一个底层“超时”必须按发生位置分类：连接建立前超时属于 `TIMEOUT/not_applied`；请求可能写入后的响应超时属于 `RESULT_UNKNOWN/unknown`。通知链路的 Redis/NATS/chat push 错误只更新通知 outbox 或指标，不进入附件领取错误状态。

#### 4.4.9 权威路由和客户端输入边界

- 正式环境的领取 HTTP 请求不能选择 game-server。`targetInstanceId` 仅可作为 local/development 调试字段；strict/test/prod 收到时必须忽略或拒绝，不能参与 endpoint 选择。
- `mail-service` 必须根据服务发现和角色权威路由选择 `game-server.admin`。在线角色优先命中其权威实例；离线角色只有在架构能保证单写一致性时才选择确定性可写实例。
- development/local 使用 registry disabled 的固定 admin fallback 时，`local-fallback` 仅表示 endpoint 来源，不是 game-server 身份。无调试目标时使用唯一固定 endpoint 加当前 Redis v2 route；有调试目标时只接受 route 的真实 `instance_id`。两种路径都必须携带 route generation/token，由 game-server 在资产事务前重新校验。
- 找不到权威实例、存在多个候选且无法证明唯一写入方、实例摘流或迁移中时，返回 `ROUTE_UNAVAILABLE`。不得随机选择健康 endpoint 尝试资产写入。
- 玩家不能通过 body 覆盖 `player_id`、`character_id`、`mail_id`、附件、`request_id`、`source`、指纹或内部实例。HTTP path、认证上下文和邮件权威记录是这些字段的唯一来源。
- `trace_id` 是关联标识，不是认证或幂等凭证；日志不得输出 ticket、admin token、完整邮件正文或无界附件 payload。

#### 4.4.10 内部查询、人工恢复与审计

`mail-service` 提供独立内网控制面 `/api/v1/internal/mail-operations`。该控制面不接受玩家 ticket、普通发信 `MAIL_SERVICE_TOKEN` 或下游 `GAME_ADMIN_TOKEN`；查询、普通恢复调度和通知重放要求 `MAIL_OPERATIONS_TOKEN`，从 `manual_review` 恢复还必须同时提供独立 `MAIL_HIGH_RISK_TOKEN`。两个控制面令牌只接受 header，生产环境必须与彼此、`MAIL_SERVICE_TOKEN` 和 `GAME_ADMIN_TOKEN` 不同；`GAME_ADMIN_TOKEN` 始终只保存在 `mail-service` 内部。

领取查询接口为 `GET /api/v1/internal/mail-operations/claims`：

- 必须至少传一个精确过滤条件：`mail_id`、`request_id`、`player_id`、`character_id` 或领取工作流 `status`，不提供无过滤全表扫描。
- `limit` 默认 20、最大 50；使用单调递减的 `before_id` 游标分页，不返回总数。
- 每条记录关联邮件状态、领取状态、附件指纹、受限错误代码/分类、最近 game-server 查询证据、通知 outbox 摘要和最近 5 条管理操作审计。
- 查询以冻结的 `request_id + character_id + attachments_fingerprint + attachments_snapshot` 调用所有健康 `game-server.admin` endpoint 聚合结果；响应异常、实例不可用或结果不一致统一显示 `result_unavailable/unknown`，不能据此改变邮件状态。
- HTTP 响应不返回邮件标题/正文、附件快照或物品明细、ticket、token、内部 endpoint、数据库错误和自由文本下游错误。game-server 成功摘要只保留角色、来源和物品项数量。

恢复操作均要求 `operation_request_id`、`actor` 和最多 512 字节的 `reason`：

| 接口 | 权限 | 行为 |
|------|------|------|
| `POST /claims/:mailId/reconcile` | operations | 把无活动租约的异常工作流排入 `reconciliation_pending` |
| `POST /claims/:mailId/retry-original` | operations | 排入同一 query-first 流程，不能覆盖冻结请求 |
| `POST /claims/:mailId/manual-recover` | operations + high-risk | 仅允许从 `manual_review` 重新排队，并重置自动恢复计数 |
| `POST /outbox/:eventId/replay` | operations | 仅把 `terminal` 通知恢复为 `pending`，保持原 `event_id` 和 payload |

三个领取操作都不直接调用发奖、不直接把邮件标记为 `claimed`。恢复 worker 必须先查询 game-server；只有全部健康实例一致返回 `not_seen`，才按冻结的 request、character、snapshot 和 fingerprint 重试。查询一致 `succeeded` 时只补写邮件完成状态；冲突、不可用或不一致继续 fail closed。通知重放只影响在线提示 outbox，不更新邮件、领取工作流或资产。

`operation_request_id` 在 `mail_admin_operation_audit` 中唯一。相同 ID、action、target、actor、reason 和风险级别的重复点击返回第一次结果，不再次改变状态；ID 被复用于其他操作上下文时返回冲突。业务状态变更和审计 INSERT 位于同一 PostgreSQL 事务。审计强制记录 actor、reason、高风险标记、前后受限快照和结果；表通过数据库 trigger 拒绝 `UPDATE/DELETE/TRUNCATE`，并撤销 PUBLIC 的对应权限。快照不含邮件正文、附件 payload 或凭证。

保留和关联窗口如下：

| 数据 | 默认策略 | 关联要求 |
|------|------|------|
| 邮件 | 至少 400 天，当前不自动删除 | `mail_id` 关联领取、outbox 和审计 |
| `sent` 通知 outbox | 7 天后批量清理 | 清理前可按 `mail_id/event_id` 关联 |
| `terminal` 通知 outbox | 30 天后批量清理 | 清理前允许受限重放 |
| 领取工作流 | 至少 400 天，当前不自动删除 | `claim_request_id = mail_claim:<mail_id>` |
| game-server 发奖幂等结果 | 不短于领取工作流，策略值默认 400 天；当前不自动删除 | 按 `request_id + fingerprint` 查询 |
| 管理操作审计 | append-only，不自动删除 | 按 target 和 `operation_request_id` 查询 |

对应策略配置为 `MAIL_RETENTION_DAYS`、`MAIL_CLAIM_WORKFLOW_RETENTION_DAYS`、`MAIL_GAME_GRANT_RETENTION_DAYS` 及既有 outbox retention 配置。`mail-service` 启动时强制邮件和 game 幂等策略值都不短于领取工作流。若未来启用邮件、领取或 game 幂等清理，必须先保证 game 结果保留期不短于仍可恢复的领取工作流，并先归档不可变审计；不能独立缩短某一侧造成无法对账。

告警使用无玩家/邮件高基数标签的聚合指标：

- 在 `MAIL_CLAIM_ALERT_WINDOW_MINUTES`（默认 10 分钟）窗口内，`mail_claim_retryable_failures + mail_claim_permanent_failures + mail_claim_result_unknown` 除以 `mail_claim_attempts` 达到 `MAIL_CLAIM_ALERT_FAILURE_RATE_PERCENT`（默认 20%）时，检查 service registry、game admin 错误分类和数据库事务失败。
- `processing/retryable_failure/permanent_failure/reconciliation_pending` 从 `recovery_started_at`（尚未进入恢复时使用 `updated_at`）起超过 `MAIL_CLAIM_ALERT_LONG_RUNNING_MINUTES`（默认 15 分钟）时，使用 `mail_claim_long_running` 告警并先查 game-server 结果，禁止盲目再次发奖；`manual_review` 由独立 backlog 指标覆盖。
- `mail_claim_fingerprint_conflicts > 0` 立即按高优先级处理，冻结普通重试并核对冻结快照、跨版本指纹 fixture 和 game 幂等记录。
- `mail_claim_manual_review_backlog` 达到 `MAIL_CLAIM_ALERT_MANUAL_REVIEW_COUNT`（默认 1）时通知人工处理；人工恢复必须填写原因并使用高风险凭证，处理后以审计前后快照复核。

#### 4.4.11 非目标和兼容边界

本轮邮件可靠交互明确不包含：

- 不引入 JetStream；Core NATS 继续作为允许丢失的在线通知通道。
- 不建设全仓库通用 outbox/inbox SDK，也不改造 metrics、session kick、GM 广播和其他服务事件。
- 不让 `chat-server` 保存邮件、补发离线邮件通知、确认邮件送达或参与附件领取状态。
- 不让 `mail-service` 直接操作 game-server 背包表，也不让 game-server 修改邮件状态。
- 不把短期 `event_id` 去重升级成永久 inbox；邮件列表和 PostgreSQL 邮件记录仍是离线权威来源。
- 不要求三服务同一时刻升级。部署顺序必须先让 `chat-server` 兼容新旧通知、让 `game-server` 支持指纹幂等和结果查询，再启用新的 `mail-service` 生产与恢复逻辑。

#### 4.4.12 灰度开关与回滚安全闸

`mail-service` 将玩家领取入口和存量恢复能力拆成两个开关：

| 配置 | 默认值 | 关闭语义 |
|------|------|------|
| `MAIL_CLAIM_NEW_REQUESTS_ENABLED` | `true` | 不创建或重领玩家 claim lease，不调用 game-server；无工作流的新领取返回 `503 MAIL_CLAIM_INTAKE_DISABLED`，已有工作流只返回持久状态 |
| `MAIL_CLAIM_RECOVERY_ENABLED` | `true` | 只允许在新领取也关闭且 `mail_claim_workflows` 没有任何非 `claimed` 记录时关闭 |

配置层直接拒绝 `MAIL_CLAIM_RECOVERY_ENABLED=false` 与 `MAIL_CLAIM_NEW_REQUESTS_ENABLED=true` 的组合。恢复关闭时，worker 启动会查询 `processing/retryable_failure/permanent_failure/reconciliation_pending/manual_review` 总数和有效玩家/恢复租约；只要存在一条未完成记录，就以 `MAIL_CLAIM_RECOVERY_DISABLE_BLOCKED` 拒绝服务启动。`GET /healthz` 公开两个布尔开关供部署系统核验，但不公开 backlog 明细。这个安全闸不把 `claiming` 释放回普通邮件，也不生成新的 request ID。

部署、灰度指标、回滚 SQL、兼容删除门槛、正式变量和本地联调命令统一见 [邮件可靠链路灰度与回滚手册](../后台与运维/邮件可靠链路灰度与回滚手册.md)。固定顺序为：数据库契约 -> game-server 幂等发放与查询 -> 开启有期限兼容的 chat-server -> `MAIL_CLAIM_NEW_REQUESTS_ENABLED=false` 的 mail-service -> 验证后开启新领取。回滚时先关闭所有 mail-service 新领取，继续保留恢复 worker 和 game-server 查询，等待或接管租约并收敛存量工作流；不能回滚到会释放 `claiming` 后重新发奖的旧实现。

### 4.5 内网隔离测试与验收

邮件内网验收只覆盖本地或隔离测试环境中的邮件业务和跨服务可靠性，不覆盖 Caddy、DNS、TLS、公开 `services.mail` descriptor、生产发布或公网可达性。玩家列表、详情、已读和领取始终使用选角后签发的 character-bound game ticket；内部发信始终使用独立 service token。两类凭证不能互换，也不能通过 query、邮件正文、测试输出或日志记录。

#### 4.5.1 入口、依赖与服务发现

- `tools/mock-client` 手工联调必须显式传入 loopback `--mail-base-url`；玩家场景同时传 `--no-service-discovery`，防止登录响应中的 descriptor 改写测试目标。`9003` 只是本地默认端口，自动化验收不占用它。
- `tests/mail/mail-internal-core-flow.test.mjs` 自行启动隔离的 Redis、Core NATS、`auth-http` 和 `mail-service`，为 auth/mail/game-proxy 占用随机 loopback 端口，并使用独立 Redis prefix。该用例只在 `auth-http` 侧关闭 registry/discovery，使登录响应不下发内部邮件 descriptor；`mail-service` 仍以 `REGISTRY_ENABLED=true`、`DISCOVERY_REQUIRED=true` 向独立 registry prefix 注册并续约。玩家邮件请求显式使用 harness 返回的隔离 mail endpoint，验证真实注册、登录、创建角色、选角、签票、内部发信及玩家列表/详情/已读闭环，不把 registry endpoint 暴露给玩家。
- `tests/mail/mail-reliability-fault-drill.test.mjs` 自行启动隔离的 Redis、Core NATS、两个 `game-server`、`chat-server`、两个 `mail-service` 和故障代理，全部使用随机 loopback 端口。邮件领取必须经独立 Redis registry prefix 发现 `game-server.admin`，并与权威在线路由交叉校验；固定 admin host/port 不是验收路径。
- PostgreSQL 必须是操作者确认的本地或隔离实例，测试账号需有创建和删除数据库的权限。凭证解析依次读取进程环境中的 `TEST_POSTGRES_ADMIN_URL`、兼容变量 `TEST_DATABASE_URL`，再回退到本地 `apps/mail-service/.env` / `apps/auth-http/.env`；不要把连接串写进命令、文档或测试日志。测试只允许创建名称匹配 `myserver_mail_acceptance_<run-id>` 的专用数据库。
- Redis 可执行文件通过 `REDIS_SERVER_BIN` 或系统 `PATH` 提供；Core NATS 通过 `NATS_SERVER_BIN`、仓库 `bin/nats-server.exe` 或系统 `PATH` 提供。可靠性演练还要求已编译的 `game-server` 与 `chat-server`，默认读取 `target/debug/`，也可用 `TEST_GAME_SERVER_BIN` / `TEST_CHAT_SERVER_BIN` 指向相对项目根目录的隔离制品。

不要为这些自动化用例手工启动默认端口服务，也不要复用或停止开发者已经运行的进程。测试 harness 负责临时进程和随机端口；若依赖缺失，应先修正本地工具或编译制品，再重新运行同一命令。

#### 4.5.3 脱敏与清理

- player ticket、service/admin token、签名私钥和 PostgreSQL/Redis 连接串只通过进程环境或测试 harness 注入；验收记录只保留命令、通过数量、受限错误分类和清理结论。
- 日志不得包含完整 header、URL query、邮件标题/正文、附件 payload、私钥、token 或连接串。需要关联时只记录受限 request ID、`mail_id`、实例测试 ID 和稳定错误分类。
- 核心流与故障演练都使用 `runWithCleanup` 注册反向清理：终止测试托管进程和代理、关闭 NATS/Redis/数据库连接、删除独立 Redis prefix，最后删除专用 PostgreSQL 数据库。即使主流程失败，也必须继续执行后续清理并保留主错误与清理错误。
- 清理完成以测试内置反查为准：Redis prefix 无残留、专用数据库不存在、托管进程已退出。失败中断时先按测试输出识别本轮 run ID，只处理该 run 的资源，不停止默认端口服务，不删除共享数据库或无关 Redis key。

## 5. 公告系统设计

### 5.1 定位

公告系统独立于 `auth-http`，因为 `auth-http` 只负责登录认证。

当前仓库实现说明：

- 已落地独立 `announce-service`
- 当前对外使用 HTTP 接口，而不是独立 TCP / protobuf 公告协议
- 当前支持：
  - `GET /api/v1/announcements`，默认要求 `ANNOUNCE_READ_TOKEN` 或玩家 game ticket
  - `GET /api/v1/announcements/:announceId`，默认要求 `ANNOUNCE_READ_TOKEN` 或玩家 game ticket
  - `POST /api/v1/announcements`，要求 `ANNOUNCE_ADMIN_TOKEN`
  - `PUT /api/v1/announcements/:announceId`，要求 `ANNOUNCE_ADMIN_TOKEN`
  - `DELETE /api/v1/announcements/:announceId`，要求 `ANNOUNCE_ADMIN_TOKEN`
- `ANNOUNCE_ADMIN_TOKEN` 支持 `Authorization: Bearer <token>` 和 `X-Admin-Token: <token>` header，不支持 query token；生产环境禁止空值或开发默认值
- `ANNOUNCE_READ_TOKEN` 支持 `Authorization: Bearer <token>`、`X-Read-Token` 和 `X-Service-Token` header；玩家 game ticket 支持 `Authorization: Bearer <game_ticket>` 和 `X-Game-Ticket`，并校验签名、过期、Redis ticket 归属和 `player-ticket-version:<playerId>`；不支持 query token
- `ANNOUNCE_READ_AUTH_REQUIRED=false` 只允许本地/内网兼容调试；生产环境强制为 `true`，并拒绝默认/弱 `ANNOUNCE_ADMIN_TOKEN`、默认/弱 `TICKET_SECRET` 和默认/弱或与 admin token 相同的 `ANNOUNCE_READ_TOKEN`
- `announce-service` 默认仍是内网能力服务，不是生产公网入口；只读查询第一阶段鉴权已落地，但如果临时公网暴露，仍需要网关、TLS、用途隔离/换票、RBAC 和审计查询继续兜底
- 当前存储支持：
  - `DB_ENABLED=true` 时使用 PostgreSQL 持久化
  - `DB_ENABLED=false` 时回退到内存存储
- 已验证 PostgreSQL 模式下公告在服务重启后仍可查询
- 已通过 `tools/mock-client` 完成 `announce-list/get/create/update/delete` 联调验证

### 5.2 建议放置位置

**方案A**：独立 `announce-service`
- 完全独立，职责单一
- 仅本地开发或手工调试 fallback 可被客户端 HTTP 直连；测试、预发和线上不以固定 host/port 直连作为准入路径，应经 registry endpoint、API/BFF、网关或服务端入口收敛

**方案B**：放在 `game-proxy` 内
- 与 `game-proxy` 部署在一起
- 减少服务数量

**推荐方案A**，原因：
- 公告更新频率低，但逻辑可能扩展（如定时公告、区域公告）
- 独立服务更容易单独扩缩容
- 职责清晰，不与代理混淆

### 5.3 公告协议

```proto
message AnnouncementListReq {
  string locale = 1;              -- 语言
  int32 priority = 2;             -- 优先级筛选

message AnnouncementListRes {

  string id = 1;

message AnnouncementPushReq {     -- 管理员推送

  string content = 2;
  int32 priority = 3;

  string target_group = 5;
```

### 5.4 公告存储

公告 `announce_id` 使用全局 ID 字符串格式 `ann_<base32>`，HTTP CRUD、后台展示和 mock-client 参数均使用该 ID。

```sql
CREATE TABLE announcements (
    id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    announce_id varchar(64) UNIQUE NOT NULL,
    locale varchar(32) NOT NULL DEFAULT 'default',
    title varchar(256) NOT NULL,
    content text NOT NULL,
    priority integer DEFAULT 0,
    announce_type varchar(32) DEFAULT 'banner', -- popup / banner / scroll
    target_group varchar(128) DEFAULT 'all',    -- all / vip / new_user 等
    start_time timestamptz NOT NULL,
    end_time timestamptz NOT NULL,
    created_at timestamptz NOT NULL DEFAULT current_timestamp,
    updated_at timestamptz NOT NULL DEFAULT current_timestamp
);

CREATE INDEX IF NOT EXISTS idx_announcements_locale ON announcements (locale);
CREATE INDEX IF NOT EXISTS idx_announcements_priority ON announcements (priority);
CREATE INDEX IF NOT EXISTS idx_announcements_time ON announcements (start_time, end_time);
```

## 7. 客户端获取公告的流程

```
1. 客户端启动
2. 请求 auth-http 登录
3. 登录成功后，可从返回的 `services.announce` 获取公告服务地址
4. HTTP 请求 announce-service 获取公告列表，并携带 game ticket；如果经内部网关读取，也可由网关携带 `ANNOUNCE_READ_TOKEN`
5. announce-service 返回当前有效公告
6. 客户端展示公告
```

当前仓库实际情况补充：

- `auth-http` 在允许暴露内部服务 endpoint 的非生产场景，可通过 registry 把 `chat-server.tcp`、`mail-service.http`、`announce-service.http` 写入统一的 `services` 对象
- 生产环境和正式客户端不得暴露 chat/mail/announce 内网 endpoint；公网聊天 WSS 落地后使用部署配置提供的 Caddy 边缘入口，公告和邮件仍经游戏入口、服务端入口、API/BFF 或网关收敛
- 同时仍保留旧的 `gameProxyHost/gameProxyPort` 字段兼容现有客户端
- 当前公告获取链路是“登录后主动 HTTP 拉取”，不是 `game-proxy` 自动推送

```json
{
  "services": {
    "announce": {
      "host": "127.0.0.1",
      "port": 9004,
      "protocol": "http"
    }
  }
}
```

以下是未实现的备选方案，不是当前链路：

```
1. 客户端连接 game-proxy 时
2. game-proxy 自动推送当前有效公告
```
