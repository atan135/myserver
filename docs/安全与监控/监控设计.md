# 服务健康检查与监控实现说明

统一资产事务、奖励邮件、领取恢复和低基数指标的当前边界见[统一资产事务与奖励交付运行边界](../游戏服与接入层/背包与物品/统一资产事务与奖励交付运行边界.md)。

## 1. 概述

当前仓库中的监控系统已经完成基础落地，目标是为管理后台提供：

- 服务在线 / 离线状态
- 最近 5 秒桶聚合的 QPS 与平均延迟
- 同服务多实例实时指标明细
- 服务专属在线类指标
- 历史窗口图表查询
- rollout / drain 控制面状态轮询、展示和告警
- 超期 metrics 数据归档

这套能力由以下模块共同组成：

- 各服务内部 metrics 模块，周期性发布到 Core NATS
- `metrics-collector` 订阅 `myserver.metrics.>`，写入 Redis metrics v2 latest/history 有界索引；legacy heartbeat 默认停写
- `admin-api` 监控接口读取 Redis，内置分钟级自动归档调度，并提供共用同一归档锁的手动入口
- `admin-api` 只读查询 `game-proxy` admin HTTP `GET /rollout`，归一化 rollout / drain 观测状态
- `admin-web` 监控页面，展示总览卡片、rollout / drain 告警区域与详情图表

当前实现已经落地，不再是纯设计稿。

本文的 `metrics-collector` 只负责 Core NATS 指标消息、Redis metrics v2 和指标归档，不负责采集服务 stdout/stderr，也不负责写入普通运行日志目录。普通运行日志由已纳入 release bundle 的常驻 Vector 负责采集，Docker 缓冲和 `/data/myserver/log` 留存契约见[服务端日志采集与留存设计](./服务端日志采集与留存设计.md)。Vector 的运行诊断通过其 systemd JSON 日志、internal metrics、`vector-status.sh` 和 `vector-alerts.sh` 获取；不得把 `metrics-collector` 或 metrics 归档状态当作文本日志采集状态，未在目标宿主机启动 Vector 时仍使用 `docker logs` 有限窗口兜底。

## 2. 当前实现架构

### 2.1 数据流

```text
服务运行时采集指标
  -> 每 5 秒发布 Core NATS myserver.metrics.<service>.<instance>
  -> metrics-collector 写入 Redis metrics v2 latest/history/index
  -> admin-api 读取 Redis 生成监控接口响应
  -> admin-web 通过监控页面串行轮询展示

admin-api 归档调度器（启动后立即执行，之后默认每 5 分钟）
  -> 按有界 history index 读取一小时前的 5 秒桶
  -> 聚合为每服务每分钟一行并写入 PostgreSQL metrics_archive
  -> 数据库提交成功后清理对应 Redis history

game-proxy admin GET /rollout
  -> admin-api GET /api/admin/monitoring/rollout-drain 归一化状态和告警
  -> admin-web /monitoring 每 15 秒串行轮询展示
```

## 3. Redis 数据结构

Redis 中的 metrics 数据当前由 `metrics-collector` 写入，服务本身不再直接写 Redis metrics。

### 3.1 Metrics 数据

```text
Key:    metrics:v2:latest:{service_name}:{service_instance_id}
Value:  Redis Hash（实例最新快照）
TTL:    180 秒

Key:    metrics:v2:history:{service_name}:{timestamp_5s_bucket}
Value:  Redis Hash（field 为 instance_id，value 为实例 JSON）
TTL:    4500 秒（一小时查询窗口 + 15 分钟归档缓冲）

Index:  metrics:v2:latest-index:{service_name}
Index:  metrics:v2:history-index:{service_name}
```

5 秒桶时间戳为秒级 Unix 时间戳，按 5 秒对齐。

legacy 兼容 key：

```text
Key:    metrics:{service_name}:{service_instance_id}:{timestamp_5s_bucket}
Key:    metrics:{service_name}:{timestamp_5s_bucket}
```

legacy key 只在 `METRICS_LEGACY_WRITE_ENABLED=true` 的受控迁移窗口写入；默认和生产目标值为 `false`。当前 `admin-api` 已切换到 `metrics:v2:latest:*` 与 `metrics:v2:history:*` 有界索引，不再以扫描 legacy key 作为正常查询或归档路径。v2 完整结构、TTL、容量与清理顺序见[Registry 监控读模型设计](./Registry监控读模型设计.md)。

### 3.2 心跳数据

```text
Key:    metrics:heartbeat:{service_name}
Value:  最近一次上报时间戳字符串
TTL:    30 秒
```

实例级心跳：

```text
Key:    metrics:heartbeat:{service_name}:{service_instance_id}
Value:  该实例最近一次上报时间戳字符串
TTL:    30 秒
```

这些 heartbeat 仅供 legacy 兼容写使用；关闭 legacy 后不再创建或续期。`admin-api` 使用 v2 latest 的 `_reported_at` 与 Registry heartbeat 分别判断指标新鲜度和实例注册状态。

说明：

- `metrics:heartbeat:*` 不是 service registry heartbeat，不能用于服务发现或流量路由。
- v2 latest 缺失、延迟或过期只表示指标状态 `missing/delayed/stale`，不能把仍有 Registry heartbeat 的实例误报为离线。
- Registry 实例状态与 metrics 新鲜度在 API 和页面中分别展示。

### 3.3 Metrics Hash 字段

| 服务 | 当前写入字段 |
|------|--------------|
| `auth-http` | `qps` `latency_ms` `online_sessions` `unique_players` `active_sessions_5m` `active_window_seconds` |
| `game-server` | `qps` `latency_ms` `online_players` `room_count`，以及活动请求结果、发奖延迟、恢复 backlog、缓存失败、邮件附件幂等和客户端协议版本判定窗口计数 |
| `game-proxy` | `qps` `latency_ms` `connections` 和客户端协议版本判定窗口计数 |
| `chat-server` | `qps` `latency_ms` `online_players`、TCP/WSS 连接与握手、实例连接容量拒绝、出站队列失败，以及邮件通知和 routed chat push 的接收、发布、投递、陈旧 route、队列/解析失败和 publish queue depth/capacity |
| `match-service` | `qps` `latency_ms` `pool_size` |
| `announce-service` | `qps` `latency_ms` |
| `mail-service` | `qps` `latency_ms`，以及通知 outbox、附件领取、积压告警和恢复 worker 指标 |
| `admin-api` | `qps` `latency_ms` |
| `db-migration` | `database_key` `target_migration_version` `applied_migration_versions` `attempted_migration_versions` `outcome` `error_category` |

所有新 metrics hash 会额外写入 `instance_id` 字段，字段值与 key 中的 `service_instance_id` 保持一致。

`db-migration` 是按需启用的运维 producer，不属于玩家服务或管理后台固定服务列表。`tools/db.js up` 在数据库 migration 和 audit 得到结果后，通过 `tools/db-migration-metrics.js` 向 `myserver.metrics.db-migration.<base64url-instance>` 发布现有 NATS metrics 信封；instance 固定为 `migration-<database>-<target-version>`，因此 Redis 中可以按精确版本定位 `metrics:v2:latest:db-migration:<instance>` 及对应 history bucket。只有 `MYSERVER_DB_MIGRATION_METRICS_ENABLED=1` 时才连接 NATS，`MYSERVER_DB_MIGRATION_METRICS_NATS_URL` 优先于 `NATS_URL`。child 环境为严格 allowlist，`NATS_URL` 是唯一允许的通用 transport URL，不继承 `REDIS_URL`、数据库/服务 URL、PG*、Stage7/deploy 或通用凭据。连接或 publish 在受限超时内失败时，迁移结果保持不变并记录 `metrics.state=unavailable`；不能把该 CLI 字段视为 collector 已写 Redis 的证明。事件只含版本和安全错误类别，不含 DSN、密码、SQL 或原始数据库错误。

`game-proxy` 的 `connections` 表示活跃前端连接数，包含尚未完成 `AuthReq` 的预鉴权连接；它不再仅代表已经绑定 upstream 的代理连接。

玩家协议版本判定会在 `game-proxy` 和 `game-server` 的 5 秒 bucket 写入 `client_protocol_auth_accepted_legacy_total`、`client_protocol_auth_accepted_current_total`、`client_protocol_auth_accepted_supported_older_total`、`client_protocol_auth_rejected_too_old_total` 与 `client_protocol_auth_rejected_too_new_total`。它们是每个 bucket 的增量，不是跨进程单调总量；正式客户端版本退役只聚合 proxy 实例，game-server replay 计数不能和 proxy 相加。协议策略与退役门槛见[协议版本协商与发布边界](../协议与客户端/协议版本协商与发布边界.md)。

`admin-api` 会把各服务的在线类字段统一映射成 `online_value` 返回给前端：

- `auth-http` -> `unique_players`
- `game-server` -> `online_players`
- `game-proxy` -> `connections`
- `chat-server` -> `online_players`
- `match-service` -> `pool_size`
- `announce-service` / `mail-service` / `admin-api` -> `0`

### 3.4 多实例聚合策略

`admin-api` 读取同一 `service + bucket` 下的所有实例 key 后生成服务级聚合，同时返回 `instances` 明细。

聚合规则：

- 累加字段：`qps`、`online_sessions`、`unique_players`、`active_sessions_5m`、`online_players`、`connections`、`pool_size`、`room_count`
- 最大值字段：`latency_ms`
- 非数值/未知字段：服务级聚合保留第一个出现的值；实例明细保留各实例自己的字段
- `instance_ids` 为参与聚合的新实例 ID 列表，`instance_count` 为新实例数量
- 旧 key 数据参与服务级聚合，并在历史点实例明细中以 `instance_id=legacy` 标记；它不计入 `instance_count`

## 4. 指标来源

### 4.1 Node.js 服务

`auth-http`、`announce-service`、`mail-service`、`admin-api` 当前通过中间件统计：

- QPS：HTTP 请求完成数
- 延迟：请求开始到响应结束的耗时

其中：

- `auth-http` 维护 session/player 过期索引与最近活动索引；每次采集只执行三个有界 `ZREMRANGEBYSCORE` 和三个 `ZCARD`，不扫描 session key。存量会话通过默认 dry-run、显式确认后才写入的一次性 backfill 工具迁移
- `announce-service` 与 `admin-api` 当前只上报基础 HTTP 指标；`mail-service` 还从 outbox、领取状态机、恢复 worker 和运维查询路径上报邮件专属指标

`auth-http` 索引 key：

```text
<REDIS_KEY_PREFIX>auth-index:sessions:expires
<REDIS_KEY_PREFIX>auth-index:players:expires
<REDIS_KEY_PREFIX>auth-index:activity:last-seen
```

登录替换、会话续期、活动刷新、登出和密码修改会同步维护索引。续期使用 Lua 校验 `player-session:<playerId>` 仍指向当前 token 后再原子续期，避免已经被新登录替换的旧请求重新写回索引。过期成员由采集 pipeline 按 score 有界清理，ZSET 为空后 Redis 自动删除 key。

存量迁移脚本为 `apps/auth-http/scripts/backfill-session-metrics-index.js`。脚本默认 dry-run，只有同时传入 `--apply --confirm backfill-session-metrics-index` 才写入；它是一次性运维工具，允许受控扫描精确的 `<REDIS_KEY_PREFIX>session:*`，不得接入服务启动、定时任务或请求路径。滚动发布时先用新镜像 dry-run 并执行一次 backfill，全部 `auth-http` 实例切换完成后再补跑一次，以覆盖发布窗口内由旧实例创建或续期的会话；随后确认 Redis `cmdstat_scan` 不再按 5 秒增长。

### 4.2 Rust 服务

`game-server`、`chat-server`、`match-service`、`game-proxy` 当前已经接入真实运行时路径：

| 服务 | QPS / 延迟来源 | 在线类指标来源 |
|------|----------------|----------------|
| `game-server` | TCP 消息主分发路径 | 在线玩家数、房间数 |
| `chat-server` | 聊天消息主循环 | 在线聊天会话数 |
| `game-proxy` | 代理会话处理路径 | 活跃前端连接数 |
| `match-service` | gRPC handler | 匹配池大小 |

### 4.2.1 活动可靠性指标

`game-server` 对活动动作使用固定集合 `list/detail/progress/claim/draw/history/game_entry/unknown`，每个动作写入 `activity_request_<action>_total`、`activity_success_<action>_total`、`activity_qualification_failure_<action>_total`、`activity_duplicate_<action>_total` 和 `activity_rate_limit_<action>_total`。这些字段是当前 5 秒 bucket 增量。`history` 只统计历史查询请求结果，不包含角色 ID、游标、活动 ID 或记录内容等高基数字段；存储不可用、游标错误和限流应结合对应 error code 与 PostgreSQL 运行日志排查。

奖励与恢复字段包括：

- `activity_reward_delivery_latency_ms`：本窗口统一奖励交付调用的平均耗时。
- `activity_reward_delivery_count`：参与上述平均值的交付次数。
- `activity_recovery_backlog`：奖励邮件 outbox 中处于 pending、retryable failure 或租约已失效 processing 状态的当前可自动恢复记录数。
- `activity_cache_failure_read_total`、`activity_cache_failure_write_total`、`activity_cache_failure_refresh_total`：固定原因分类；`activity_cache_failure_total` 保留兼容总计数。

字段名只由编译期固定枚举生成，不拼接角色/账号 ID、原始活动 ID、request ID、claim ID、token 或版本。主体级排障读取受权限保护的 PostgreSQL 运行记录和审计，不能通过增加动态 metrics 字段解决。`activity_recovery_backlog` 是每实例从共享库查询的 gauge，多实例服务级展示不得求和；当前 admin-api 对未知扩展字段不保证正确聚合，活动告警应查看 `instances` 明细。建议在 backlog 连续增长、缓存刷新失败持续非零、资格失败或限流相对请求量突增、发奖延迟显著偏离基线时暂停活动发布并检查 PostgreSQL、Redis、mail-service 和 registry。

### 4.2.2 chat-server 容量与多实例投递告警

`chat-server` 的计数指标是当前 5 秒 bucket 增量；`connection_capacity_current`、`tcp_connections_current`、`websocket_connections_current`、`chat_push_publish_queue_depth` 和 `chat_push_publish_queue_capacity` 是当前实例 gauge。所有规则先按实例查看，不能只依赖服务级聚合：

| 条件 | 阈值 | 处置 |
| --- | --- | --- |
| 单实例连接接近容量 | `connection_capacity_current >= 450` 持续 1 分钟 | 停止扩大接入，检查慢客户端、RSS 和重连风暴；不要提高 `CHAT_MAX_CONNECTIONS`。 |
| 容量已拒绝连接 | `connection_capacity_rejected_total > 0` | 立即摘除接新流量并扩容到经验证的独立多实例拓扑，或等待连接回落。 |
| Upgrade 洪峰 | `websocket_handshake_success_total + websocket_handshake_failure_total >= 480` / 5 秒持续 1 分钟，或 `websocket_handshake_rate_limited_total > 0` | 检查 Caddy/reload、客户端退避与异常来源，保留每实例 `120/s` 与 `64` pending 的门槛。 |
| 慢客户端 | `tcp_outbound_queue_failure_total + websocket_outbound_queue_failure_total > 10` / 5 分钟 | 检查网络、消息大小和客户端消费；优先隔离慢客户端，不能扩大 `32` 条队列逃避内存预算。 |
| publish 积压或失败 | `chat_push_publish_queue_depth >= 96` 连续 3 个 bucket，`chat_push_remote_queue_failed > 0`，或 `chat_push_publish_failed / (chat_push_published + chat_push_publish_failed) > 1%`（最少 100 次）/ 5 分钟 | 检查 Redis route 和 NATS，暂停灰度/扩容；聊天历史和邮件列表仍按持久化路径恢复。 |
| 连接迁移或陈旧路由异常 | `chat_push_stale_skipped / chat_push_received > 5%`（最少 100 次）/ 5 分钟，或 `chat_push_session_queue_failed > 10` / 5 分钟 | 检查 route owner、连接替换和实例摘流；受控重连的短暂 spike 可记录，但持续增长必须阻断发布。 |
| 容器内存 | Docker RSS `>= 205MiB` 持续 5 分钟，`>= 230MiB`、OOM 或重启 | 停止接新连接并排查；`mem_limit=256m` 不是可用预算，不能以扩大 swap 或取消边界处置。 |

当前生产 Compose/release apply 仍固定 `chat-server` 一副本。Caddy 对新 WSS 连接的 round-robin 仅提供接入均衡，不能视为多实例投递或容量扩容已经完成。

### 4.3 邮件可靠链路灰度指标

灰度必须同时查看三个服务的实例明细：

- mail-service：`mail_outbox_backlog`、`mail_outbox_oldest_age_ms`、`mail_outbox_published`、`mail_outbox_retries`、`mail_outbox_terminal`、`mail_claim_attempts`、`mail_claim_succeeded`、`mail_claim_route_unavailable`、`mail_claim_grant_failures`、`mail_claim_result_unknown`、`mail_claim_retryable_failures`、`mail_claim_permanent_failures`、`mail_claim_long_running`、`mail_claim_fingerprint_conflicts`、`mail_claim_manual_review_backlog` 和全部 `mail_claim_recovery_*`。
- chat-server：`mail_notification_received`、`mail_notification_parse_failed`、`mail_notification_version_rejected`、`mail_notification_legacy_rejected`、`mail_notification_deduplicated`、`mail_notification_pushed`、`mail_notification_offline_skipped` 和 `mail_notification_queue_failed`。
- game-server：`inventory_grant_first_success_total`、`inventory_grant_idempotent_hit_total`、`inventory_grant_fingerprint_conflict_total`、`inventory_grant_transaction_failure_total` 和 `inventory_grant_push_failure_total`。

当前 admin-api 对未列入累加规则的扩展字段只保留一个服务级值，因此邮件灰度不能只看服务级聚合卡片；应读取 `instances` 明细或底层同窗口 metrics hash 后自行求和。`mail_notification_offline_skipped` 是在线提示语义，不计业务失败；`inventory_grant_idempotent_hit_total` 是恢复证据，不计重复发奖。指纹冲突任一非零立即暂停灰度。具体公式、基线对比、回滚 SQL 和兼容删除门槛见 [邮件可靠链路灰度与回滚手册](../后台与运维/邮件可靠链路灰度与回滚手册.md)。

```json
          "unique_players": 160,
          "last_heartbeat": 1713000000000
        }
      ]
    }
  ]
}
```

当前逻辑：

- 从服务实例索引与 `metrics:v2:latest-index:{service_name}` 批量读取当前注册状态和 latest snapshot
- 依据 v2 `_reported_at` 区分 fresh、delayed、stale、missing，Registry heartbeat 独立决定实例是否可发现
- 历史图表按 `metrics:v2:history-index:{service_name}` 的时间范围读取有界 bucket，不扫描 Redis
- 返回 `qps`、`latency_ms`、`online_value` 以及原始指标字段
- 同时返回 `instances`，包含每个实例在最新 bucket 的指标、实例心跳状态和最后心跳时间

### 5.3 `GET /api/admin/monitoring/services/:name/metrics`

用于监控详情页图表。

请求参数：

```text
window=1m|5m|15m|1h
```

返回示例：

```json
{
  "service": "auth-http",
  "window": "5m",
  "points": [
    {
      "timestamp": 1713000000,
      "qps": 118,
      "latency_ms": 5,
      "online_value": 320,
      "online_sessions": 348,
      "unique_players": 320,
      "active_sessions_5m": 126,
      "instance_count": 2,
      "instances": [
        {
          "instance_id": "auth-http-001",
          "qps": 58,
          "latency_ms": 5,
          "online_value": 150,
          "unique_players": 150
        }
      ]
    }
  ]
}
```

当前逻辑：

- 只接受固定窗口 `1m` / `5m` / `15m` / `1h`
- 只通过 Redis history ZSET 的 `ZRANGEBYSCORE` 获取对应时间范围内的 5 秒桶，再 pipeline 读取确定的 hash key
- 同一 bucket 的多实例 key 会聚合成一个图表点，并在该点下返回 `instances` 明细
- 结果按时间戳升序返回

注意：

- 当前详情接口没有从 PostgreSQL `metrics_archive` 回查历史数据
- 因此归档后的老数据目前不会通过该接口重新读出来

### 5.4 `GET /api/admin/monitoring/rollout-drain`

用于监控总览页展示 rollout / drain 控制面状态。接口仍挂 `monitoring.read` 权限，只做只读观测，不会调用 `POST /rollout/complete-if-drained`、`POST /rollout/end`，也不会自动停止旧服进程。

数据来源:

- `admin-api` 通过 Redis service registry 发现 `game-proxy.admin` endpoint，按 instance id 聚合可用 proxy admin 实例
- `GAME_PROXY_ADMIN_HOST` / `GAME_PROXY_ADMIN_PORT` 只允许在 `development` / `local` 且 discovery 非 required 时作为 local fallback；test / staging / production 不允许依赖固定地址访问 proxy admin
- 优先使用 `GAME_PROXY_ADMIN_READ_TOKEN`，未配置时使用 `GAME_PROXY_ADMIN_TOKEN`
- 请求 `GET /rollout`，读取 `rollout_session` 与 `drain_evaluation`

返回会归一化为适合前端展示和告警的结构:

```json
{
  "ok": true,
  "source": "game-proxy",
  "checked_at": 1713000000000,
  "updated_at": 1713000000000,
  "active": true,
  "status": "blocked",
  "alert_level": "warning",
  "alert_message": "仍有旧服房间/玩家/迁移中阻塞",
  "drained": false,
  "rollout": {
    "epoch": "rollout-20260612-1",
    "old_server": "game-server-old",
    "new_server": "game-server-new",
    "state": "Active",
    "started_at": 1713000000000
  },
  "blockers": {
    "blocked_room_count": 2,
    "blocked_player_count": 1,
    "stale_room_route_count": 0,
    "stale_player_route_count": 0,
    "blocked_room_samples": ["room-1", "room-2"],
    "blocked_player_samples": ["player-1"]
  }
}
```

状态语义:

- `empty` / `info`：没有 active rollout
- `blocked` / `warning`：仍有 old owner room route、迁移中/失败 room route 或指向旧服的 player route
- `drained` / `warning`：proxy route store 已排空，rollout 仍 active，需要人工收尾或显式控制面收尾
- `interrupted` / `critical`：rollout state 为 `Interrupted`，需要人工复查
- `error` / `critical`：`game-proxy` admin 控制面不可达、鉴权失败、超时、响应过大或 JSON 异常

失败兜底:

- `admin-api` 不把 `game-proxy` admin 失败升级成监控页 500 崩溃，而是返回 `ok=false`、`status=error`、`alert_level=critical` 与错误信息
- 前端再额外兜底 admin-api 请求失败，仍在 rollout 区域显示“控制面不可达”

### 5.5 `POST /api/admin/monitoring/archive`

手动触发一次归档任务。该入口与内置后台调度共用 Redis 分布式锁；已有任务运行时返回 `skipped=true`，不会并发执行第二份归档。

返回示例：

```json
{
  "ok": true,
  "archived": 160,
  "failed": 0,
  "source_buckets": 1920,
  "resolution_seconds": 60,
  "duration_ms": 3500,
  "skipped": false,
  "reason": null
}
```

当前归档逻辑：

- 按 `metrics:v2:history-index:<service>` 有界读取超过一小时的 5 秒桶，不执行 `SCAN`
- 同一服务最多 12 个 5 秒桶聚合成 PostgreSQL `metrics_archive` 的一条分钟记录
- PostgreSQL 幂等提交成功后才删除对应 Redis history hash 和 index member
- 默认启动后立即执行，之后每 5 分钟自动执行；手动入口用于补跑和运维检查

实现位置：

- `apps/admin-api/src/services/archive.js`

## 7. 归档实现现状

### 7.1 PostgreSQL 表

归档运行时只写 auth 库，Schema 由 `db/migrations/auth/20260729173000_add_admin_metrics_archive.sql` 管理；`db/init.sql` 仅是历史兼容与 catalog 对照来源。当前表和索引契约为：

```sql
CREATE TABLE IF NOT EXISTS metrics_archive (
  id bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  service_name varchar(64) NOT NULL,
  bucket_time integer NOT NULL CHECK (bucket_time >= 0),
  qps integer NOT NULL DEFAULT 0 CHECK (qps >= 0),
  latency_ms integer NOT NULL DEFAULT 0 CHECK (latency_ms >= 0),
  online_value integer NOT NULL DEFAULT 0 CHECK (online_value >= 0),
  extra jsonb NULL,
  created_at timestamptz NOT NULL DEFAULT current_timestamp
);

CREATE INDEX IF NOT EXISTS idx_metrics_archive_service_time
  ON metrics_archive (service_name, bucket_time);
CREATE UNIQUE INDEX IF NOT EXISTS uk_metrics_archive_service_time
  ON metrics_archive (service_name, bucket_time);
```

数据库约束只校验时间戳非负；`bucket_time` 的分钟对齐由归档实现负责，并通过 `service_name + bucket_time` 唯一索引保证同服务同分钟幂等。

### 7.2 当前归档策略

- Redis v2 history 保留 4,500 秒，包含一小时查询窗口和 15 分钟归档缓冲
- 超过一小时的 5 秒桶先按 `service + bucket` 聚合实例，再合并为一分钟一条服务级记录
- `bucket_time` 为分钟起点；`qps` 为分钟平均 QPS，`latency_ms` 为请求数加权延迟，`online_value` 为样本平均值
- `extra` 记录分辨率、源桶数、请求总数、在线峰值、实例集合及低基数扩展字段，不保存每个实例的完整历史曲线
- `admin-api` 启动后立即归档，此后默认每 5 分钟执行；多实例调度与手动入口通过同一 Redis 锁防重入
- 生产 Compose 显式设置 `METRICS_ARCHIVE_ENABLED=true`、`METRICS_ARCHIVE_INTERVAL_SECONDS=300`、`METRICS_ARCHIVE_LOCK_TTL_SECONDS=240` 和 `METRICS_ARCHIVE_BATCH_SIZE=240`
- PostgreSQL 当前没有自动保留期或删除任务，归档数据会持续保留

分钟归档、session 指标索引和 24 小时生产稳定性证据见[Registry 监控超时根治 Checklist](./checklists/Registry监控超时根治_checklist.md)。

### 7.3 当前查询限制

当前监控查询接口只读 Redis，不读 PostgreSQL。

因此“归档”当前的实际效果是：

- 减少 Redis 中的历史 metrics 占用
- 为后续补 PostgreSQL 历史查询能力预留数据

但它还不是“完整冷热分层查询”。

## 8. 与旧设计稿的主要差异

当前实现与旧版设计文档相比，已经有以下明确差异：

1. 前端路由实际是 `/monitoring` 与 `/monitoring/:service`，不是 `/admin/monitoring/*`。
2. 后端监控接口前缀是 `/api/admin/monitoring`，前后端路径不能混写。
3. 实现文件当前以 `.js` 为主，不是文档里旧写法的 `.ts`。
4. 监控接口使用固定服务列表，不依赖 `service-registry` 里的服务注册信息。
5. 历史 metrics 查询当前只读 Redis，没有实现“超过一小时自动查 PostgreSQL”。
6. 详情页图表实现比旧设计简化，没有完整 tooltip、自动滚动和 time 轴能力。
7. Redis 实时 metrics 已支持多实例 key 和实例明细，但 PostgreSQL 归档表尚未支持按实例维度回查历史。

## 9. 注意事项

1. 监控接口已挂 `JwtAuthGuard` 和 `AdminPolicyGuard`，但生产仍不应作为玩家公网入口暴露。
2. `admin-web` 的监控页面受前端路由守卫保护，后端 `GET` 查询允许 `viewer` / `operator` / `admin`，手动归档仅允许 `admin`。
3. 自动调度和手动入口共用 Redis 锁；手动请求被锁跳过时属于正常防重入，不代表归档失败。
4. 角色体系 GM 写操作走 `admin-api` HTTP 路径，会同时写 `admin_audit_logs` 和游戏域日志；监控排查时应关注 `admin-api` 的 4xx/5xx、延迟尖刺和审计日志中 `gm_character_*` 动作。权限不足由 `AdminPolicyGuard` 写入 `security_audit_logs.event_type=admin_policy_denied`。
5. 四属性、称号和职业 GM 写操作不经过 `game-server` admin TCP，也不依赖 NATS；它们直接访问游戏库，这不是内部服务 host/port 直连路径，也不属于 registry endpoint 发现范围；生产环境必须保证 `ADMIN_GAME_DATABASE_URL` / `GAME_DATABASE_URL` 指向正确游戏库，且后台 API 只暴露在运营网络边界内。
6. 如果后续补上 PostgreSQL 历史查询、服务注册联动或更细粒度权限控制，本文需要继续同步。
