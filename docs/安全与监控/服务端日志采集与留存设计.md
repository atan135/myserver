# 服务端日志采集与留存设计

## 1. 文档定位

本文定义 MyServer 在 Docker 单机部署下的普通运行日志采集、短期缓冲、本机留存和后续归档边界。它是独立的日志架构设计文档，不是采集器安装手册；具体实现状态以代码和部署配置为准，本文定义目标态的职责、边界和数据契约。

本文状态为“目标设计，采集器尚未落地”。当前实现与目标态必须分开阅读。

本文只讨论普通运行日志。`admin_audit_logs`、`security_audit_logs`、`game_connection_audit_logs` 等审计数据，以及 Redis/NATS/PostgreSQL 中的 metrics 数据，仍由各自的持久化或监控设计负责。

## 2. 设计目标

- 业务服务保持统一输出到 stdout/stderr，不要求每个应用维护长期文件日志。
- 采集器持续读取 Docker 提供的稳定日志接口，将日志按服务、实例和 UTC 日期落盘到宿主机 `/data/myserver/log`。
- Docker 日志保留固定大小和文件数上限，作为采集器短暂停机或排障时的有限兜底，不作为长期事实源。
- 采集器输出支持按 `level`、服务、实例、时间和发布版本检索；不通过应用端物理拆分 `info.log` 与 `error.log`。
- 采集延迟、重连、补采、落盘失败、磁盘压力和可能的缺口可观察，无法补回的窗口必须明确报告。
- 已关闭的本机分片可被后续压缩、上传或异机归档工具只读消费，归档工具不修改活动文件。

## 3. 当前实现现状

当前生产 Compose 中业务服务使用 `LOG_ENABLE_FILE=false`，应用日志以 console 为主输出。Node.js 服务的日志实现为 `log4js`，Rust 异步服务使用 `tracing + tracing-subscriber + tracing-appender`；这些库提供应用内日志级别和 console/file 开关，但不代表生产已经启用长期文件日志。

Docker 宿主机使用 `local` logging driver，当前基线为单容器 `20m x 3`。运维脚本 `ops-logs.sh` 当前直接调用 `docker logs`。仓库中尚未有普通运行日志采集器，也没有已落地的 `/data/myserver/log` 持续输出链路。

因此，在采集器完成前：

1. 最近日志和 Docker 保留窗口内的历史日志通过 `docker logs` 查看。
2. Docker 日志文件的保留时间受日志量、`max-size` 和 `max-file` 共同影响，不能按日期保证长期可追溯。
3. 不应把当前 `LOG_DIR`、容器内部 `logs/` 或 Docker 私有目录当作长期日志接口。

## 4. v2 目标架构

目标数据流如下：

```text
业务服务 stdout/stderr
  -> Docker local driver（固定大小的短期缓冲）
  -> 常驻日志采集器（稳定日志流/API）
  -> /data/myserver/log/<service>/<UTC 日期>/<instance>.0001.jsonl
  -> 后续归档工具（压缩、校验、上传或异机保存）
```

采集器运行在宿主机或等价受控的运维环境中，不进入业务容器，不要求业务容器访问 Docker socket。若采用运维容器，必须单独审查 Docker socket 的权限和隔离边界。

采集器先读取 Docker 保留窗口内可获得的历史记录，再进入实时跟随。重连和重启通过有界 checkpoint、容器 ID 和日志流身份恢复读取位置；禁止把定时执行一次 `docker logs` 作为主采集机制。

## 5. 数据与文件契约

### 5.1 目录和文件

目标根目录固定为 `/data/myserver/log`：

```text
/data/myserver/log/
  <service>/
    <YYYY-MM-DD>/             # UTC 日期
      <instance-id>.0001.jsonl
      <instance-id>.0002.jsonl
```

服务名、实例 ID 和分片号必须经过白名单和路径安全校验。不同容器或实例不得共同覆盖活动文件。分片达到配置的大小上限后，采集器先 flush 并关闭旧文件，再原子创建下一分片；跨 UTC 日期时同样切换目录，单条记录不得被拆分。

采集器应区分活动分片和已关闭分片。后续归档工具只读取已关闭分片，并通过 manifest、哈希或等价完整性证据确认归档成功后再清理本机文件。

### 5.2 记录 envelope

每条 JSONL 记录应尽量包含以下字段：

| 字段 | 说明 |
|---|---|
| `service` | 规范化服务名 |
| `container_id` | Docker 容器 ID |
| `instance_id` | `SERVICE_INSTANCE_ID`，缺失时使用安全降级标识并告警 |
| `release_id` | release/build 标识，无法获取时为空或 `unknown` |
| `captured_at` | 采集器接收时间，使用 UTC |
| `event_time` | 原始日志时间，可解析时填写 |
| `level` | 规范化级别；无法解析时为 `unknown` |
| `stream` | `stdout` 或 `stderr` |
| `message` | 原始消息或结构化消息 |
| `parse_status` | 解析状态，保留非 JSON、异常编码等情况 |

无法解析为 JSON、时间或级别的记录不得被静默丢弃；应保留原文并标记解析状态。单条消息必须有大小上限，异常输入不能无限消耗采集器内存或队列。

## 6. 日志级别和查询方式

普通运行日志以完整日志流为事实源。`INFO`、`WARN`、`ERROR` 等级别在采集器 envelope 中规范化，查询工具按 `level=error`、服务、实例和时间范围筛选。

默认不让每个服务同时维护 `info.log` 与 `error.log`：这会产生重复写入、轮转不同步、跨文件排序和遗漏上下文等维护成本。需要错误视图时，应由采集器下游查询生成，或从已关闭分片生成可重建的派生文件；派生视图不是原始事实源。

`stderr` 不能自动等同于 `ERROR`。采集器应同时保留 stream 和解析后的 level，避免把运行时输出流误判成业务错误。

## 7. 职责边界

| 数据类型 | 事实源 | 普通运行日志采集器是否负责 |
|---|---|---|
| 服务运行日志、启动/退出、请求和运行时错误 | console 日志流及采集器输出 | 是 |
| 管理员操作审计 | PostgreSQL `admin_audit_logs` 等审计表；必要时保留隔离 JSONL | 否，不合并为普通日志 |
| 安全事件审计 | PostgreSQL `security_audit_logs` 等安全审计表 | 否，不以普通日志替代 |
| 连接审计 | `game_connection_audit_logs` 或对应审计实现 | 否，按审计策略单独留存 |
| QPS、延迟、在线人数等 metrics | NATS -> `metrics-collector` -> Redis/PostgreSQL | 否，`metrics-collector` 不是日志采集器 |

`metrics-collector` 自身的启动、连接和错误 console 输出仍属于普通运行日志；目标态采集器应采集这些输出，但不采集或重写其 NATS/Redis/PostgreSQL metrics 数据。

审计写入失败、metrics 写入失败和普通日志解析失败必须有各自的故障语义；任何一类数据不得伪装成另一类链路已经成功。

## 8. 缓冲、延迟和丢失边界

Docker `local` driver 是有限窗口。采集器正常运行时，`/data/myserver/log` 应成为日常排障主入口；采集器延迟、重启、Docker API 不可用或输出目录写入失败时，运维人员再使用 `docker logs` 查看仍在 Docker 保留窗口中的记录。

采集器必须持续流式读取并维护位点，而不是依赖轮询间隔。若采集器停止时间超过 Docker 保留窗口，旧日志可能已经被 Docker 覆盖，无法补回；采集器必须输出缺口时间段或疑似丢失计数，不能宣称绝对零丢失。

采集器故障不得让业务请求同步等待或导致业务进程退出。采集器自身应使用有界队列、批量写入和重试，并暴露读取延迟、队列深度、重连次数、落盘失败、补采范围和磁盘保护状态。

## 9. 容量、保留和后续归档

Docker 缓冲、采集器本机保留和远端长期归档是三个独立的保留层：

1. Docker 缓冲：固定大小和文件数，服务采集器短暂停机和即时兜底。
2. `/data/myserver/log`：按日期和大小分片，保留期与宿主机容量、排障需求和归档成功状态共同决定。
3. 专门仓库、对象存储或异机磁盘：保存压缩后的长期日志，并承担跨主机恢复职责。

本机清理只能针对已确认完成远端归档、或明确允许丢弃的已关闭分片；清理前应记录 manifest、哈希和清理结果。达到磁盘保护阈值时应告警并按预定优先级处理，不能无限增长，也不能静默删除尚未归档的日志。

月度压缩、远端上传、跨主机复制和恢复演练不属于当前采集器目标的隐含完成项。它们应由独立的归档任务和工具负责，输入只读消费已关闭分片。

## 10. 安全和权限

- `/data/myserver/log` 只允许采集器和受控归档工具写入；业务容器不得访问其他服务日志或长期归档目录。
- 采集器不得复制 secret 环境变量，不得记录密码、token、ticket、JWT、DSN、邮件正文、完整附件或其他敏感 payload。
- 服务名、实例 ID、日期和文件名必须防路径穿越、符号链接和未知服务写入。
- 采集器诊断日志不得输出 Docker socket 凭据、完整环境变量或其他服务路径中的敏感信息。
- 普通运行日志不替代数据库审计。需要不可抵赖、按操作者查询或权限审查的记录，应使用独立审计事实源。

## 11. 目标态实施顺序

实现应分阶段推进：先冻结职责和记录契约，再实现常驻采集、按日分片、Docker/生产接入、可靠性和故障测试，最后接入归档工具。首次上线时应先安装并验证采集器的实时延迟和补采能力，再启用清理策略。

在采集器尚未落地前，本文中“目标架构”“目标根目录”和“目标运维入口”均表示设计约束，不表示代码、Compose 或宿主机已经具备对应能力。采集器落地后，应回填本文的实现状态、实际参数、部署命令和验证证据。
