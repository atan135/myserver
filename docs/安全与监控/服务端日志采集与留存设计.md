# 服务端日志采集与留存设计

## 1. 文档定位

本文定义 MyServer 在 Docker 单机部署下的普通运行日志采集、短期缓冲、本机留存和后续归档边界。它是独立的日志架构设计文档，不是 Vector 安装手册；具体实现状态以代码和部署配置为准，本文定义目标态的职责、边界和数据契约。

本文状态为“代码与 release bundle 已落地，Linux/生产 live 验证待执行”。Vector 配置、systemd unit、部署准入和离线诊断已纳入仓库；未执行宿主机安装或故障注入时，仍不得把运行目录或延迟指标误报为线上事实。

本文只讨论普通运行日志。`admin_audit_logs`、`security_audit_logs`、`game_connection_audit_logs` 等审计数据，以及 Redis/NATS/PostgreSQL 中的 metrics 数据，仍由各自的持久化或监控设计负责。

## 2. 设计目标

- 业务服务保持统一输出到 stdout/stderr，不要求每个应用维护长期文件日志。
- Vector 持续读取 Docker 提供的稳定日志接口，将日志按服务、实例和 UTC 日期落盘到宿主机 `/data/myserver/log`。
- Docker 日志保留固定大小和文件数上限，作为 Vector 短暂停机或排障时的有限兜底，不作为长期事实源。
- Vector 输出支持按 `level`、服务、实例、时间和发布版本检索；不通过应用端物理拆分 `info.log` 与 `error.log`。
- Vector 的采集延迟、重连、补采、落盘失败、磁盘压力和可能的缺口可观察，无法补回的窗口必须明确报告。
- 已关闭的本机分片可被后续压缩、上传或异机归档工具只读消费，归档工具不修改活动文件。

## 3. 当前实现现状

当前生产 Compose 中业务服务使用 `LOG_ENABLE_FILE=false`，应用日志以 console 为主输出。Node.js 服务的日志实现为 `log4js`，Rust 异步服务使用 `tracing + tracing-subscriber + tracing-appender`；这些库提供应用内日志级别和 console/file 开关，但不代表生产已经启用长期文件日志。

Docker 宿主机使用 `local` logging driver，当前基线为单容器 `20m x 3`。release bundle 已携带 Vector `0.47.0` 配置、systemd unit、安装器、preflight、status、alerts 和 recovery-check；`ops-logs.sh` 优先读取 `/data/myserver/log`，Vector 输出不可用时才回退 `docker logs`。Windows 工作区仅完成离线/临时目录验证，宿主机 `/data/myserver/log` 的持续输出需在用户确认后于 Linux/WSL 安装并验证。

在 Vector 尚未于目标宿主机启动前：

1. 最近日志和 Docker 保留窗口内的历史日志通过 `docker logs` 查看。
2. Docker 日志文件的保留时间受日志量、`max-size` 和 `max-file` 共同影响，不能按日期保证长期可追溯。
3. 不应把当前 `LOG_DIR`、容器内部 `logs/` 或 Docker 私有目录当作长期日志接口。

## 4. v2 目标架构

目标数据流如下：

```text
业务服务 stdout/stderr
  -> Docker local driver（固定大小的短期缓冲）
  -> Vector（宿主机受控服务，`docker_logs` source）
  -> /data/myserver/log/<service>/<UTC 日期>/<instance-id>.<container-id-prefix>.<shard>.jsonl
  -> 后续归档工具（压缩、校验、上传或异机保存）
```

Vector 首选以宿主机 systemd service 运行，不进入业务容器，不要求业务容器访问 Docker socket；Vector 使用 Docker 支持的日志流/API（优先 `docker_logs` source）读取 stdout/stderr。若未来采用运维容器，必须单独审查 Docker socket 的权限和隔离边界。

Vector 先读取 Docker 保留窗口内可获得的历史记录，再进入实时跟随。重连和重启通过有界 `data_dir`/checkpoint、容器 ID 和日志流身份恢复读取位置；禁止把定时执行一次 `docker logs` 作为主采集机制。

### 4.2 运行制品与版本

v2 固定使用 Vector `0.47.0`（Linux `x86_64`）和 YAML 配置格式。发布 bundle 携带 `vector/vector.yaml` 与 `vector/vector.service`；服务器安装到 `/etc/vector/vector.yaml`、`/etc/systemd/system/vector.service`，二进制固定为 `/usr/bin/vector`，状态、checkpoint 和 disk buffer 固定在 `/var/lib/vector`。安装器先执行 `vector validate /etc/vector/vector.yaml --no-environment`（vector 0.47.0 validate 子命令只接受 positional 配置路径，不接受 `--config` yaml flag；加 `--no-environment` 跳过 healthcheck），再由受控运维窗口启用/启动 systemd；本阶段不自动启动服务。Vector 0.47.0 file sink `path` 字段仅支持 event 字段引用（如 `{{ service }}`）和 strftime 字面（如 `%Y-%m-%d`），不允许函数调用（如 `format_timestamp(...)`），模板变量必须在 VRL remap transform 中预先计算。

升级必须先校验新二进制版本和 SHA-256、离线执行 `vector validate /etc/vector/vector.yaml --no-environment`，再原子替换二进制并重启 Vector，保留上一版本二进制直到新进程完成 Docker 补采和实时延迟检查。回滚只切回已校验的上一版本并复用 `/var/lib/vector` checkpoint；不得删除输出目录、checkpoint 或已关闭分片，也不得通过清空 checkpoint 掩盖缺口。

### 4.1 生产服务 allowlist

普通运行日志采集只允许以下九个生产应用服务，服务名必须与 Compose service name 精确匹配；未知服务、临时测试容器和 Vector 自身均拒绝写入业务输出根目录：

```text
game-server
game-proxy
auth-http
admin-api
chat-server
match-service
mail-service
announce-service
metrics-collector
```

`metrics-collector` 是 metrics 数据的消费者（NATS -> Redis/PostgreSQL），不是 metrics 专用日志框架。它自身的启动、连接和错误 console 输出仍属于普通运行日志，已落地的 Vector 与其他八个服务一样采集；Vector 不读取或改写其 metrics 数据，也不把 metrics 数据转成普通日志。

## 5. 数据与文件契约

### 5.1 目录和文件

目标根目录固定为 `/data/myserver/log`。服务目录只能来自上述 allowlist，日期目录一律使用 UTC：

```text
/data/myserver/log/
  <service>/
    <YYYY-MM-DD>/             # UTC 日期
      <instance-id>.<container-id-prefix>.<shard>.jsonl
      <instance-id>.<container-id-prefix>.<shard>.jsonl.open
```

文件名中的 `instance-id` 使用 `[A-Za-z0-9._-]` 安全字符并限制 64 字节；`container-id-prefix` 为 Docker ID 的前 12 个十六进制字符；`shard` 为从 `0001` 开始的四位十进制序号。同一实例的不同容器不得复用同一文件名。写入中的分片使用 `.jsonl.open` 后缀，完成 flush、fsync 和关闭后原子 rename 为 `.jsonl`；后续归档工具只读取无 `.open` 后缀的文件。服务名、实例 ID、日期和分片号都必须经过白名单、路径穿越和符号链接校验。

单个分片达到 `256 MiB`（二进制 `268435456` 字节）上限时，Vector 先完成当前 JSONL 记录、flush 并关闭旧文件，再原子创建下一分片；跨 UTC 日期时同样切换目录，单条记录不得被拆分。

Vector `0.47.0` file sink 不提供单文件大小 rotation；阶段 3 使用 `scripts/docker/rotate-vector-files.sh` 作为受控协调器。sink 持续写入 `.jsonl.open`，轮转器在达到 `256 MiB` 后获取 `/var/lib/vector/rotation.lock`，停止 Vector 触发 sink flush/close，执行 `sync -f`，按同一实例/容器计算下一个四位 shard 并原子 rename 为 `.jsonl`，随后重新启动 Vector 从 checkpoint 恢复。轮转器拒绝未知服务、日期、实例、容器前缀、符号链接和目标冲突；失败时保留原文件并尝试恢复 Vector。只有无 `.open` 后缀的分片可供归档工具读取。

阶段 3 的 `prune-vector-files.mjs` 默认只读扫描最近 `14` 个 UTC 日期之外的已关闭分片；只有 `archive-manifest.jsonl` 中存在匹配的相对路径、大小和 SHA-256，且显式携带 `--apply --confirm vector-retention-v2` 时才删除，并在 `/var/lib/vector/retention-actions.jsonl` 追加机器可读结果。未归档、manifest 不匹配、`.open` 活动文件、符号链接和未知目录一律跳过并报告，不以清理规避磁盘保护阈值。

Vector 应区分活动分片和已关闭分片。后续归档工具只读取已关闭分片，并通过 manifest、哈希或等价完整性证据确认归档成功后再清理本机文件。

### 5.2 记录 envelope

每条 Vector 输出的 JSONL 记录必须包含以下字段（字段名和类型属于稳定契约）：

| 字段 | 说明 |
|---|---|
| `service` | 规范化服务名 |
| `container_id` | Docker 容器 ID |
| `instance_id` | `SERVICE_INSTANCE_ID`，缺失时使用安全降级标识并告警 |
| `release_id` | release/build 标识，无法获取时为空或 `unknown` |
| `captured_at` | Vector 接收时间，使用 UTC |
| `event_time` | 原始日志时间，可解析时填写；缺失或非法时为 `null` |
| `level` | 规范化级别（`trace`、`debug`、`info`、`warn`、`error`、`fatal` 或 `unknown`） |
| `stream` | `stdout` 或 `stderr` |
| `message` | 原始消息或结构化消息 |
| `parse_status` | 解析状态码数组，至少为 `["ok"]` 或包含异常码 |

`parse_status` 使用稳定的小写状态码数组，可同时包含多个值：`plain_text`（非 JSON，按原文保存）、`invalid_utf8`（异常编码，使用 UTF-8 replacement 字符并保留可追溯的 `message`）、`missing_event_time`（缺少或无法解析时间）、`unknown_level`（无法识别级别）、`truncated`（超过单条消息上限）。完全解析成功时为 `["ok"]`。无法解析为 JSON、时间或级别的记录不得被静默丢弃；原始字节无法直接表示时，`message` 必须使用确定性的 `\xNN` 转义或 replacement 文本，并在同一记录增加受限大小的 `raw_message_base64`，以便离线复核原始字节；`parse_status` 标明 `invalid_utf8`。单条消息上限为 `1 MiB`（`1048576` 字节），超限只截断该条并继续采集，同时记录 `message_sha256` 诊断摘要，不能无限消耗 Vector 内存或队列。

`raw_message_base64` 和 `message_sha256` 是仅在相应异常时出现的扩展字段，不改变上述十一个必需字段；扩展字段同样禁止携带 secret、token、ticket、DSN 或完整业务 payload。

## 6. 日志级别和查询方式

普通运行日志以完整日志流为事实源。`INFO`、`WARN`、`ERROR` 等级别在 Vector envelope 中规范化，查询工具按 `level=error`、服务、实例和时间范围筛选。

默认不让每个服务同时维护 `info.log` 与 `error.log`：这会产生重复写入、轮转不同步、跨文件排序和遗漏上下文等维护成本。需要错误视图时，应由 Vector 下游查询生成，或从已关闭分片生成可重建的派生文件；派生视图不是原始事实源。

`stderr` 不能自动等同于 `ERROR`。Vector 应同时保留 stream 和解析后的 level，避免把运行时输出流误判成业务错误。

### 6.1 查询入口

Vector 落地后，普通运行日志的首选入口是 `/data/myserver/log/<service>/<UTC 日期>/` 中已关闭的 `.jsonl` 分片；按 `service`、`instance_id`、`event_time`/`captured_at` 和 `level` 查询。Vector 延迟、重启或落盘失败时，使用目标容器的 `docker logs` 查看 Docker `local` driver 保留窗口内的短期兜底数据。admin/security audit 通过 PostgreSQL 的 `admin_audit_logs`、`security_audit_logs`（以及连接审计表）或 admin-api 的审计查询入口；数据库迁移/部署审计通过各数据库 `_myserver_migration_audit` 与 SQLx history；metrics 通过 `metrics-collector` 写入的 Redis/PostgreSQL metrics v2 查询入口。不得用普通运行日志代替这些事实源。

## 7. 审计与职责边界

### 7.1 admin audit 日志隔离

`game-server` 和 `game-proxy` 的 admin audit 不属于普通运行日志，不能共用可互相读取的 `game-audit` volume。生产部署分别使用两个 named volume：

```yaml
game-server:
  volumes:
    - game-server-audit:/var/log/myserver
  environment:
    GAME_ADMIN_AUDIT_PATH: /var/log/myserver/admin-audit.jsonl

game-proxy:
  volumes:
    - game-proxy-audit:/var/log/myserver
  environment:
    PROXY_ADMIN_AUDIT_PATH: /var/log/myserver/admin-audit.jsonl

volumes:
  game-server-audit:
  game-proxy-audit:
```

`GAME_ADMIN_AUDIT_PATH` 和 `PROXY_ADMIN_AUDIT_PATH` 必须使用容器内绝对路径，避免相对路径落入 `/app` 可写层而在容器重建时丢失。Vector 的 `docker_logs` source 只采集 stdout/stderr，不读取或把这两个 JSONL 文件合并为普通运行日志；若未来需要采集 audit 文件，必须另设独立的 Vector `file` source、权限和留存策略，并保持 audit 查询与 PostgreSQL 审计事实源的边界。

生产 Compose 已将 `game-server` 和 `game-proxy` 分别挂载 `game-server-audit`、`game-proxy-audit`，并固定使用 `/var/log/myserver/admin-audit.jsonl`；应用默认配置中的相对路径仅适用于非生产环境，不能覆盖生产 Compose 的绝对路径。

### 7.2 普通运行日志与其他数据边界

| 数据类型 | 事实源 | Vector 普通运行日志链路是否负责 |
|---|---|---|
| 服务运行日志、启动/退出、请求和运行时错误 | console 日志流及 Vector 输出 | 是 |
| 管理员操作审计 | PostgreSQL `admin_audit_logs` 等审计表；必要时保留隔离 JSONL | 否，不合并为普通日志 |
| 安全事件审计 | PostgreSQL `security_audit_logs` 等安全审计表 | 否，不以普通日志替代 |
| 数据库迁移/部署审计 | 各数据库 PostgreSQL `_myserver_migration_audit` 与 SQLx history | 否，不以普通日志替代 |
| 连接审计 | `game_connection_audit_logs` 或对应审计实现 | 否，按审计策略单独留存 |
| QPS、延迟、在线人数等 metrics | NATS -> `metrics-collector` -> Redis/PostgreSQL | 否，`metrics-collector` 不是日志采集器 |

`metrics-collector` 自身的启动、连接和错误 console 输出仍属于普通运行日志；Vector 采集这些输出，但不采集或重写其 NATS/Redis/PostgreSQL metrics 数据。

审计写入失败、metrics 写入失败和普通日志解析失败必须有各自的故障语义；任何一类数据不得伪装成另一类链路已经成功。`game-server` 审计不可写时，高风险 admin 写操作在状态变更前拒绝并返回 `ADMIN_AUDIT_WRITE_FAILED`；业务处理后追加失败仍返回明确的审计写失败。`game-proxy` 审计追加失败返回 500/`admin audit write failed`，不把普通运行日志当作补偿事实。Vector 普通日志解析失败仅在 envelope `parse_status` 标记并继续输出，不阻塞业务；落盘失败/队列溢出由 Vector 指标和 fallback 入口报告。

## 8. 缓冲、延迟和丢失边界

Docker `local` driver 是固定的有限窗口：每个容器 `max-size=20m`、`max-file=3`，理论上最多保留约 `60 MiB`，实际窗口随日志量变化。Vector 正常运行时，`/data/myserver/log` 应成为日常排障主入口；Vector 延迟、重启、Docker API 不可用或输出目录写入失败时，运维人员再使用 `docker logs` 查看仍在 Docker 保留窗口中的记录。

Vector 必须持续流式读取并维护位点，而不是依赖轮询间隔。若 Vector 停止时间超过 Docker 保留窗口，旧日志可能已经被 Docker 覆盖，无法补回；Vector 必须输出缺口时间段或疑似丢失计数，不能宣称绝对零丢失。

Vector 故障不得让业务请求同步等待或导致业务进程退出。Vector 自身使用有界队列、批量写入和重试：磁盘队列上限 `1 GiB`，内存队列上限 `64 MiB`；达到上限时配置 `drop_newest`，即保留已排队的较旧记录、丢弃新到的普通运行日志并产生缺口告警，不阻塞业务容器。错误/安全审计不经过该普通日志队列。必须暴露读取延迟、队列深度、重连次数、落盘失败、补采范围和磁盘保护状态。

阶段 2 配置通过 Vector `internal_metrics` source、localhost API `127.0.0.1:8686` 和 `vector-status.sh` 暴露诊断：`component_received_events_total`/`component_sent_events_total`、buffer bytes、component errors、进程 uptime，以及 checkpoint 文件时间和最新已关闭/活动分片 mtime。脚本输出首次可见 checkpoint、最新读取/落盘近似时间和磁盘占用；真实缺口仍以 Vector source/sink error、Docker 保留窗口和人工核对为准，不宣称阶段 2 已具备精确 gap 计数。Vector 重启/容器替换的旧游标诊断在 `/var/lib/vector` 保留，阶段 3 再完善分片级 first/latest read/write 和原子状态标识。

## 9. 容量、保留和后续归档

Docker 缓冲、Vector 本机保留和远端长期归档是三个独立的保留层。v2 默认参数如下，部署可在不低于磁盘保护阈值的前提下显式调整并记录：

1. Docker 缓冲：每容器 `20m x 3`，服务 Vector 短暂停机和即时兜底。
2. `/data/myserver/log`：单分片 `256 MiB`；默认保留最近 `14` 个 UTC 日期目录（`14 x 24h`），仅清理已关闭且已确认归档或明确获准丢弃的分片。
3. 专门仓库、对象存储或异机磁盘：保存压缩后的长期日志，并承担跨主机恢复职责。

本机清理只能针对已确认完成远端归档、或明确允许丢弃的已关闭分片；清理前应记录 manifest、哈希和清理结果。`/data` 可用空间低于 `20%` 时告警并暂停新增归档清理以外的低优先级写入；低于 `10%` 时 Vector 进入保护模式（停止创建新分片、保留诊断并报告缺口），低于 `5%` 时由运维立即停止清理任务并扩容/转移数据。任何阈值动作都不得静默删除尚未归档日志，也不能无限增长。

Vector 本地输出和已关闭分片默认保留 `14` 天；`data_dir`/checkpoint 仅保留当前及最近容器/流位点，不按日志正文扩张，也不保存 secret 或完整日志正文。磁盘队列达到 `1 GiB` 上限时按 `drop_newest` 触发保护和缺口告警。

月度压缩、远端上传、跨主机复制和恢复演练不属于当前 Vector 目标的隐含完成项。它们应由独立的归档任务和工具负责，输入根目录只读为 `/data/myserver/log`，只消费无 `.open` 后缀且通过大小、JSONL 行完整性和 SHA-256 manifest 校验的已关闭分片；任何 `.open` 文件、临时文件、符号链接、未知服务/日期/实例目录均排除并告警。归档工具不得移动、截断或修改活动文件。

## 9.1 故障与恢复边界

| 情形 | 必须可观察的结果 | 恢复边界 |
|---|---|---|
| Vector 正常停止/重启 | systemd 状态、最后读取/落盘时间、队列深度和 checkpoint 路径可查询 | 重启后从 checkpoint 补读仍在 Docker `20m x 3` 窗口内的记录；窗口外不承诺补回 |
| 容器替换 | 新旧 container ID、实例 ID 和起止时间分别记录；旧分片关闭 | 新容器建立独立游标和文件，不覆盖旧容器；相同实例 ID 也不得合并文件 |
| Docker API 不可用 | Vector 记录重试、错误码、估算缺口和延迟；业务容器保持运行 | API 恢复后按 checkpoint 补采可获得窗口；超过 Docker 窗口的缺口必须报告 |
| `/data` 磁盘满/只读 | 落盘失败、剩余空间、保护模式和受影响服务告警 | 不阻塞业务；恢复可写空间后继续新分片，期间仅能从 Docker 窗口兜底 |
| checkpoint 损坏/不可读 | 拒绝静默从零开始；记录校验失败并隔离损坏文件 | 人工确认后以新 checkpoint 从 Docker 可读窗口重新补采，可能重复但不得静默跳过；重复由 `container_id`+时间+消息哈希诊断 |

## 10. 安全和权限

- `/data/myserver/log` 只允许 Vector 和受控归档工具写入；业务容器不得访问其他服务日志或长期归档目录。
- Vector 不得复制 secret 环境变量，不得记录密码、token、ticket、JWT、DSN、邮件正文、完整附件或其他敏感 payload。
- 服务名、实例 ID、日期和文件名必须防路径穿越、符号链接和未知服务写入。
- Vector 诊断日志不得输出 Docker socket 凭据、完整环境变量或其他服务路径中的敏感信息。
- 仓库/CI 的 `scripts/docker/scan-log-sensitive-patterns.mjs` 只扫描受控 Node/Rust 日志源、Vector 配置/unit、Compose 和运维诊断脚本；它拒绝原始 token/ticket/password、DSN、通知 payload、Docker 私有日志路径和 secret 文件引用，不读取生产 secrets、Docker 私有目录或运行期输出。
- 普通运行日志不替代数据库审计。需要不可抵赖、按操作者查询或权限审查的记录，应使用独立审计事实源。

## 11. 上线与后续归档顺序

首次上线顺序固定为：初始化 `/data/myserver/log`、`/var/lib/vector` 和权限；离线校验 bundle 并安装 Vector；启动 Vector；用 `vector-preflight.sh`、`vector-status.sh`、`vector-alerts.sh` 验证补采、实时延迟、队列和磁盘；再启动或更新业务服务；最后在确认 manifest 后启用清理。回滚时保留 Vector 输出、checkpoint 和 Docker 缓冲，先停止清理任务，必要时切回已校验的 Vector 版本；不得删除 Docker/应用容器来绕过缺口诊断。

后续压缩或远端归档工具只读消费 `/data/myserver/log` 中无 `.open` 后缀的关闭分片，按相对路径、大小、JSONL 完整性和 SHA-256 生成/校验 manifest，成功后再移动或压缩；活动文件、临时文件、符号链接、未知服务和未知日期一律排除。长期目标可为专门日志仓库、对象存储或异机磁盘，传输失败需有界重试、重复归档按 manifest 幂等处理，并通过独立恢复演练确认本机缓存不超过容量上限；这些后续工作不阻塞本版本采集链路验收。

宿主机首次上线和清理前应记录实际服务/实例、Vector 采集延迟、磁盘占用、队列和 Docker fallback 观察结果。本文的 Linux/systemd/Docker live 验证记录必须由受控环境补写，不能用 Windows 离线测试替代。
