# MyServer 缺失功能详细清单

更新时间：2026-07-19

## 文档目标

本文用于梳理 MyServer 相对 `mybevy` 当前游戏世界观和玩法目标仍缺少的服务端能力，并作为后续专题设计、独立功能 checklist 和开发排期的功能地图。

本次重梳理不再以“通用大型 MMO 功能是否齐全”为唯一判断标准，而以当前项目的独特核心循环为主：无传统等级的四属性修行、职业/流派、称号、方圆灵构、界域开拓、纪元更替、天道自演、天道灵压、宗门议会、须弥空间和纪元档案。支付、拍卖行、通行证等通用商业化能力仍属潜在缺口，但在产品边界确定前不进入当前主路线。

## 判断口径

- 当前代码、协议、数据库和配置优先于文档。
- MyServer 整体边界以 `docs/总览/整体架构.md` 及对应专题文档为准。
- 产品目标主要参考 `C:/project/mybevy/docs/世界观/`，尤其是 `世界观总览.md`、`玩法体系设想.md`、`方圆灵构.md`、`天道自演.md`、`天道灵压.md`、`纪元天道议会.md`、`背包与须弥空间.md` 和 `灵名溯源.md`。
- `mybevy` 世界观文档大多是目标态，不代表客户端或服务端已经实现；其中仍标记“待补充设计”的规则，必须先形成专题设计，不能直接按描述编码。
- `mybevy` 本地 RON 蓝图、渲染、Prefab、Chunk、LOD 和预览能力属于客户端/工具链基线；只有权威审核、持久化、多人同步、资产归属和世界生命周期属于 MyServer 缺口。

状态标记：

- `已落地基线`：代码和数据结构已有明确闭环，本清单不重复列为缺失。
- `半闭环`：已有模型或 demo，但尚不能支撑目标玩法。
- `缺失`：未见可用的服务端模型、协议或运行时闭环。
- `待设计`：产品规则仍不足，开发前必须先补专题设计。

## 当前已落地基线

以下能力已存在，不应继续按“完全缺失”处理：

- 账号下多角色的创建、列表、选择、软删除、恢复，以及 ticket 绑定 `character_id`。
- 稳定全局 ID、`world_id`、世界来源成员关系和世界合并事件的基础数据结构。
- 角色四属性亲和/掌握、变更日志、查询与推送。
- 职业/流派学习、激活、切换、积累点数、阶位配置与审计日志。
- 称号解锁、佩戴、过期字段、查询、推送与审计日志。
- 角色进度配置和奖励入口，但当前仍只是成长底座，不等于完整事件驱动修行系统。
- 背包、仓库、装备、属性、Buff、外观、持久化和幂等 GM 发物品主链路。
- 场景表、出生点、区域、传送门、NPC、怪物刷新、交互和场景上下文的配置加载/查询基础。
- Room 生命周期、帧推进、重连、观战、匹配、空房迁移/灰度接管和服务发现基础。
- 聊天、邮件、公告、管理后台、审计和 metrics 基础链路。
- 战斗 ECS、技能/Buff catalog、移动同步和锁步模拟 demo。
- PostgreSQL 五库已具备 SQLx 版本化迁移、迁移审计、存量 baseline、漂移检测、独立回填、部署 gate、静态 CI 与受保护临时库的故障/恢复演练；`db/init.sql` 仅作为兼容和对照保留。详见[数据库迁移体系 Checklist](../docs/数据库/checklists/01_数据库迁移体系_checklist.md)。

这批基线的主要问题是“尚未被统一世界规则和真实玩法消费”，而不是模型完全不存在。

## 目标能力依赖

```text
角色修行事件 + 统一资产事务 + 世界/区域模型
  -> 方圆洞府 / 灵构工坊 / 界域开拓
  -> 天道灵压 / 天道自演
  -> 宗门界域工程 / 纪元天道议会
  -> 纪元结算、迁移、档案与传承
```

## 功能域 1：角色修行与身份闭环


当前状态：`半闭环`。四属性、流派、称号和角色进度已有存储与协议，但主要通过直接接口或调试入口变化，尚未形成世界事件驱动的无等级成长闭环。

- 定义统一修行事件模型，覆盖探索、战斗、采集、建造、制作、治疗、世界事件和组织贡献等来源。
- 建立服务端权威事件入口，禁止客户端直接提交最终掌握度、流派点数、阶位或称号结果。
- 为事件增加 `event_id/request_id`、来源对象、世界、区域、纪元、发生时间和规则版本，保证幂等与可追溯。
- 把四属性掌握、流派点数、阶位晋升和称号解锁接到同一结算事务，失败时整体回滚。
- 将亲和与掌握的边界规则配置化，明确哪些行为能改变先天亲和、哪些只能增加后天掌握。
- 补齐流派前置条件、互斥/并行规则、激活切换冷却和跨世界有效性。
- 建立称号来源、有效期、撤销、历史保留和纪元荣誉分类，不把称号仅作为展示字符串。
- 扩展角色档案，展示稳定短标识、当前世界层级、流派阶位、主称号、组织和纪元荣誉。
- 明确重名策略：允许灵名重名，以稳定 ID 和上下文区分；移除“全服角色名必须唯一”的旧式假设。
- 在聊天、交易、排行榜、举报和组织管理等高风险场景携带可区分身份信息，防止同名冒充。
- 为成长结算增加异常增量、重复事件、越权来源和规则版本漂移的日志与指标。
- 增加修行事件到属性/流派/称号结果的单元测试，以及重复投递和事务回滚测试。

## 功能域 2：统一世界、纪元与区域权威模型


当前状态：`半闭环 + 待设计`。已有 `worlds`、来源合并记录和场景上下文，但没有世界层级、纪元状态机、区域运行状态或角色纪元归属闭环。

- 补充世界分层与纪元专题设计，明确下界/中界/上界命名、层数、周期、准入和开放玩法。
- 建立 `World`、`Epoch`、`Region`、`WorldRuleVersion` 的稳定身份、状态机和持久化模型。
- 区分 `world_id`、`scene_id`、`region_id`、`room_id` 和运行实例 ID，禁止用 Room 直接代替长期世界身份。
- 建立角色当前世界、当前纪元、历史世界、迁移状态和迁移原因记录。
- 定义安全区、普通区、开拓区、秘境和镜像区的规则标签，并由服务端权威校验交互权限。
- 将 `ScenePortal`、`SceneRegion`、`SceneContext` 接入真实传送、区域进入/离开和条件判断，而不只停留在配置查询。
- 建立世界规则快照，记录资源倍率、属性潮汐、准入条件、灵压阈值和灵构预算等可变参数。
- 明确世界规则发布、灰度、生效时间、版本兼容和回滚流程。
- 设计飞升、暂缓飞升、留界、回流和重新飞升状态机，所有迁移都可重试且可审计。
- 设计高阶角色留在低层世界时的天道压制，保存永久成长并只计算场景内有效值。
- 为新手和低活跃角色保留基础体验，世界规则不得锁死回流路径或必要主线。
- 增加跨世界迁移、重复结算、部分失败恢复和旧规则版本兼容测试。

## 功能域 3：方圆灵构服务端权威链


当前状态：`缺失`。`mybevy` 已有本地蓝图格式、校验、预算和预览路线，但 MyServer 未见正式蓝图存储、审核、归属、发布或多人同步。

- 先确定客户端 RON 是否仅为创作源格式，并设计稳定、可版本化的服务端传输/存储格式，避免直接绑定 Rust RON 实现细节。
- 定义蓝图身份、所有者、对象类型、源版本、编译版本、内容哈希、审核状态和生命周期。
- 建立文本/语音意图提交、AI 生成任务、结果回调、超时、取消和重试状态机；语音转写本身可由外部能力承担。
- 对生成提示和结果做输入长度、敏感内容、提示注入、路径、资源引用和数据规模校验。
- 服务端实现独立审核器，校验 cube/sphere 约束、primitive 数、bounds、材质 profile、role、socket、碰撞、遮挡和性能预算。
- 建立按家园、装备、技能、NPC/天道生成物分类的预算 profile，不能用客户端本地审核结果代替服务端判定。
- 计算角色灵构额度，读取四属性、流派、称号、世界层级、纪元规则和对象分类限制。
- 审核失败返回稳定错误码、finding 和可接受降级建议，而不是仅返回布尔失败。
- 将“个性表现层”和“系统规则层”分离；蓝图不得写入真实伤害、奖励、资源产出、控制时间或碰撞危险边界。
- 建立草稿、预览、修订、确认、发布、撤回、封存和重校状态机，并对并发修订使用版本号或 ETag。
- 支持蓝图资产归属、收藏、复制来源、可见性和删除保护，保留生成与审核审计。
- 生成可供客户端缓存的 manifest、依赖表、内容哈希和缺失资源 fallback 信息。
- 为蓝图解析、预算边界、恶意输入、并发确认、审核重放和规则版本升级增加测试。

## 功能域 4：方圆洞府、家园与灵构试炼场


当前状态：`缺失`。客户端有静态家园预览和后续 Chunk/LOD 路线，服务端尚无洞府实例、布局资产、放置权限或访客规则。

- 定义个人洞府的长期身份、所属世界、落位区域、实例策略、访问策略和生命周期。
- 持久化洞府当前发布蓝图、布局版本、对象实例、交互状态和纪元校准状态。
- 实现放置、移动、删除、撤销和发布的服务端校验，检查边界、重叠、预算、权限与版本冲突。
- 区分纯装饰、轻互动、储物入口、修行设施和组织入口；第一阶段只开放无经济收益或模板化轻功能。
- 建立主人、访客、协作者和 GM 权限，覆盖参观、点赞、评论、举报和编辑。
- 建立洞府分享/访问路由、离线加载、空实例回收和重连恢复。
- 让洞府蓝图可继承，但迁入新世界后必须根据空间、地脉、安全区和灵构额度重新落位。
- 实现超预算或规则不兼容时的封存/降级，禁止直接删除玩家长期蓝图资产。
- 建立灵构试炼场，允许测试蓝图可读性、碰撞、性能和技能模板映射，但不发放常规副本收益。
- 记录试炼规则版本、输入、权威结果和回放摘要，为后续技能蓝图审核提供证据。
- 增加两名玩家并发访问、编辑冲突、实例回收恢复、跨纪元重校和恶意布局测试。

## 功能域 5：界域开拓、场景实体与四属性事件


当前状态：`半闭环`。已有场景配置、移动/战斗 demo 和 Room 容器，但缺少可持续的区域状态、通用世界实体、任务事件和开拓结算。

- 建立通用世界实体身份和生命周期，覆盖玩家、NPC、怪物、资源点、机关、传送节点、灵构对象和天道生成物。
- 实现通用 AOI/兴趣管理，提供 enter/leave、实体快照、增量广播、重连重建和 fanout 指标。
- 把外观、称号、流派、Buff、掉落和附近交互推送接入 AOI，而不是仅发给本人或 demo 房间全广播。
- 建立区域开拓状态机：未发现、侦察、建立阵标、稳定地脉、开放、衰退、重组。
- 配置开拓目标模板，覆盖探索、修复传送节点、清理灵压、区域事件和多人协作贡献。
- 建立通用任务/目标引擎，目标和奖励由服务端模板定义，并由移动、战斗、交互、背包和区域事件推进。
- 建立 NPC/怪物模板、刷新、仇恨、AI、死亡、掉落和归位闭环；将现有场景表从加载成功推进到真实运行时消费。
- 建立四属性区域事件，让事件类型、交互分支和结算结果读取角色掌握、流派和当前纪元属性潮汐。
- 建立统一奖励结算和资产事务，物品、货币、进度、称号和贡献具备幂等、审计与回滚能力。
- 补齐物品堆叠、掉落归属、拾取、合成/制作和来源追踪；不在资产事务完成前开放玩家交易。
- 为区域状态、实体快照和玩法进度定义 Room Transfer 导出/导入边界，明确哪些是 Room 临时状态、哪些是世界长期状态。
- 增加区域事件并发贡献、重复领奖、实体迁移、AOI 重建和 Room 迁移一致性测试。

## 功能域 6：天道灵压与容量分流


当前状态：`缺失 + 待设计`。现有 metrics 和房间容量底座尚未形成“区域玩家体验指标 + 服务端负载”的统一压力模型。

- 定义区域压力计算规则，组合人数、技能频率、结算频率、实体数、灵构量、交互频率和节点负载。
- 为安全区、普通区、战场、秘境和世界事件配置独立阈值、滞回区间与冷却，避免等级抖动。
- 建立轻度、中度、重度和群修天劫状态机，记录进入原因、规则版本、持续时间和恢复条件。
- 轻度阶段先做预警和表现事件；中度阶段才做收益/非关键交互调节；重度阶段提供明确迁移入口。
- 安全区只允许镜像分流、排队、展示降级和柔性限流，不使用高伤害惩罚。
- 保护新手、回流、主线关键步骤和必要交互，任何分流都不得永久损伤资产。
- 实现镜像区域、相邻区域或安全区的候选选择，迁移失败时可回到原权威节点并重试。
- 将热点信号提供给 AOI、Chunk/LOD、Room 调度和客户端表现，但保持各自降级边界。
- 记录压力来源、受影响玩家、采取动作、迁移结果和恢复耗时，并配置告警。
- 增加阈值边界、抖动、节点过载、迁移失败、安全区保护和突发世界事件压测方案。

## 功能域 7：天道自演与世界记忆


当前状态：`缺失 + 待设计`。应按风险从纯表现和弱互动起步，不能直接接资源、怪物和高价值奖励。

- 定义生成意图模型，记录区域空缺、玩家互动、组织占领、属性潮汐、纪元预兆和低活跃区域等触发来源。
- 建立灵感、显化、活跃、衰退、固化、归档状态机，所有转换具备原因、时间和规则版本。
- 第一阶段只支持纯表现层：装饰、碑文、低成本异象和无奖励 NPC 外观。
- 第二阶段支持弱互动：查看、对话、点赞、收藏、举报、家园邀请和个人见闻。
- 复用方圆灵构审核链和区域预算，天道生成内容不能使用另一套无约束规则。
- 建立因果值账本，区分查看、互动、收藏、组织/事件引用、举报成立和长期无人互动等增减来源。
- 因果值只决定衰退/固化候选，不直接生成战斗强度、稀缺资源或高价值奖励。
- 建立区域内容预算和回收策略，预算压力下优先回收装饰、临时残留和个性表现层。
- 模板任务层只能由 AI 生成外观、对话和故事包装，目标、数量、冷却和奖励必须来自固定模板。
- 资源/怪物/世界事件层延后到统一经济、战斗模板和世界预算成熟后再开放。
- 所有生成物支持审核、举报、GM 回收和审计保留；删除运行实体不得删除必要历史记录。
- 增加生成任务重复回调、违规内容、预算竞争、衰退回收、固化和纪元归档测试。

## 功能域 8：宗门、界域工程与纪元天道议会


当前状态：`缺失 + 待设计`。聊天群不能替代宗门；议会依赖组织、贡献、世界事件和纪元状态，不能提前做成孤立投票接口。

- 建立宗门/联盟身份、成员、职位、权限、申请、退出、转让、解散和操作日志。
- 保留散人参与模型，不把所有世界内容强制绑定宗门。
- 建立组织贡献账本，来源必须是可验证的开拓、事件、工程和成员行为，不能由客户端直接报数。
- 建立宗门界域工程的蓝图、材料捐献、阶段进度、空间落位、权限、维护和纪元迁移状态。
- 组织资产和玩家资产使用统一事务、冻结、幂等和审计规则。
- 支持跨世界保留组织关系，并为跨界聊天、支援、交易和整体迁移配置门槛与冷却。
- 定义议会资格、议席、代表授权、撤销授权、散人代表和临时联盟规则。
- 议题必须来自运营配置的有限选项，不接受玩家自由文本直接修改底层规则。
- 建立议题发布、立场、内部投票、世界事件投入、结算、公示和申诉状态机。
- 实现单组织权重上限、连续主导限制、异常投票检测和反方补偿，防止大组织长期垄断。
- 议会结算生成下一纪元规则候选，经版本化发布流程生效，不直接修改在线世界配置。
- 将参与角色、组织、结果、称号和纪元历史持久化并可追溯。
- 增加权限越权、重复投票、授权撤回、并发结算、组织解散和规则发布回滚测试。

## 功能域 9：须弥空间、资产封存与纪元传承


当前状态：`半闭环 + 待设计`。现有背包/仓库是技术基线，但须弥空间不是普通仓库皮肤，需要解锁、远程访问、分类限制和跨纪元封存。

- 明确随身背包、普通仓库、须弥空间、洞府陈列和交易冻结区的职责与资产所有权。
- 设计须弥空间解锁和扩容规则，接入四属性、流派、称号、试炼、道具或纪元奖励。
- 为物品定义重量/体积、活体、不稳定、区域绑定、任务绑定、纪元绑定、污染和交易锁定等存储标签。
- 服务端校验存入、取出、远程取用、批量整理和跨区访问，客户端不能通过容器 ID 绕过限制。
- 建立远程取用的战斗、任务、交易、区域、冷却和消耗规则。
- 为地/火/水/风和流派提供差异化承载、保存、隔离和远程调度能力，但避免形成不可维护的特殊分支。
- 建立冻结/封存容器；超限、违规或新世界不兼容资产进入封存，不直接删除。
- 定义角色迁移清单：永久成长、称号历史、流派、背包、须弥空间、家园/装备/技能蓝图和纪元记录。
- 对区域绑定、世界事件绑定和旧规则资产执行可解释的保留、封存、重校或补偿策略。
- 纪元迁移使用可恢复工作流，记录导出清单、校验哈希、目标导入、所有权切换和失败回滚。
- 建立纪元档案，保存角色、组织、世界事件、议会结果、高因果内容、蓝图和称号历史。
- 增加跨纪元重复执行、部分资产失败、超限封存、远程取物竞态和旧版本资产兼容测试。

## 功能域 10：运营控制面、生产与数据治理


当前状态：`半闭环`。已有管理后台、审计、metrics、服务注册和灰度迁移基础，但尚不能运营上述世界系统。

- 管理后台支持世界、纪元、区域规则、灵压状态、蓝图审核、天道生成物、宗门、议题和迁移工作流查询。
- 高风险操作采用细粒度权限、二次确认/审批、操作理由、前后快照和审计，不只依赖管理员登录态。
- 支持冻结/恢复蓝图、回收生成物、修复区域状态、重跑结算和恢复封存资产；所有动作幂等且可追踪。
- 建立统一 outbox/inbox 或等价可靠事件机制，覆盖跨服务成长结算、奖励、迁移、通知和归档。
- 数据库 schema 已完成 SQLx 正式迁移、版本记录、漂移检测、回填治理、部署 gate 与 CI；后续世界系统新增表、跨服务事务、归档和数据保留策略仍须按此体系接入和补齐。
- 为核心表定义备份、恢复、归档、数据保留、隐私删除和大表索引策略。
- 建立世界/区域/玩法级 SLI：在线实体、AOI fanout、tick 延迟、压力等级、生成队列、审核延迟、迁移结果和资产事务失败率。
- 配置容量阈值、告警、降级开关和应急 runbook，验证 Redis、NATS、PostgreSQL、AI 供应方或单服务不可用时的行为。
- 协议和配置变更具备版本兼容、灰度顺序、旧客户端处理和回滚方案。
- 补齐单元、属性、集成、故障注入和负载测试；涉及真实服务联调时按仓库约定先列出依赖并等待确认。
- 同步 MyServer 架构、协议、数据库、运维和对应世界观落地文档，明确目标态与已实现状态。

## 暂缓项与触发条件

以下不是“永远不做”，而是当前世界观主循环尚不足以决定服务端模型：

- 玩家自由交易、拍卖行和跨界交易：统一资产事务、身份反欺诈和世界经济规则完成后再设计。
- 多货币、商城、支付、通行证和商业化活动：商业模式确定后单独建专题，不默认套用传统 MMO 模型。
- 竞技场、段位和传统副本池：核心战斗和技能蓝图规则生产化后再确定。
- 排行榜：先明确它服务于纪元资格、组织贡献还是展示，避免先建一个无业务口径的通用榜单服务。
- 自由 AI 任务与资源生成：模板任务、统一奖励、世界预算和审核回收闭环全部完成后再开放。
- 跨服实时战斗和大规模无缝世界：先完成区域权威、AOI、热点分流和 Room/世界状态边界验证。

## 优先级与独立立项建议

以下优先级只表达依赖与产品价值，不把多个功能域压缩成同一个开发 checklist：

1. `P0`：角色修行与身份、世界/纪元/区域模型、方圆灵构权威链。
2. `P1`：方圆洞府、界域开拓、场景实体与天道灵压。
3. `P2`：天道自演的纯表现层和弱互动层。
4. `P3`：宗门界域工程与纪元天道议会。
5. `P4`：须弥空间、纪元迁移、档案与长期资产传承。
6. 运营控制面和生产治理是所有功能域的横切要求，应进入每份独立 checklist。

后续立项时，原则上一个功能域至少拆成一份完整 checklist；范围较大的功能域应继续拆分。例如“方圆灵构服务端权威链”可以分别建立蓝图协议与存储、AI 生成任务、审核预算、发布同步四份 checklist。本文不记录开发阶段、时间、完成状态或验证结果。

## 跨功能域完成约束

以下内容是各独立功能设计和 checklist 都应按适用范围继承的共同约束，不表示本文本身可据此勾选完成：

- 角色长期成长由四属性、流派、称号和事件贡献表达，客户端无法直接决定结果。
- 世界、纪元、区域和 Room 身份边界清晰，纪元结算与迁移可重试、可回滚、可审计。
- 方圆灵构从意图、生成、审核、预览到发布形成服务端权威闭环，AI 不能直接生成强度或收益。
- 至少形成“洞府/灵构工坊”和“四属性事件/界域开拓”两条可持续玩法闭环。
- 天道灵压能根据体验和负载渐进分流，并保护安全区、新手、回流和关键流程。
- 天道自演至少完成纯表现和弱互动层，生成物可审核、可举报、可回收、可归档。
- 宗门贡献和议会结果可验证，组织不能绕过上限或直接篡改底层世界规则。
- 背包、须弥空间、蓝图、称号和纪元档案在迁移中有明确继承、重校和封存策略。
- 所有资产、成长、组织、投票、生成和迁移关键动作具备幂等、权限、审计和失败恢复。
- 关键协议、配置、数据库迁移、指标、告警、降级、测试和运维文档达到生产准入要求。
